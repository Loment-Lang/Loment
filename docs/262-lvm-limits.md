# 262 · LVM 的上限：**逐个点名，并写出语料的实测最大值**

> 状态: **规范**（2026-10-18，issue #353）· 判据: `tools/lvm_stability_test.py` 判 C
> 一句话: **改一个上限应当是"一个决定"，不是"一个猜"** —— 所以每个常量旁边都要有数。

---

## 1. 为什么要有这一页

`tools/lvm.py` 从第一天起就有边界检查与一个步数上限（后者是 2026-10-18 才补上的，见 §4），
`loment/tools/lvm.lomt` 则有一整套固定容量。**但没有任何一页说清它们是多少、满了会怎样、
离满还有多远。** 于是"把这个常量调大"只能靠猜，而"跑得动"与"快跑不动了"分不出来 ——
固定表越界在镜像那侧**不一定是报错**（见 §3）。

本页就是那张表。**判据 C 盯着它存在**；数值变了就要改这里，改不动就是一次决定。

## 2. 参考实现（`tools/lvm.py`）

| 常量 | 值 | 含义 | 满了会怎样 |
|---|---|---|---|
| `MEM_SIZE` | **16 MiB** | 整个 VM 地址空间 | 读/写越界当场抛 `LvmError`（`读越界` / `写越界`） |
| `GLOBAL_BASE` | 64 KiB | `[0, 64 KiB)` 是零页，全局从这儿起 | —— |
| `FRAME_SIZE` | 4096 | 每层调用的栈区 | 与堆相撞时抛 `栈溢出` |
| `SLOT` | 8 | 每个标量一格 | —— |
| `STEP_CAP` | **50,000,000** | **一次函数调用**里执行的指令条数 | 抛 `步数上限 …`，点名函数 / 块 / 第几条 |
| `MAX_DEPTH` | **128** | 调用深度（语料实测最大 **10**；镜像那边是 32） | 抛 `栈溢出（调用深度上限 128）` |

**为什么深度上限是 128 而不是"地址空间算出来的 4080"**：4080 是**地址**能放多少层，
而**宿主 Python 的栈**在 ~200 层就先炸 —— 那之前程序会死在一个 `RecursionError` 上，
**那不是 VM 的话**。取 128 是两头都留余量：比镜像的 `MAX_DEPTH = 32` 宽松（孪生不会因此更严），
又远低于宿主栈。（这一条是判据 B 当场抓的：深递归夹具先撞了 Python，而不是撞 VM。）

## 3. 自举镜像（`loment/tools/lvm.lomt`）

固定表，没有"动态增长"这条路。**右列是落地这一页时的实测最大值**（语料 9 份，2026-10-18）。

| 常量 | 值 | 语料最大 | 满了会怎样 |
|---|---|---|---|
| `MAX_GLOBALS` | 256 | 37 | 点名报"全局表满了" |
| `MAX_FUNCS` | 512 | 281 | 点名报 |
| `MAX_PARAMS` | 2048（每函数 ≤10） | 每函数 10 | 点名报 |
| `MAX_BLOCKS` | 8192 | 每函数 139 | 点名报 |
| `MAX_INSTRS` | 32768 | 全程序 10659 | 点名报 |
| `MAX_EDGES` | 65536 | 每条 `br` 1–2 条、`switch` N+1 条 | 点名报 |
| `MAX_VALS` | 1024（一帧） | 每函数 227 | 点名报 |
| `MAX_DEPTH` | 32 | **10** | 点名报 |
| `MEM_SIZE` | 4 MiB | —— | 越界**不一定**报：镜像的边界检查只覆盖它显式检查的那几处 |
| `FRAME_SIZE` | 32768 | —— | 帧用尽会点名报（"帧用完了"） |
| `STEP_CAP` | 50,000,000 | 见下 | 点名报 |

⚠ **"点名报"不等于"处处点名报"**。固定表越界在镜像那侧**可能是段错误**而不是错误消息 ——
这是**已经踩过**的一类（`docs/243` §5.1）。所以这张表的作用不是"证明它安全"，
是**让人知道离墙有多远**（每一格现在至少还有一个数量级）。

## 4. 步数上限：参考实现此前**没有**

这是这一页落地时补上的第一个缺口。镜像一直有 `STEP_CAP`，参考实现**没有** ——
于是"挂死"与"慢程序"在参考那侧根本分不开，而所有判据都跑在参考实现上。

现在三档（t0 / t2 / t3）都有，口径一致：**一次函数调用**里执行的指令条数。

**语料的实测**（整趟，不是单次调用；所以单次调用的上限只会更小）：

| 程序 | 整趟执行的指令数 |
|---|---|
| `lumtui_demo`（最重） | **2,193,819** |
| `tour` | 1,005 |
| `all_loment` | 961 |
| 其余 6 份 | < 600 |

⇒ 离 50,000,000 还有 **20 倍以上**的余量。**上限不是性能护栏，是"不许挂死"**（`docs/243` §5.1
同一句）：真撞上它意味着程序在跑死循环，不意味着它慢。

## 5. 语料的形状（判据 C 要的那个"旁边有数"）

| 量 | 最大 |
|---|---|
| 函数数 | 281（`lumtui_demo`） |
| 每函数块数 | **139** |
| 每函数指令数 | **350** |
| 每函数形参数 | **10** |
| 调用深度 | **10** |

`MAX_BLOCKS` 的注释里写着"每函数 ≤139"，与这张表对得上 —— 那是它当初立表时的依据。

## 6. 我不主张

1. **不主张这张表让 VM 变成"不会崩"**。§3 那条警告就是反例：固定表越界可能是段错误。
2. **不主张上限值是对的**。它们是**当时的**决定；这一页的用处是让下一次改动**看得见代价**，
   不是把现值当成结论。
3. **不主张步数上限能抓住所有挂死**。它抓的是"执行了太多指令"；一个阻塞在系统调用上的
   程序它管不着（VM 目前的系统调用表里没有会阻塞的号）。
