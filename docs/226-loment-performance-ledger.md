# 226 · Loment 的性能账：运行 / 编译 / 胶水

> 2026-10-11 · **这份文件是"要动 Loment 的性能"时先读的那一份** —— 三个轴各有实测表、
> 口径、已知缺陷与杠杆清单。上游：`docs/212`（卸载：那 10.7× 与三件套）、
> `docs/200`（`lomelf` 的表容量）、`docs/204`（语言取舍）、`docs/143` §93（`use` 上限）、
> issue `#44` / `#226`（编译器的递归没有护栏）。
> 复现脚本在本文件 §7，自足。

## 0. 一句话

**三个轴各有各的瓶颈，而且都不在同一条线上**：运行慢在**后端没有优化器**（原生 ≈ C -O2 的
**4.0–6.4×**）；编译慢在**前端**（前门翻译 + 检查占了三分之二，且随规模**超线性**）；
胶水**不慢**——调一个 C 函数比调自己的函数还便宜（**0.65 ns vs 1.46 ns**），进程桥每次
**0.36 ms**。所以"Loment 慢"这句话，分开看才有下一步。

## 1. 口径（不照做会量到别的东西）

| | |
|---|---|
| 机器 | AMD Ryzen 9 7945HX，WSL2（Linux），`nproc` = 32 |
| 版本 | **仓内 HEAD**（`2e21d07` 时的 `tools/`），**不是**装的 0.1.4 包 |
| 运行侧 | 产物是 x86-64 **静态 ELF**，在 WSL 里直接跑；`min of N`（与 `docs/212` 同口径） |
| **计时位置** | **所有样本在一次 `wsl` 调用里量完**（用 WSL 内的 python3） |
| 对照 | C 用 WSL 的 `gcc`（-O0 / -O2）；Rust 用 Windows 的 `rustc -O` |

**两个必须记下来的坑**（第一版都踩了）：

1. **一次 `wsl -e bash -lc` 光启动就 ~130 ms。** 每个样本各起一次 WSL，量到的是 WSL 启动
   开销而不是负载 —— 第一版的四行数（178/131/155/152 ms）就是这么来的，与负载无关。
   **计时必须在一次 WSL 调用内做完。**
2. **`timeout` / 退出码要看真的那一个。** 第一版没看退出码，把
   "`alloc(65536)` 崩了（SIGILL，rc=132）" 当成了 "34 ms，很快"。

**边界（诚实）**：

* **Rust 那一列在 Windows 上跑**（WSL 里没有 rustc）—— **跨 OS，不可与其余列直接比**，
  只作旁证。要正经比，得把 rustc 装进 WSL。
* 数字是**相对**的：换机器绝对值会变，比值才是结论。

> **订正（2026-10-11 同日）**：本节初版写着"本机**没有 clang**，所以 **IR → clang -O2**
> 的卸载路本轮没量"。**那句是错的** —— clang 在 `C:\Program Files\LLVM\bin\clang.exe`
> （22.1.8），只是**不在 `PATH` 上**，我用 `command -v clang` 查漏了。那条路补量如下。

### 2.1 卸载那一格：**Loment 的 IR 喂 clang -O2，快 3.7×**

同一份 `sum`（§2 那张表的第一行），同一台机，`min of 5`：

| 产物 | ms | 相对 lomelf |
|---|---|---|
| `lomelf` 原生 | 56.6 | 1.00× |
| **同一份 IR → `clang -O2`** | **15.3** | **0.27×** |
| 手写 C（`gcc -O2`，§2） | 11 | 0.19× |

命令就是一行（`docs/212` §5 粒度 A 的原话）：

```bash
python tools/lomentc.py --emit llvm prog.lomt -o prog.ll
clang --target=x86_64-unknown-linux-gnu -O2 -static -nostdlib -ffreestanding -o prog prog.ll
```

**这是 `docs/212` §4 那条"天花板就是 C"的直接实测**：同一个后端（LLVM），
Loment 的 IR 编译出来只比手写 C 慢 **1.4×**，而原生栈机慢 5.1×。
§6 的杠杆 2 因此从"理论上成立"变成"这一格已经量过"。

## 2. 运行速度：原生 ≈ C -O2 的 4.0–6.4×

同一份算法三条路（`min of 5`，单位 ms）：

| 负载 | Loment 原生 | C -O0 | C -O2 | **原生/C-O2** | Rust -O（Windows，旁证） |
|---|---|---|---|---|---|
| `sum`（20M 次 `acc += (i*7)%1000`） | 56 | 20 | 11 | **5.13×** | 24 |
| `mem`（5M 次字节写+读，32 KiB 缓冲） | 34 | 10 | 6 | **5.95×** | 15 |
| `fib(32)`（纯递归调用） | 18 | 11 | 5 | **4.01×** | 18 |
| `bits`（2M 次 Kernighan popcount 内循环） | 42 | 14 | 6 | **6.41×** | 15 |

**怎么读这张表**：

* **原生比 C -O0 还慢 1.6–3.4×** —— 这是"栈机 + 没有寄存器分配"的直接代价，
  与 `docs/212` §1 那条 10.7× 是同一件事，只是那份语料是**数组**码、这份是标量码。
* **内存型负载吃亏更多**（`mem` 5.95×、`bits` 6.41% 对上 `fib` 4.01×）：
  栈机每访问一次访存都要走槽位，没有寄存器把它们留住。
* `docs/212` §4 那条仍成立：**Loment 的 IR 就是 LLVM IR**，所以天花板是 C 本身——
  换后端（卸载）就能把这一格整个拿掉。

**杠杆**：① `lomelf` 加寄存器分配/窥孔（治本，付的是后端复杂度）；
② 卸载给真后端（`docs/212` 的粒度 A：`clang -O2 prog.ll`，一行的事，但要 clang）。

### 2.2 LVM 的四档（T0 / T1 / T2 / T3）—— 以及它离原生有多远

> 2026-10-18，issue #354。口径同 §1：同一进程背靠背、`min of N`；原生那一列在 WSL 里
> `date +%s%N` 取三次最小。**绝对值只在这一次测量里成立**，比值才是结论。

| 程序 | 原生（`lomelf`） | T0 解释 | T1（T0+剖面） | T2 编译 | T3（T2+守卫特化） |
|---|---|---|---|---|---|
| `lumtui_demo` | **5 ms** | 6454.5 ms | 6906.4 ms | 1152.3 ms | 1673.2 ms |
| `tour` | —— | 9.97 ms | 9.91 ms | 7.87 ms | 9.35 ms |

**比值**：`lumtui_demo` 上 T2 = **T0 的 1/5.60**、T3 = **1/3.86**；对原生，T0 慢 **1291×**、
T2 慢 **230×**、T3 慢 **335×**。

**诚实列（这一档最该看的三句）**：

1. **VM 比原生慢两到三个数量级。** 它是解释器，而原生自己已经比 C `-O2` 慢 10.7×
   （`docs/212`）。把 VM 当"更快的路"是反的（`docs/232` §1.2 第一条）。
2. **T3 比 T2 慢**（1673 vs 1152）。原因在**实现**不在设计：T3 的 `_body` 把每条指令都交给
   一个 Python 函数（`self._one`），而 T2 的热路径是**就地展开**的。这一格今天的卖点是
   **"去优化那条路成立"**（`docs/261` §1），不是快。要提速就把热路径抄回去 —— 那是一次
   实打实的改动，不是调参。
3. **T1 的记录不是免费的**：重的那份 **+7%**（6454 → 6906）。判据只要求"记录不改变被记录的
   行为"（`docs/247` 判据 D），**没有**要求它零开销 —— 这句写在这里，免得以后被当成回归。

**为什么不给比值门禁**：墙钟比值随机器散布（同一个量测出过 3.2× / 4.13× / 5.4×，界 5.0
正落在散布里）。`tools/lvm_perf_test.py` 因此只给**绝对天花板**（120s，抓挂死 / 掉一个数量级）
与**符号**（T2 < T0、T3 < T0）。

### 2.2.1 A4 超级指令（T2 + 融合，`docs/266` / issue #647）

> 2026-10-19。同一进程交替跑、`min of 3`。**只判符号**，倍数记账。
> 从这一页起 **T2 默认带 A4** —— 上一节表里的 T2 绝对值是 A4 之前量的。

| 夹具 | T2 不融合 | T2 融合 | 比值 |
|---|---:|---:|---:|
| `lumtui_demo` | 1202 ms | **1168 ms** | 1.03× |
| 分派密集循环（3×10⁷ 条纯算术） | 4949 ms | **4507 ms** | 1.10× |

**为什么差这么多**：A4 省的是**分派**。`lumtui_demo` 的热点是访存与 `lvm.arith` 本身，
分派不是大头；纯算术循环把这一项放大到 10%。两个数都记着，免得拿 10% 去说真实程序。


### 2.2.2 镜像的 T2（`docs/267` / issue #586）

| 程序 | 镜像 T0 | 镜像 T2 | 倍数 | 执行期解码 T0 -> T2 |

## 3. 编译速度：前端是大头，且随规模超线性

阶段 = `front`（前门翻译 + 词法/语法/语义）/ `check` / `ir`（`emit_llvm`）/ `lomelf`（汇编）。

### 3.1 一个函数里的语句数

| 语句数 | front | check | ir | lomelf | 合计 | IR | ELF |
|---|---|---|---|---|---|---|---|
| 100 | 4 ms | 8 ms | 7 ms | 4 ms | 24 ms | 12 K | 16 K |
| 1000 | 35 | 73 | 107 | 29 | 243 ms | 120 K | 100 K |
| 5000 | 236 | 552 | 602 | 153 | 1.54 s | 614 K | 480 K |
| 20000 | 3.49 s | 1.88 s | 2.24 s | 735 ms | 8.35 s | 2.5 M | 1.9 M |
| 50000 | 17.1 s | 4.91 s | 5.83 s | 1.83 s | **29.7 s** | 6.4 M | 4.7 M |

几千条语句以内是平价；**上万条开始超线性**，5 万条要 30 秒。

### 3.2 函数个数（**不是瓶颈**）

10 个函数 9 ms、100 个 53 ms；**单模块 2000 个函数只 0.16 s**（1000 个 0.07 s）。
"函数多"本身不花钱。

### 3.3 模块个数（**这里最贵**）

来自 `loment/examples/megaproject/` 那条线（同一个判据 `loment_megaproject_test`）：

| 模块数 | load+check | ir | lomelf | ELF |
|---|---|---|---|---|
| 100 模块 / 1000 函数 | 1.7 s | 0.5 s | 0.1 s | 233 KB |
| 304（3 hub × 100 叶子） | 19.4 s | 2.0 s | 0.9 s | 1.4 MB |
| **1011**（10 × 100） | **192.1 s** | 7.0 s | 2.8 s | 4.73 MB |
| **2021**（20 × 100） | **765 s** | 16.1 s | 3.9 s | 9.46 MB |

**模块数 ×2 → 前端时间 ×4**（304→1011 是 3.33× 对 9.9×；1011→2021 是 2.0× 对 4.0×）——
干净的**平方**。而后端（IR + `lomelf`）**一直是秒级**：到上千模块时，代价**全在前端**。

> 顺带：一个文件最多 `use` **300** 条（`docs/143` §93，超了 E020，消息是"门面拆小"）。
> 所以"上千个模块"**不可能**由一个宿主平铺 —— 必须分层（Python 叶子 + 原生 hub）。
> 那条上限的边界样本在 `loment/examples/megaproject-java/`（宿主正好 300 条）。

### 3.4 一处**会崩**的地方：扁平长表达式（issue #226）

一个**扁平**（不是嵌套）的二元表达式到 **~250 项**，`check` 就抛 Python `RecursionError`：

```
$ python tools/lomentc.py --check deep.lomt     # 260 项的 a + a + …
Traceback (most recent call last): … 3002 行 …
RecursionError: maximum recursion depth exceeded
$ echo $?
1
```

**没有 `[ERR]`、没有文件、没有行号。** 阈值随进程已用的递归深度浮动（240 项有时过、
260 项必崩），所以它不是语言规则。触发是**深度**、不是内容：全写成同一个名字也崩，
一串 `f(1) + f(1) + …` 同样崩。

这与 issue **#44**（约 400 层嵌套**块** → SIGSEGV）是**同族**（递归走一遍结构、没有护栏、
没有诊断），但触发不同、阈值低得多。**要动编译器的性能/健壮性就先看这两条**——
它们是"规模上去之后第一批撞到的墙"。

## 4. 胶水速度：**调 C 比调自己还快**

### 4.1 C ABI（`extern fn` + `lomelf` 直接链一个 gcc 编的 `.o`）

同一个循环三种写法，相减得到每次调用的开销（N = 10 000 000，`min of 5`）：

| | ms | 每次调用 |
|---|---|---|
| 不调用（基线） | 26.7 | — |
| 调**本地** Loment 函数 | 41.3 | **1.46 ns** |
| 调 **extern** 函数 | 33.1 | **0.65 ns** |

**两条独立运行给出同样的次序**，所以不是噪声。**未验证的解释**（别当结论读）：
本地调用走的是 `lomelf` 自己的调用约定（参数摆栈、有帧），而 extern 是一次寄存器传参的
直接 `call` —— 在一个**没有优化器**的后端上，后者的序列反而更短。若解释成立，
"把热函数挪到 C"在这个后端上**连调用开销都不增加**，那是 `docs/212` 卸载那件事的一个额外理由。

### 4.2 进程桥（`use proc` 的 `proc_sh`）

| `proc_sh("true")` | ms |
|---|---|
| 程序自身启动（0 次调用） | 2.09 |
| 1 次 | 2.61（第一次 +0.52） |
| 20 次 | 9.37 → **每次 0.36 ms** |

0.36 ms 是 `fork`+`exec`+收回的价钱（WSL 的 fork 比原生 Linux 慢）。**按次调用它是这一档
最贵的东西**：一次进程桥往返 ≈ 一次 C 调用的 **55 万倍**。所以桥适合"一次起进程、
批处理"，不适合放进内循环。

## 5. 已知缺陷与边界（这一档会咬人的）

| 现象 | 出处 | 状态 |
|---|---|---|
| **扁平表达式 ≥ ~250 项** → `check` 抛 `RecursionError`（3000 行 traceback，无诊断） | **#226** | open |
| ~400 层嵌套**块** → SIGSEGV | **#44** | open |
| `alloc(65536)` **自己**就 SIGILL（rc=132，不写也崩）；二分：**57344 能用、65536 死** | 本条实测 | 与 SKILL 陷阱 6.2.14 那句（"`alloc(65536)` 成功、再加 64 才死"）**不符** |
| 一个文件 `use` 上限 **300** | `docs/143` §93 | 设计如此（E020，消息有用） |
| `lomelf` 回填表容量（小程序也可能满） | `docs/200` | 已知 |
| 前门在模块数上**平方** | 本条 §3.3 | 未见 issue，值得先量再报 |

## 6. 杠杆在哪（按"能收多少"排）

1. **后端加优化**（收掉 §2 那 4–6.4×）：`lomelf` 加寄存器分配 + 窥孔。
   代价是后端复杂度；`docs/212` §7 记过"不外包"这条路。
   **怎么证伪**：同一份 `sum`/`mem`/`bits`，原生/C-O2 的比值应当从 4–6 掉到 1–2。
2. **卸载给真后端**（`docs/212` 粒度 A）：`clang -O2` 直接吃 Loment 的 IR，**一行的事**，
   把 §2 整格拿掉。代价：那一档要 clang；可复现性要另说（`docs/212` §6）。
   **怎么证伪**：`Rust -O` 与 `C -O2` 同量级已是既证（`docs/212` §1），ir 喂 clang 后
   比值应当同样塌到 ~1。
3. **前端那平方**（收 §3.3）：先把热点定位到"前门翻译 / 检查 / 依赖解析"哪一段，
   再决定要不要缓存（同一份源在一次构建里被读了几次？`docs/182` §1.9 那类"读 L1 源的入口"）。
   **怎么证伪**：`--scale` 那几档的 load+check 时间应当从平方变成线性。
4. **递归护栏**（#226 / #44）：把"结构走太深"变成**一条诊断**而不是 Python 崩溃。
   这一条**与性能无关但必须一起做** —— 优化会改遍历方式，而现在的失败模式是静默崩溃。

## 7. 复现（自足；都不进包，`tools/` 才是随包发的）

三个脚本都放在仓根一个 `tmp` 目录里跑，路径按需改：

**§2 运行速度**

```python
# 四条负载：sum / mem / fib / bits。Loment 原生 vs C -O0/-O2，计时在**一次** WSL 调用里。
import subprocess, sys, time
from pathlib import Path
ROOT = Path(r"D:/Dev/Loment-DEV").resolve()
sys.path.insert(0, str(ROOT / "tools"))
import lomelf, lomentc
W = ROOT / "tmp-bench"; W.mkdir(exist_ok=True)
SRC = """module b

fn work_sum(n: u64) -> u64 {
    let acc: u64 = 0;
    let i: u64 = 0;
    while i < n { acc = acc + (i * 7) % 1000; i = i + 1; }
    return acc;
}

fn _start() { syscall4(60, work_sum(20000000) % 256, 0, 0); }
"""
p = W / "b.lomt"; p.write_text(SRC, encoding="utf-8", newline="\n")
mod = lomentc.load(p); deps = lomentc.resolve_deps(mod, ROOT, p.parent, entry=p)
assert not lomentc.check(mod, deps=deps)
blob, _ = lomelf.compile_ll(lomentc.emit_llvm(mod, ROOT, deps), [])
e = W / "b.elf"; e.write_bytes(blob)
wsl = "/mnt/" + str(e).replace("\\", "/")[0].lower() + str(e).replace("\\", "/")[2:]
subprocess.run(["wsl", "-e", "python3", "-c", f'''
import os, subprocess, time
os.chmod("{wsl}", 0o755)
best = None
for _ in range(5):
    t0 = time.perf_counter(); subprocess.run(["{wsl}"]); dt = time.perf_counter() - t0
    best = dt if best is None else min(best, dt)
print("loment sum:", round(best * 1000, 1), "ms")
'''])
# C 侧：写 b.c（同一个 work_sum），wsl 里 `gcc -O2 -o b.bin b.c`，用同一个计时循环跑
```

**§3 编译速度**：把 §3.1 的语句数换成你要扫的列表，逐段 `perf_counter()` ——
`lomentc.load` / `check` / `emit_llvm` / `lomelf.compile_ll` 就是那四段。

**§4 胶水**：`extern fn c_inc(x: i64) -> i64;` + `wsl gcc -O2 -c -o glue.o glue.c`，
再用 `lomelf.compile_ll(ir, [lomelf.ForeignObject(obj)])` 链进去；
三档（不调用 / 本地 / extern）相减，就是每次调用的开销。进程桥用 `use proc` 的
`proc_sh("true", buf, 4096)` 循环调用。
