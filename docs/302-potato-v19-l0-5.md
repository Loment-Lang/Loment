# Potato v19：`gc_ladder` 的第五格 `l0_5`

> 2026-11-04。设计背景与量出来的分布见 `docs/210` §2.10。

## 1. 为什么升版，而不是改四格

`gc_ladder` 从 v10 起有一条**自洽**判据：

```
l0 + l1 + l2 + l3 == total_sites
```

校验器读不到源码，判不了"这几个数数得对不对"，但判得了"它们自相矛盾"。
L0.5 是新的一格；如果直接把它加进那四个分量，**已经发出的 v10–v18 对象会一起变非法** ——
而台阶的规矩是**只往上加，不回溯改写**（`docs/147` §3）。

所以：

* **v19 起**，`gc_ladder` 有**五个**分量，`l0_5` **必填**；
* 自洽那条变成 `l0 + l0_5 + l1 + l2 + l3 == total_sites`；
* **v10–v18 的对象仍然只有四格**，仍然合法，也**不许**带 `l0_5`（那一版没有这一格）。

## 2. 形状

```json
"gc_ladder": {
  "l0": 1,
  "l0_5": 2,
  "l1": 1,
  "l2": 1,
  "l3": 1,
  "total_sites": 6
}
```

* 五个分量都是**非负整数**；
* `total_sites` 是**非负整数**，且等于五者之和；
* 键集合是**封闭**的：`l0_6` 之类会被点名拒。

## 3. 数的是什么

`l0_5` = 被**函数级栈区**接走的 `alloc` 站点（`docs/210` §2.10）。口径：

* 候选**就是** L0 的候选（`f.l0`）—— 不外逃、尺寸是字面量；
* 一个函数里**至少两处**才开区；只有一处的站点留在 L0；
* 合计超过 `L05_MAX = 2048` 字节时，按声明序先到先得，放不下的留在 L0。

于是 `l0 + l0_5` 恰好是"L0 的证明面"，拆开只是为了读者能看出**布局**：
`l0` 各自一条 `alloca`，`l0_5` 共用一块。
