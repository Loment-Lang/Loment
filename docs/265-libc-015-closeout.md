# 265 · LibC 0.1.5 收尾 —— 以及「孪生判据看不见的那一半」

> 状态: **记录**（2026-10-19）· 上游: `docs/219`（世界端口）· `docs/232`（LibL）·
> `docs/183`（V1/V2）· issue #360 / #406 / #595 / #591 / #617 / #631 / #637
> 一句话: 0.1.5 里 **50 条 LibC 缺陷 + 3 条极端缺陷**已经清完；清的过程中发现
> **包内那份链接器（自举镜像）比参考实现少一整类能力** —— 而"两边一致"的判据
> 看不见它（两边都不支持也是一致）。这一页记的是那一半怎么补上的。

---

## 1. 账目

`0.1.5` 的 LibC 线起点是 #574（V2 动态链接 + 发行闸 #406）。此后按用户要求
分三批开了 **50 条**（#590–#639，每条带 `file:line`、复现、修的方向）与
**3 条极端缺陷**（#641–#643，进程直接死而不是给诊断）。

收尾时按"先把修好的关闭"走了一遍：**23 条**在主线上已修，逐条带证据关闭；
剩下 5 条在 `feat/libc-015` 上补齐：

| issue | 缺陷 | 落点 |
|---|---|---|
| #591 | 没有 `.type` 的汇编导出（`STT_NOTYPE`）被当成"库里没有这个名字" | 两份实现的导出扫描都收 `0/1/2/10`（PR #885 / 本轮镜像） |
| #595 | 无 `DT_SONAME` 的 `.so` 只记 basename，产物跑起来找不到库 | `DT_NEEDED` 记**命令行给的路径**（GNU ld 同一条） |
| #617 | 弱未定义引用被当成硬需求：进端口门、进归档需要集，解析不到就报错 | 弱引用绑 0；`_GLOBAL_OFFSET_TABLE_` 由链接器定义 |
| #631 | 只链 `.so` 时不发收编面，`memcpy` 一族只能落到 glibc 的 IFUNC 上 | `objects or shared` 两边同一条判断 |
| #637 | Debian 的 `libc.so` 是 `GROUP (...)` 脚本，报成"不是 ELF 对象" | 两份实现都**点名脚本指向的真文件** |

`0.1.5` 里带 `libc` 标签的 issue 到此清零。

## 2. 这一轮真正的新东西：镜像追平参考

#609 / #610（`-fPIC` 的 `GOTPCREL` 族、`__thread` 的 `TPOFF32/64`）当时是按**参考实现**
验收并关闭的。收尾时把同一份对象喂给**包内那份**（`loment/tools/lomelf.lomt`，自举镜像）：

```
mirror: rc=1  loment: unknown relocation type (docs/173 section 3)
```

——一个 Debian 上默认开 hardening flags 的库，在**用户手上那只链接器**里根本链不过。
`test_lomelf_selfhost_matches_reference` 没红，因为它的语料是**纯 Loment 程序**，
一个外部对象都没有：**"两边产物逐字节相同"在两边都不支持时照样成立**（`docs/772`
那条"孪生只证明一致"的第二种形状）。

镜像这轮补上的：

- **静态 GOT**：`GOTPCREL` / `GOTPCRELX` / `REX_GOTPCRELX`，槽按名字排序（与参考同序，
  于是产物逐字节相同），槽内容 = 符号地址；
- **TLS 块**：`.tdata` / `.tbss` 按对象顺序摆，每个对象 16 对齐、块尾是线程指针
  （variant II）、之后 0x40 字节 TCB；`TPOFF32` 写 `S + A - TP`；
- **弱未定义**：名字进 `TB_WK`、不进端口门与需要集，解析不到时 `S = 0`
  （GOT 族写槽的相对位移，不写 0 —— 写 0 会让 `if (weak_fn)` 为真去 call 空地址）；
- **端口门后移到"所有对象摆完"**：`a.o` 调 `g`、`b.o` 定义 `g` 的自闭合组合不再被拒；
- **`_GLOBAL_OFFSET_TABLE_`** 由链接器定义（原先它会被数成"通向世界的端口"）；
- **GNU ld 脚本**：`GROUP (` / `INPUT (` 里的第一个路径印出来（#637）。

## 3. 判据

`loment_elf_test` 新增两条：

- `test_mirror_matches_reference_on_pic_tls_and_weak_objects`：四类对象
  （`-fPIC`、`__thread` × 2 个对象、弱未定义、弱定义 + 强定义）各链一遍，
  比较**两份实现的产物字节**、再**真跑退出码**（7 / 5 / 7 / 2）。
  最后一类**不开 `--allow-ports`**，钉住"端口门判的是解析之后还剩什么"。
- `test_a_gnu_ld_script_names_the_file_it_points_to`：两份实现都必须印出
  `/usr/lib/x86_64-linux-gnu/libc.so.6`，而不是一句"不是 ELF 对象"。

⚠ 这两条都**要求真的链过去**：只比"两边一致"会被"一起失败"骗过去。

## 4. 边界（下次别当成缺陷重新开）

- **TLS 只做 local-exec**（`TPOFF32/64`）。`-fPIC` 的默认模型是 global-dynamic
  （`TLSGD`），要 `__tls_get_addr` + GOT 对 —— 仍未做，**拒绝时点名类型**。
- **TLS 对象与共享对象一起链**：拒绝。这一版的 TLS 块只在自立产物里安装，
  动态链接时 `fs` 归 loader 管（参考实现同一句）。
- **`M_TLS` / 四张表的位置是硬编码**（`loment/tools/lomelf.lomt`）。#956（`#777`）
  合入后已按它的落点排好：`TB_GOT 5,775,136` / `TB_WK 5,824,288` /
  `TB_TLS 5,857,056` / `TB_ND 5,861,152`（表尾 5,893,920），`M_TLS` 在 `ARENA`
  （36,712,448）之后、`ARENA` 移到 **36,777,984**。再抬内存时四张表跟着表尾走，
  `M_TLS` 跟着 `ARENA` 走。
- 容量条数 228、沉默 156（`loment_caps_test`）；新增五处都有 `fail` 路径。
