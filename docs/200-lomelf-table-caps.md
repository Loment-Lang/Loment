# 200 — `lomelf` 的零碎表：容量、越界为什么是静默的、以及台面（`docs/192` 的姊妹篇）

`docs/192` 记的是**输入缓冲**那条上限（种子 `.ll` 装不装得进 `lomelf`）。这一篇记的是
**同一个病的另外三处**：`lomelf.lomt` 里那几张"单调 bump"的小表，以及 `lomrel.lomt`
的归一化副本。2026-09-20 实测撞上，
起因是 `docs/189` S1 第十九格（自举侧的 Potato 发射）把驱动链加长了。

## 1. 症状：一条空白标签名

自举链的第 1/4 步（`genesis` 把种子汇编成 stage1）报：

```
lomelf: 未定义的标签: 
```

**冒号后面是空的。** 没有文件名、没有行号、没有"哪个标签"—— 而 `.ll` 是逐行语法，
按常理该报出一个具体的名字。同一份种子喂给**参考实现**（`tools/lomelf.py`）完全正常，
所以这是一处**两个实现不一致**，而不是种子坏了（种子与参考实现逐字符相同，
`loment_seed_test` 一直绿着）。

## 2. 定位：先把"静默"变成"响亮"

`lomelf.lomt` 里那几张表都是这样的形状：

```rust
fn gadd(tab: ptr, ...) {
    let gi: u32 = cell(tab, C_NG);
    let gbase: u32 = TB_G + gi * 32;   // ← 没有任何边界检查
    ...
    setcell(tab, C_NG, gi + 1);
}
```

表与表**首尾相接**排在同一块 2 MiB 的表区里，于是第 N+1 条写的是**下一张表的开头**。
越界几十条不会立刻崩，只会把邻居改坏 —— 报出来的错离现场很远（这里：全局表写进标签表，
查标签查出一个空名字）。

所以修法第一步不是"抬容量"，是**让越界出声**。六个 `*_add` / `*_put` 各补一条守卫，
与 `IN_CAP` 那条（`docs/192` §1）同一个形状：

```rust
if gi >= TB_G_MAX {
    let _f: u32 = fail("全局表满了 — 抬高 TB_G 的容量 (loment/tools/lomelf.lomt 的 TB_G_MAX)");
}
```

加完再跑一次 bootstrap，它当场说出了真话：

```
lomelf: 回填表满了 — 抬高 TB_FIX 的容量 (loment/tools/lomelf.lomt 的 TB_FIX_MAX)
```

**这就是"响亮"的价值**：第一次抬了全局表（1801 → 2086 条，旧上限 2048）之后，
下面还压着一张回填表，如果不加守卫，第二次仍然是空白标签名。

## 3. 两处抬高与整条表区的重排

| 表 | 旧上限 | 新上限 | 旧起址 | 新起址 |
|---|---|---|---|---|
| 全局表 `TB_G` | 2048 | **4096** | 256 | 256 |
| 标签表 `TB_LBL` | 16384 | 16384（不动） | 65792 | **131328** |
| 回填表 `TB_FIX` | 16384 | **32768** | 459008 | **524544** |
| 槽表 `TB_SLOT` | 32768 | 32768 | 917760 | 1442048 |
| alloca `TB_ALLOC` | 8192 | 8192 | 1442048 | 1966336 |
| `TB_ARG` | — | — | 1573120 | 2097408 |
| phi `TB_PHI` | 512 | 512 | 1573504 | 2097792 |
| `TB_IDATA` | — | — | 1581696 | 2105984 |
| `TB_EXT` | 4096 | 4096 | 1587200 | 2111488 |
| `TB_OBJ` | 256 | 256 | 1588000 | 2112288 |
| `TB_FREL` | 4096 | 4096 | 1589000 | 2113288 |

因为各表**首尾相接**，抬一张就是"它之后的所有起址整体后移"：全局表 +65536
（= 32 × 2048），回填表 +458752（= 28 × 16384）。表尾最后一个偏移 2244360，
所以 `M_TAB`（表区）跟着从 2 MiB 抬到 **4 MiB**，`M_OBJ`（`= M_TAB + 表区`）与
`ARENA`（`= M_OBJ + OBJ_CAP`）依次后移 —— 与 `docs/192` §2 抬输入缓冲时同一条式子。

### 3.1 2026-10-10 又抬一次：标签表（两条线同日撞墙，最后落在 32768）

§4 那句"**下次撞墙大概率在标签表**"应验了，而且**只隔了一天** —— 更巧的是**两条线同一天
撞上同一堵墙**，各自抬了一次：

* **联网那条线**（`syscall7` / PE poll 那批，§3.2）把种子推到 16387，抬到 **32768**；
* **命令这条线**（`docs/223` 的 `register`：形态 B 的命令扫描 + 形态 A 的块）把它推到
  **16914**，抬到 20480。

两边抬的是同一格、同一天，合并后**取大的那个**：`TB_LBL_MAX = 32768`，
`TB_FIX` 及其后各表起址按 `24 × 16384 = 393216` 整体后移（§3.2 的式子）。

**这次合并的取舍**：本线那一版（20480 / +98304）作废 —— 它不是错的，是被同日更大的
一次盖住了。两边的**理由与写法完全一样**（都写了"抬之前先量、别照抄旧表"，
都指出 genesis 二进制要重打），所以这里只留一条记录，不再各写一份。

**有一条经验值得留下**：`TB_LBL` 在两次抬之前都只剩**个位数余量**（先是 9，再是
"给入口发一个 `"stackrealign"` 属性就多 3 个全局 + 9 个基本块"）。这不是"下一次改动就撞"，
是**已经在撞**——所以 §5 那条"抬容量之前先量一遍"要当成动自举编译器**之前的例行一步**，
而不是撞了之后才做的事。

**genesis 是随包发的那个链接器**：上限写在 `lomelf.lomt` 里，不重打那一份的话
`bootstrap.sh` 照样按**旧上限**报满 —— `loment_genesis_test::test_bootstrap_needs_no_clang`
正是这么红的（它不是读源码，是真跑一次 bootstrap）。修法是
`python tools/loment_genesis.py --emit`（要 clang/WSL）。

## 4. 判据：把余量变成看得见的预算

新加 `loment_genesis_test::test_seed_fits_lomelf_table_caps`，与 `IN_CAP` 那条**同一个
形状**（从 `lomelf.lomt` 里**读**上限，不另抄一份）：它按表模型数一遍种子，断言三张表都
装得下，并把余量打出来：

```
全局表 2215 / 4096, 余量 1881
标签表 13202 / 16384, 余量 3182
回填表 17009 / 32768, 余量 15759
```

三个数的数法（判据的 docstring 里也写着）：

* **全局表** = `^@x = ` 的行数。参考实现给**每个字符串字面量站点**发一个 `.str.<函数>.<序号>`
  全局、**不按内容去重**，所以"驱动链里多几十个字符串字面量"就等于"全局表多几十条"
  —— 这正是这一格撞墙的原因（第十九格自己就带了上百条 JSON 片段字面量）。
* **标签表** = 全局 + `declare` + `define` + 基本块名（`lbl_add` 的四类调用点）。
* **回填表** = 每次 `call` / `br` 一条，**加上"每个函数里引用到的全局"各一条**（`em_mov_abs`；
  槽表按函数去重，同一个全局在一个函数里引用多次只算一次）。

这个回填模型用**旧上限验过**，所以它可信：旧上限 16384 下，HEAD 那版种子算出来 13634
（过），2026-09-20 那版算出来 15686（当场顶破）—— 与实际行为一致。

**现在最紧的是标签表**：2026-09-22 再量（`potato.lomt` 的单态化那一节落地之后，
种子 2639135 B）是 **81%**（13202/16384），不是刚抬过的两张。下次撞墙大概率在它。
**—— 它第三次撞墙确实就是标签表**（§3.1，超 92 条）。抬到 24576 之后重量的余量是
**标签表 16476 / 24576（余 8100）· 全局表 2651 / 4096（余 1445）· 回填表 20948 / 32768
（余 11820）**，种子 3254657 B —— 三张表里**现在最紧的换成了全局表**（65%），
不是刚抬过的标签表。
（这三个数**跟着种子走**：单态化那一节落地时是 2226/13242/17072，清掉两处死代码后
种子小了、计数也跟着降 —— 抬容量之前先量一遍，别照抄旧表。）

### 4.1 落地：2026-10-10，预测的那次撞墙

上面那句"下次撞墙大概率在标签表"**准了**，而且比预想的近得多：并进 `origin/main` 之后
种子是 **16375 / 16384**（余量 **9**）。也就是说**任何**让自举编译器自己多出两位数基本块
的改动都会顶破它 —— 触发这次的是给程序入口发一个 `"stackrealign"` 属性
（`docs/212` §5.2）：`codegen.lomt` 的 `emit_fn` 多一个 `if`、多两个字符串字面量，
种子当场 **16387 / 16384**，`bootstrap.sh` 的 1/4 步（genesis 汇编种子）直接报
`标签表满了`。

第三次抬法同前（`TB_LBL_MAX` 16384 → **32768**，整条表区往后挪 `24 × 16384 = 393216`）：

| 表 | 旧起址 | 新起址 |
|---|---|---|
| 标签表 `TB_LBL` | 131328 | 131328（不动） |
| 回填表 `TB_FIX` | 524544 | **917760** |
| 槽表 `TB_SLOT` | 1442048 | 1835264 |
| alloca `TB_ALLOC` | 1966336 | 2359552 |
| `TB_ARG` | 2097408 | 2490624 |
| phi `TB_PHI` | 2097792 | 2491008 |
| `TB_IDATA` | 2105984 | 2499200 |
| `TB_EXT` | 2111488 | 2504704 |
| `TB_OBJ` | 2112288 | 2505504 |
| `TB_FREL` | 2113288 | 2506504 |

表尾 2244360 → **2637576**，仍在 4 MiB 表区里，所以这次 `M_TAB` / `M_OBJ` / `ARENA`
**都不用动**（与前两次不同）。抬完三个数是：

```
全局表 2639 / 4096, 余量 1457
标签表 16387 / 32768, 余量 16381
回填表 20843 / 32768, 余量 11925
```

**现在最紧的换成了全局表**（64%）—— 它跟着"字符串字面量的站点数"走，所以往
自举编译器里加字面量之前先量一遍。

**同一天、同一堵墙、两笔独立的改动**（2026-10-10）：`docs/222` §4 那一维
（`choose hosted`）落地时也在 `checker` / `potato` / `codegen` 上加了百来行，独立撞到
**16476 / 16384**。两条分支各自抬了一次，合并时取了**这次（32768）** ——
它更大、更晚、记账更全。这件事本身就是 §4.1 开头那句话的证据：
**余量只剩 9 的时候，两笔互不相干的改动会在同一天先后撞上来**，而它们各自都会以为
"是我这一笔的错"。抬表**只在 genesis 重建之后才算数**（`loment_genesis.py --emit`）——
它是链条的起点，带着旧上限的那份二进制照样会把种子挡在门外，症状与"没改"一模一样。

## 5. 同一天里的**第三处**：`lomrel` 的归一化副本（2 MiB）

把上面两处修完、`loment_seed_test` 4/4 之后，`loment_rel_test` 红了，而且红得**很像"清单过期"**：

```
[DIFF] loment/build/selfhost_driver.ll
[DIFF] loment/build/genesis/lomelf-linux-x64.elf
...
loment_release: 260/486 一致
```

而两边的**写**（`--emit`）是逐字节相同的，`--checksums` 也一致 —— 只有 `--check`（读清单、
逐件重算哈希）说 226 条对不上。**根因**：`lomrel.lomt` 的 `M_NORM` 是固定的 2 MiB
（`NORM_CAP = 2097152`，通用换行归一化的副本），而清单里**有比它大的工件** —— 自举种子。
越界正好写进紧挨着的 `M_CUR`（**已装载的清单**），于是：

* 报出来的不是"这个文件的字节不对"，而是**它之后每一条都对不上**（清单被改坏了）；
* 分界点精确落在种子那一条（清单第 260 条 = 2432497 B 的种子）；
* 而"两边的写一样"是因为**写**走的是目录遍历那条路，不经过归一化副本。

修法：`NORM_CAP` 抬到 **4 MiB**（= `IN_CAP`：**读得进来的就得归一化得了**），`M_CUR` 与
`ARENA` 依次后移；`sha_of_file` 里补一条守卫（超了就报错退出，别静默写坏清单）。
判据是 `loment_rel_test::test_seed_fits_lomrel_normalization_buffer` —— 与 §4 那两条同一个
形状（从 `lomrel.lomt` 里**读**上限、报余量）：

```
最大工件 loment/build/selfhost_driver.ll 2432511 B / 归一化上限 4194304 B, 余量 1761793
```

**三处的共同形状**（这张表值得记）：都是"**一块定长的缓冲 + 一个更大的工件**"，
都是**单调写**、越界都**不报错**，而症状都离现场很远：

| 处 | 缓冲 | 越界的症状 |
|---|---|---|
| `lomelf` 输入（`docs/192`） | `IN_CAP` | 截断的 `.ll` → 汇编出一个**跑起来段错误**的可执行文件 |
| `lomelf` 三张表（本文 §3） | `TB_G` / `TB_FIX` | 写进邻居表 → `未定义的标签: `（**空名字**） |
| `lomrel` 归一化（本节） | `NORM_CAP` | 写进已装载的清单 → **从某一条起后面全对不上** |

## 6. 没做的（写明，不装作没有）

* 守卫只**报错退出**，不"自动扩容" —— 与 `IN_CAP` 那条同一个取舍：容量是编译期布局，
  运行期只能说"装不下"。
* 三张**每函数**的表（槽 / alloca / phi）也补了守卫，但它们离上限很远，没有单独的预算判据
  （数它们要按函数建模，收益不抵成本）。
* `TB_EXT` / `TB_OBJ` / `TB_FREL` 的注释里那三个容量**互相重叠**（`TB_EXT` 声明的 32768
  已经越过了 `TB_OBJ` 的起址）—— 这是本篇之前就有的口径不一致，实际用的容量更小；
  这一轮只做**整体平移**，没有顺手改它们的数（改了就得先弄清外部目标文件那条路真实用多少）。

> **2026-10-16 更正一处用法**（`docs/252`）：上面那条"守卫只报错退出"是关于**真越界**的，
> 它成立。但"**看到 `回填表满了` 就说明是容量问题**"**不成立** —— 那条消息后来被当成了
> 一次**死循环**的出口：镜像的 `do_switch` 在多行 case 表上把 case 指针赋回了 **0**，
> 每绕一圈发一条回填，32768 圈后报满。**空 case 表也照样复现**（一条回填都不该要），
> 所以那次与 `TB_FIX_MAX` 无关，抬常数救不了。`TB_FIX_MAX` 保持 32768 未动。

## 7. 第三次：标签表 16384 → 32768（2026-10-10）

§4 的末尾已经记了这次抬高与**三笔同一天的改动**（`choose hosted` / `stackrealign` /
本文这一笔）。这一节补的是**这一笔自己的数**（`docs/224`，自举侧 Potato **v12** 的
`surfaces`），以及一条只有从这一侧才看得出来的事实：

> 抬之前，种子用掉 **16375 / 16384** —— **余量 9 条**。加 `surfaces` 多 193 条，
> 当场顶破。

* 上限：`TB_LBL_MAX` 16384 → **32768**（其余各表不变）；
* 位移：下游各表偏移整条 **+393216**（= 24 × 16384）。表尾 2244360 → **2637576**，
  仍在 4 MiB 表区内（`M_TAB` … `M_OBJ` 之间还剩 1556728 B）；
* 实测（`loment_genesis_test::test_seed_fits_lomelf_table_caps`）：
  标签表 **16568 / 32768**，余量 16200；全局表 2654 / 4096；回填表 21036 / 32768；
* **genesis 要一起重建**（`python tools/loment_genesis.py --emit`）：`bootstrap.sh` 的第一步
  是**提交进仓库的那个 genesis 二进制**在汇编种子 —— 它里面冻着旧的上限，
  只改 `.lomt` 源不改 genesis，症状是 `== 1/4 种子 -> stage1` 那一步报"标签表满了"。

**这一笔暴露的纪律问题**（前两次没有这一面）：预算判据报的是"**没超**"，而没超不等于
**有余量** —— 9 条的余量在这条判据下一路是绿的，任何一笔改动撞上来才算"红"。
`TB_LBL_MAX` 与 `TB_FIX_MAX` 现在都给了 32768，但它们**各自**的余量在下一轮里会被同样的
方式吃掉。真正的解法是把"容量"从**四张表各自的常数**变成一条**共用的预算**
（一个数说明还能长多少），但那是表区布局的重做，不在这一格里。


### 8.1 同一天还有**第四撞**：`runtime` 那一笔也撞了同一张表

`docs/227`（`runtime` 维兑现）在同一天**独立**撞上同一张表：它让种子涨到
**16421 / 16384**（超 37），当时的处置是抬到 20480 —— 合并时被本节这一笔
（**32768**）取代，**取大的那个**。这一笔自己的**测量**留在上面那个代码块里：
余量是个位数时，"下一笔改动撞上它"不是巧合，是算术。

## 9. 第五处：文本段那 2 MiB 窗口（2026-10-16，LMS 那一笔撞上来）

上面八处撞的都是**表**（全局表 / 标签表 / 回填表 / 输入缓冲 / 归一化副本），越界的形态是
"单调 bump 写进下一张表"，症状离现场很远。这一处**不是表**，是**段与段之间的间隔**：
`TEXT_VADDR = 0x400000`、`DATA_VADDR = 0x600000`，于是文本段只有 **2 MiB**
（`2097152`）可用 —— 而**越界同样不报错**。多出来的代码盖在数据段上，
症状是**产物一启动就段错误、0 字节输出**：看起来像编译器坏了，其实是链接器把全局变量
放在了代码**底下**。

**测量**（`tools/lomelf.py` 的 `compile_ll`，编译 `loment/selfhost/driver.lomt`）：

| 树 | 文本段 | 余量（对 2 MiB 窗口） |
|---|---|---|
| `main@f8d7769` | 2 082 438 | **+14 714** |
| `main@6cc53b51` | 2 084 579 | **+12 573** |
| LMS 那一笔（在 f8d7769 上） | 2 090 565 | +6 587 |
| 合并后 | 2 108 422 | **−11 270** ← 撞破 |

也就是说 **`main` 自己已占 99.4%**：任何一笔中等改动（LMS 那笔给两处分配器加了
`lms` 参数，文本段涨约 22 KB）都会顶破它。"是谁撞的"在这个数面前没有意义 ——
余量只有 12 KB 时，下一笔改动撞上它是**算术，不是巧合**。

**判据长什么样**：`loment_elf_test` 的 `test_lomelf_rebuilds_the_compiler_without_clang`
与 `test_lomelf_selfhost_rebuilds_the_compiler` 两条报**退出 139**。它们本来就是
"链接出来的编译器能不能用"那两条 —— 所以这不是新判据抓到的，是**老判据用段错误的语言
说出来的**。

**处置**：数据段改钉在 **`TEXT_VADDR + OUT_CAP`**（`0x800000`）—— 那个间隔**就是代码
缓冲本身的容量**，不是拍出来的数；文本段的容量因此变成 `OUT_CAP`（4 MiB），比原来宽一倍。
两处实现同一个数（`loment/tools/lomelf.lomt` 的 `OUT_CAP` 与 `tools/lomelf.py` 的
`TEXT_CAP` / `ELF_DATA_VADDR`），产物仍旧逐字节相同（`loment_elf_test` 的镜像那几格钉着）。

**同时把地板标出来**：原先越过窗口是**静默**的，现在 `compile_ll` 末尾与自举侧驱动里
各有一条守卫 —— `len(text) > TEXT_CAP` / `tlen > OUT_CAP` 就**点名退出**，报文里写清
抬哪两个常量。与 `TB_LBL_MAX` / `TB_FIX_MAX` / `IN_CAP` 那几条同一个纪律：
**满了就说出来，不往下写**。

**没做的**（与 §6 同一条口径）：真正的解法是让数据段**紧接文本段**（`align_up(TEXT_VADDR
+ tlen, 4096)`），没有魔数、也就没有"下次再涨就撞"。参考侧（`tools/lomelf.py`）那一边
**改起来是一处** —— 标签的值只在 `finalize()` 里被读，所以基址晚一步定是安全的；
自举侧不行：那边的标签表**只增不写**（`lbl_add` 追加、`lbl_find` 取第一条匹配），
"先登记占位、事后改地址"这条路不存在，而**外部对象的数据符号地址是在对象循环里就落表的**
（那时文本段还没长完，归档成员更是要跑完定点才挑得出来）。要落地就得重排自举侧的链接
次序（例如给 `link_object_mem` 加一趟"只登记数据符号"）。这一轮取的是**同一个数 +
守卫**：窗口宽一倍，越界会说出来。
