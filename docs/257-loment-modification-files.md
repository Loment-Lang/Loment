# 257 · 修改件：开发补丁不再改 `.lomt`，改 `.lomf`

> 状态: **格式 v1 已落地**（2026-10-15；2026-10-16 随 `fix/rt-0146-four` 一起进树）。
> 这一层只做一件事：**把"同一段文本有多个副本"的改动写成一份可核对、可机械套用的记录**。
> 它**不是**给语言加语法，编译器不认这个后缀。

## 0. 一句话

> **`.lomt` 是源，`.lomf` 是"这一笔改了什么"。** 源是事实，补丁是记录 —— 两者由一条判据钉在一起。

## 1. 为什么要有它

Loment 自己那块代码有一个反复出现的形状：**同一段文本，四个副本，而且嵌在字符串常量里。**

改 `__loment_alloc` 那一行，要动四处：

| 文件 | 为什么有这一份 |
|---|---|
| `tools/lomentc.py` 的 `_IR_HEAP` | 参考实现发普通档的运行时 |
| `tools/lomentc.py` 的 `_IR_HEAP_HOSTED` | 同一段，hosted 档（地址要经间接基） |
| `loment/selfhost/codegen.lomt` ×2 | 自举镜像的两份（**必须与参考逐字节同**，`docs/158` §5） |

由此有三件事同时成立，而 `git diff` 一件都不解决：

1. **行号漂得比代码快。** 这段文本住在一个 46 KB 的字符串常量里，上面任何一处改动都会推它；
   而按行号打的补丁（unified diff）对"嵌在字符串里的 IR"几乎每次都要重来。
2. **改错位置不会报错。** 改的是运行时 IR：错一处，编译器照旧出产物、判据照旧绿，
   只会在很久以后表现为一个**莫名的回收行为**。
3. **"这一笔改了什么"没有单独的落点。** 它散在四个文件的 diff 里，而 review 要能一眼看出
   "就是这一格"。

`.lomf` 是给这三件事的回答：**按逐字节片段定位、按次数核对、套用与否分得清。**

## 2. 形状（v1）

```
lomf 1
mod   0001-alloc-slack
about 为什么改、改的是什么（可多行，`about` 后留空就是分段）

edit <仓库相对路径> expect <n>
old <<<
<逐字节的旧文本>
>>>
new <<<
<逐字节的新文本>
>>>
```

一条 `edit` = **一处精确替换** + **它期望出现几次**。一个文件要改两处就写两条 `edit`。

`tools/lomf.py` 三个入口：

```
python tools/lomf.py --list  <x.lomf>    # 这一笔动了哪些文件、每处现在命中几次
python tools/lomf.py --check <x.lomf>    # 能不能套（不改盘）；已套用也报通过
python tools/lomf.py --apply <x.lomf>    # 套用（就地改，幂等）
```

每一处替换有三种状态，套用器**只认这三种**：

| 状态 | 判据 | `--apply` 的动作 |
|---|---|---|
| 待套用 | `old` 正好 `expect` 次 | 替换，写盘 |
| 已套用 | `old` 0 次 **且** `new` 正好 `expect` 次 | 跳过（幂等） |
| 对不上 | 其它一切 | **报错，一处也不动** |

## 3. 两条硬规矩（都不是洁癖，各有一条实测的来路）

**① 次数必须写，对不上就一处不改。** "对不上"是必然会发生的事（别人改过同一段、
或者这一笔只落了一半），那一刻只有两个选择：猜，或者停 —— 而猜的后果是**静默改错文件**
（见 §1 第 2 条）。所以套用器**先全量校验、再落盘**：任何一处对不上，整个文件一个字节不动。

**② 互为子串的替换直接拒收。** 这条是写第一版补丁时**踩出来的**：`#368` 要往
`relink:` 后面**插一行**，于是 `old`（`relink:` 那两行）成了 `new`（那两行 + 新行）的
**子串** —— 而"已套用"的判据是「`old` 0 次、`new` 正好 `expect` 次」，`old` 还嵌在 `new`
里 ⇒ 套第二遍会**再插一行**，套用器无从分辨。实测确实插重了。

所以规矩是：**两块互不为子串**（解析期就拒，报文里写明怎么改 —— 把邻近一行的上下文一起
写进去）。这一条同时买到了幂等：`--apply` 跑多少次结果都一样。

## 4. 谁套用、树里存什么

**编译器不认 `.lomf`。** 套用由 `tools/lomf.py` 显式做，**改好的源进树** —— 于是工具链、
LSP、编辑器、自举镜像全都不必知道这个后缀存在。补丁文件是**留档**：它记着这一笔"改的是
哪一段、期望出现几次"。

两者由一条判据钉住（`loment_tools_test::test_lomf_patches_in_the_tree_are_applied`）：
**树里的每一份 `.lomf` 都必须处于"已套用"**。允许"补丁放着、源另说"，它就会立刻腐烂成
一份没人对得上的说明书 —— 那比没有更坏。

**边界（今天还没做的事）**：这条判据只管"在树里的补丁必须已套用"，**不**强制"每笔改动都要
配一份补丁"。所以 §0 那句"开发补丁不再改 `.lomt` 而改 `.lomf`"目前是**约定**，不是门禁 ——
把它变成门禁要先想清楚它会不会把别人的 PR 一律打红。`tools/lomf.py` 与 `loment/patches/*.lomf`
都在 `loment_release.GLOBS` 里（发布清单收它们），所以它们不会因为"不在清单里"而消失。

## 5. 它**不是**什么

- **不是 diff。** 不按行号、不做上下文匹配、不合成两个来源 —— 只做"逐字节片段 × 期望次数"。
- **不能创建文件，也不能删除文件。** v1 只有 `edit`；将来要 `add` / `rm` 是另一条指令。
- **不是语义补丁。** 它不认识 `__loment_alloc` 这个**名字**，只认识那段文本。语义级
  （"改这个函数的这一步"）更抗漂移，但要给核心加一套补丁语义、两个实现都要有 ——
  那是**下一档**，v1 不假装做到了。
- **不参与任何一个档的编译。** 补丁套完就把自己摘出去了。

## 6. 树里的第一批：三份

`loment/patches/` 下现在有三份，都是 `#345` 那一轮（`docs/258`）落的 ——
它们正好把这份格式的三种形状各占一种：

| 补丁 | 改什么 | 形状 |
|---|---|---|
| `0001-runtime-refusal-is-its-own-code.lomf` | `E022` → `E030`（issue #321） | **同一件事、两个实现各一份**：检查器发的码与驱动器分派的码必须同步改，漏一处就是"结构化诊断写 E022、人看的那行写那句话" |
| `0002-literal-index-is-a-language-rule.lomf` | 字面量越界从 LMS 第 1 级升成语言规则（issue #18） | **一条判据、两个实现各一段 `if`**，而且必须逐字同判（只对定长数组、只对裸字面量） |
| `0003-capacities-speak.lomf` | `driver.lomt` 四处静默截断补上失败路径（issue #345） | **一个文件、五处**：`SLOT` / `DIR_CAP` / `SUBP_CAP` / `EXT_CAP` + 一句点全名的报错 |

历史：格式 v1 的第一个用户是 `#368` 那份 `0001-alloc-slack.lomf`（四处同一段文本，
`expect 2` —— **它替"四个副本"这件事本身站岗**：谁又抄出第五份，`--list` 会立刻显示
"旧=3"，套用器拒绝动手）。那一笔落在它自己的分支上，与本文一起进树的是上面这三份。

**`expect` 不是修辞**：它记的是"这段文本该出现几次"。`0001` 里那份 4 处、`0003` 里
5 处各 `expect 1`，都是逐处数过的。
