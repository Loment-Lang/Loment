## 0. 先记一条：我之前理解错了，错在哪

我（助手）前面一直把 `.lomt` 里的 Python 当成**外源代码**，于是整条思路都往
"收编 / 借用"上走：要么翻译它（当它是外国货，要把语义搬过来），要么拉起它的解释器。

**用户 2026-09-18 的原话把这条框正了：**

> Loment 可以被多种语法编写，其最终行为却无异。就比如说 Python 写了个 `print` 与 Java 的
> `out.println` 输出一样，因为最终都走向 Loment 源语法（Rust 严格子集）。
> 只是说，当别人用 Loment，他们**不再需要学习语言怎么写或者学习 Rust**，
> 而是直接按照熟悉的语法写。

所以正确的框是：

| | 外源代码（我原先按这个做的） | **表层语法**（用户的模型） |
|---|---|---|
| 那段代码属于谁 | 别人 | **本来就是 Loment** |
| 语义听谁的 | 那个语言的 | **Loment 的** |
| 要做的事 | 收编 / 借用 | **前端**（读法 → Loment 构造） |
| `print` 与 `out.println` | 两门语言的两个函数 | **同一个 Loment 操作，两种拼法** |

**"最终行为无异"这句话只有在语义统一时才成立。** 所以表层语法**只让拼法与形状，
不让语义**。这一条是本文档一切推论的前提。

### 0.1 它当场推翻了我已经写下的三处

诚实记下来，因为它们正是"理解错了会有多贵"的样例：

1. **`pytrans` 里那对辅助函数**（`__py_mod` / `__py_floordiv`）：它们是拿来**保住 CPython
   的向下取整**的。按新模型，`//` 只是"整除"的 Python 拼法，**语义该是 Loment 的**
   （向零截断，实测 `-7 % 2 == -1`）。那对函数让"Python 写法"表现得像 Python——
   **方向反了**。已拆掉，`loment/pytrans/intdiv.py` 现在钉的是**反过来的那一边**
   （本语言 62、CPython 56，两个数**必须不同**）。
2. **`from_python` 给对象填 `language: "python"`**：按新模型它是 **Loment**。已改。
3. **"Loment 的 `let` 是块级"—— 这条是错的**（我推的，没探）。见 §0.1.1。

### 0.1.1 一处**推出来、探过之后不成立**的"语义差"（教训）

`docs/187` 初稿把"**Python 是函数级作用域、Loment 的 `let` 是块级**"列成三处语义差
之一，并为此把声明**上提到函数头**；本文档 §0.1 初稿接着把它记成"做反了"的一处。
**两处都错。**

2026-09-18 探了一下（`loment/pytrans/blockscope.py` 的语料就是它）：

    fn f(c: bool) -> i32 { if c { let x: i32 = 10; } else { x = 20; } return x; }

* `lomentc.check` **不报错** —— 块里 `let` 的名，块外看得见；
* 编出来跑 `f(false)` 给 **20** —— 只有一条分支声明、另一条只赋值，值也对。

⇒ **Loment 的 `let` 在这两个形状里就是能漏到块外的**，与 Python 在这一处**本来就一致**。

所以那个"上提"**不是方向反了，是多余**。现在就地 `let`，两边结果本来就一样；
`blockscope.py` 从"拒收集"改成了**同意集**（拿 CPython 当对照）。

> **教训**：一处"语义差"要**探出来**，不能**推出来**。
> 推出来的那一处让我写了一版多余的实现，还往文档里记了一条不存在的事实 ——
> 而它**两边都编得过**，没有任何判据会红。

**这条同样是 §7.1 那条"每门先探再写"的直接理由。**

### 0.2 它与「严格 Rust 子集」那条声称是什么关系（用户 2026-09-18 的表态）

用户当天还说了：**「Loment 是时候打破 Rust 严格子集这个莫名其妙的规定了」**。
这条要接好，因为两者看着矛盾（多种语法 vs. 长得像 Rust），其实不矛盾：

| | |
|---|---|
| **那条规定的理由** | 写在 `tools/lomentc.py:5` / `tools/lomc.py:5`。不是洁癖，是**「不发明语法 → 规避 LLM 零语料」**：语法长得像 Rust，人和 LLM 才有先验 |
| **它现在的问题** | `capability` / `guard` / `comefor` / `byuse` / `foruse` / `command` / `let c { }` 早就不是 Rust 了，`module` 也不是 Rust 的 `mod` —— **这条声称描述不了这个语言** |
| **该丢的** | **语法包含**（"每个 Loment 程序都是合法 Rust"）。它早被跨过很多次了 |
| **该留的** | **共同子集上的语义一致** —— 那才是"规避 LLM 零语料"实际买到的东西，也是 VS Code 着色、agent 迁移说明所依赖的 |

**⇒ `choose write grammar` 恰恰是"该留的那半"的推广。** 原来只有一段共同子集
（Loment 与 Rust 重叠处）；现在有**三段以上**（与 Python 写法、Java 写法、C 写法各自
重叠处）。要求也因此从"重叠处同义"变成一条更一般的：

> **表层语法只决定拼法与形状，不决定语义。**
> `print(x)`（Python 写法）与 `out.println(x)`（Java 写法）是**同一个 Loment 操作** ——
> 这正是用户那句"**最终行为无异**"。

§0.1 里那两处"做反了"的地方，就是违反了这条：它们让"Python 写法"表现得更像 Python
而不像 Loment。

## 1. 声明什么

```
choose write grammar python
```

- 位置：**文件头**，在 `module` 之前 —— 它决定**后面怎么读**，所以必须先读到。
- `lock`：**出厂锁**。取值表由官方给出，**不可删**，将来可以用**哈希**把它钉死。
  用户不能扩展、不能覆盖、不能解锁。
- **拼法可以有别名**（`grammar py` / `grammar python` 都收），但**规范名进对象** ——
  源侧宽松、对象侧只许一个拼法，否则同一份源出两串字节，判据当场红。

> ⚠️ **已上报的缺口（`docs/198` §2）：这一节列了"写错"的四种样子，漏了第三种最容易犯的
> —— 关键词本身写错。** 实测：`choose language python` / `choose grammar python` /
> `grammar python` / `choose write grammars python` **四种都不报错**，`read_grammar_decl`
> 一律返回 `declared=False`，于是文件被当 Loment 读，用户看到的是
> `未知顶层关键字 'def'` 之类**指向别处**的错。而本节下面那条"兜底从'猜'变**拒绝**"
> 正是为这种情况写的 —— 现在它既不猜也不拒，是**换了一个猜法**。

### 1.1 `lock` 是**出厂**锁，不是 `docs/182` §3 那个"装进本机"

这两件事共用一个词，**必须分开**，否则实现的人一定会混：

| | `docs/182` §3 的 `lock` | 本文档的出厂锁 |
|---|---|---|
| 装到哪 | **用户目录** | 无（编译进工具链） |
| 谁改得动 | 用户（配 `chooseunlock.lomlock`） | **没人** |
| 状态 | 本机 | **官方值** |
| 阶段 | C3，**未实现** | 现在就能做 |

**⇒ 直接后果：grammar 落地不依赖 C3。** `docs/182` §4 那张落点表记着一笔代价——
"**锁的读写**在当前架构里没有落点，本仓从无『本机持久状态』"——**grammar 不付这笔钱**，
因为出厂锁没有"本机状态"这回事。

`docs/182` §3.1 那条冲突（锁与本机绑定、破坏"同一份源 → 同一串字节"）**同样不适用**：
grammar 的取值表在每台机器上都是同一份。

### 1.2 拼法可以有别名，规范名只许一个

| 源里写 | 对象里存 |
|---|---|
| `grammar loment` | `"loment"` |
| `grammar py` / `grammar python` | `"python"` |
| `grammar c` | `"c"` |
| `grammar java` | `"java"` |

别名表**只有一处**（与 `docs/179` 那条"判语法的规则只有一处"同一条纪律）——
放 `potato_from` 的语言表旁边，不要在两个实现里各写一份。

## 2. 形状：**源侧可选，对象侧必填**

理由在 `docs/140` §9 那句分工——**Loment 管"怎么写"，Potato 管"怎么看"**。
两侧任务不同，所以形状**故意不一样**。

**源侧：可选。没写就是 Loment。**

- 99% 的文件是 Loment，每份写一遍是噪声；
- 而且**没有歧义**：缺 = Loment。读不过就报"这不是 Loment——**你写的是别的
  语法就声明一下**"。
- 这一下把 `potato_from.detect_lang` 的**嗅探**（"有 `#include` 之类预处理指令"）
  换成**声明**；兜底从"猜"变"拒绝"。这正是本仓那条"不静默"。

**对象侧：必填。一份对象永远说得出自己是用什么读法读出来的。**

- 这一条不能省。今天一份 Python 写法的对象里写着 `language: "python"`，
  读者以为它**属于** Python——**就是这个字段的缺席让"猜"变成了下游的责任**。
- 参照 `abi` 的先例（`docs/179` §3.1）：**可选**的前提是"不认识它的消费者**忽略它是对的**"。
  这里**不成立**——忽略它的人会把 Python 写法当成 Loment 读，那是**误判**。
- 所以按本仓规矩**必填即升版本**：**Potato v6**，新顶层字段与 `mode` **同级同形**
  （一个字符串，取值是规范语法名）。

```json
{
  "potato": "v6",
  "unit": "policy",
  "language": "loment",     // ← 它**是** Loment
  "grammar": "python",      // ← 用哪种写法写的。缺省即 "loment"，但字段必填
  "mode": "std",
  ...
}
```

## 3. `language` 与 `abi` 的含义一并正过来

这两个字段今天被混成一个意思，那是"外源代码"那套框的残留：

| 字段 | 旧读法（外源代码） | **新读法（表层语法）** |
|---|---|---|
| `language` | 这份东西**属于**那个语言 | 这份对象**是什么** —— 用别的写法写的，**它仍然是 `"loment"`** |
| `abi` | （被 `language` 带着走） | **只在真的是外国的时候才有意义**（`let` / `foruse` 拉进来的） |

**不这么分的话，今天就有实际后果**：`lomt_from` 那道 ABI 闸门会把"Python 写着玩的
Loment"当成外国函数**挡掉**——而它本来就该被翻成 `pub fn`。`loment_diag` 里那条
"接口一条都发不出来、照建议敲会得到空 module"的提示，根因也在这里。

### 3.1 仓里自己留了一句决定性的话

`potato_from._blank` 的注释（写于 2026-09-17，那时还是"外源代码"那套框）：

> 停在 **v1** 而不是跟着编译器升到 v2：v2 的 `mode` 是"这个 Loment 程序用哪个运行模式"，
> 而这里的对象描述的是**外源模块**的结构 —— 它**不是一个 Loment 程序**，给它填 `std`
> 就是**替它声称**一件源里没有的事。……"外源结构对象不声称程序模式"这条边界因此留在数据里。

**这条理由在新模型下正好反过来**：Python 写法的单元**就是**一个 Loment 程序，
所以它**该**升到 v2+、**该**有 `mode`、`language` **该**是 `"loment"`。

旧设计自己写下了它为什么停在那儿——而那个"为什么"现在不成立了。这是新模型
站得住的旁证，也说明**停 v1 那条边界是为旧框服务的，不是为可复现性服务的**。

1. **裸 `.py` / `.c` 文件（没有 Loment 头）** → 没地方写声明，**还是靠后缀**。
   声明治的是"`.lomt` 里装别的语法"这一档——也正是今天**最容易出问题**的那一档。
2. **子集外**（`with` / `lambda` / 动态类型）→ 还是**报错**，不是声明能救的。
3. **真 Python**（要 numpy、要 PyPI 上那个只在生态里的库）→ 那是 **`let py { }`**，

## 7.1 六门表层语法（用户 2026-09-18 点名，**计划**）

用户原话：**「plan 中要完成 Python Java Go C C++ C# 五种语言的直接翻译哦」**
（列了**六个**名字、说的是"五种"—— 按**六个**做，宁多勿少）。

到今天为止：**C / Python / Java / C# 四门通了**（Python 那门方向反了，见 §0.1；
Java 与 C# 的落地见 §7.1.1）。**剩下两门：C++（对照组 WSL `g++`）与 Go（单独一份解析器）。**

### 架构决定：一份解析器 + 方言表

六份独立的翻译器 = 六倍重复，而同一件事写六遍**必然漂**（本仓那条纪律）。
所以「花括号 + 分号」那一族（**C / C++ / Java / C#**）共用一份分词器与递归下降，
差异全进**方言表**：

| 方言表里放什么 | 为什么它真的不同 |
|---|---|
| 类型拼法 | `int`→`i32`（都一样），但 Java 有 `boolean`、C++ 有 `bool`+引用、C# 有 `decimal` |
| 声明起始词 | C 的 `static`/`const` 与 Java 的 `public`/`final` 不同 |
| 函数头形状 | `<类型> <名>(…)` vs Java 的 `class` 外壳 + `static` |
| 条件要不要括号 | 四门都要 —— **Go 不要** |
| `bool ↔ int` 要不要补转换 | **C / C++ 要**（`if (x)` 收 int、`&&` 出 int）；**Java / C# 不要**（`&&` 出 `boolean`） |
| 复合赋值怎么展开 | 四门都有 `+=`，Loment 没有 |

**Go 单独一份**：类型在名字**后面**（`func f(a int) int`）、条件**不带括号**、**没有 `while`**
（只有 `for`）、`int` 的宽度随平台（要用 `int32`/`int64` 明确写）。

### 回归线

抽共享核时 **C 那条路的行为必须一字不变** —— `loment_ctrans_test` 4/4 是验收条件。
一个方言表抽错的典型症状是"另一门悄悄变了"，而那种错**两边都编得过**。

### ⚠️ 六门的翻译器**也要有 Loment 孪生**（`docs/189` §4.1）

用户 2026-09-18 另一条：**0.1.4 正式版之前移除全部非 Loment 代码**。那六门的翻译器
（`tools/ctrans.py` / `pytrans.py` / …）是 **Python** —— 按那条指令，**它们也要有
Loment 实现**，否则到 0.1.4 之前又得拆一遍。

**⇒ 从第一门起就按 `docs/159` §4b 那个模板做**：翻译器写两份、判据比**输出的 Loment

因为**判据的形状一模一样**。

**但要如实说**：`lomfmt` / `lomdoc` / `lompkg` / `lomc` 那几块能便宜地镜像，是因为它们
**只吃词法层或声明层**。翻译器要**建树**（递归下降 + 类型 + 发射）——
在自举侧是个**大得多**的活，**别按前几块的经验估**。

### 每门还各有一张"语义差"清单（先探再写，别照抄）

照 `docs/186` §5 / `docs/187` §2 的做法，**每门先探清楚它与 Loment 在哪些地方
真的不同**，再写翻译器。已经知道的：

* **C / C++**：`int` 与条件混用（`if (x)`）、`&&` 出 int → **要补转换**。
* **Java / C# / Go**：`&&` 出 `boolean`、条件只收 `boolean` → **不用补**。
  但 Go 的 `int` 有平台宽度、`/` 与 `%` 向零截断（与 Loment 同）；
  Java 的 `>>>` 是逻辑右移（Loment 的 `>>` 是算术的，实测 `-8 >> 1 == -4`）。
* **Python**：真差别**只有两处**（§0.1.1 那处探过之后**不成立**）——
  `//` `%` 向下取整（按本语言的来，不迁就）、`and`/`or` 返回操作数与 `bool` 是 `int`
  的子类（**表达不出来，拒**）。所以这一门没有"语义差清单"，只有**一张判据**：
  **能表达的就转（`if x` -> `x != 0`），表达不出来的就报错**（`docs/187`）。

### Java 与 C# 的共同点比不同点多 —— 而**不同点只有一格**

两门的方言表几乎是同一张：`&&` 出 `bool`、条件只收 `bool`、`/` 与 `%` 向零截断、
`>>` 是算术的、`int` 恒 32 位 ⇒ **两个方向的强制转换都不用补** ——
`docs/186` §5 那条判据（"能表达的就转，表达不出来的就报错"）在这里给出与 C **相反**的结论，
因为 C# 的 `int x = (a < b);` 在 C# 里**本来就编不过**，遇到它报错才对。

**唯一**没落在同一格上的是 `byte`：

| | Java | C# |
|---|---|---|
| `byte` 的取值 | -128..127（**有符号**） | **0..255（无符号）** |
| 映成 | `i8` | **`u8`** |

搞反**不会报错、会静默算错**（C# 的 `byte b = 200;` 映成 `i8` 就成了 -56，两边都编得过），
所以它单独一条判据：`loment_cstrans_test::test_csharp_byte_is_unsigned_unlike_java`，
判在 `potato_from` 那一层。

### C# 比 Java 多两层壳：`using` 与 `namespace`

`tools/trans_core.py` 的 `strip_shells` 每项是 `(名字, 正则, 透明?, 有体?)` 四格：
**命名空间是"透明"壳**（里面还会有壳，抹完继续进去找），**`class` 是不透明的**
（里面就是成员；嵌套类是另一回事，留给方言表拒）。C# 10 的**文件级** `namespace Foo;`
落在"没有体"那一档。

**搬进共享核时顺手补了 `jtrans` 原来的一处洞**：它只把**注释**抹成空白，于是
`String s = "class X {";` 会被当成一个 `class` 头、外壳从字符串**里面**开始切，
切出一份错得看不出来的源。现在字符串字面量也一起抹。

同理，C# 的**内容识别**（`detect_lang`）只认两条**专有**的信号：
`using <大写开头>;` 与 `static … Main(string[] …)`。**`namespace` 故意不当判据** ——
C++ 也有 `namespace X {`，拿它认会把一份 C++ 源码**按 C# 去翻**（静默翻错语言，
比认不出坏得多）。代价：没写 `using` 也没有入口的 C# 文件得用 `--lang csharp` 指明。

### 一条**已知边界**：翻译器不做整数宽度跟踪

共享发射器只分 `int` / `bool` / `void` 三档（`Emitter.ty_of`），**看不出 `u8` 与 `i32`
的区别**。于是

```csharp
int f(byte b) { return b; }        // C# 里完全正常（隐式提升 byte -> int）
```

翻出来是 `pub fn f(b: u8) -> i32 { return b; }`，而它在 `lomentc.check` 上**报错**
（实测：`return 类型 u8，函数 bucket 声明 i32`）。

**那是响亮地失败，不是静默算错** —— 前者是本项目的红线，"少算一步却照样编过"才是。
宽度跟踪（C# 的小整数算术本来就会提升到 `int`）留到下一版；这条边界写进了
`tools/cstrans.py` 的文件头，也写进了六语言的语言卡（`loment_diag.LANG_CARDS["csharp"]`）。

> **2026-10-09 更正（`#123` / `#125` / `#133`）**：C / C++ 那两门**已经**跟宽度了 ——
> `Dialect.usual_arith` 打开时按 C 的**寻常算术转换**插 `as`（`docs/186` §5.1），
> 因为不插的那一半是**静默**的：`int a = -1; unsigned b = 0; a > b` 在 C 里为真、
> 在这边为假，而两边都退 0。**这条边界今天只对 Java / C# / Go 成立**（它们的转换
> 规则各不相同，按 C 的插会写出那几门本不接受程序 —— 所以那边照旧，响亮的失败）。
> 本章后面几处"不做整数宽度跟踪"的话，都按这一条读。

### 一条**比数字更硬**的判据：同一个程序、两种拼法、翻出**同一份** Loment

`loment/cstrans/Sample.cs` 与 `loment/jtrans/Sample.java` 是**同一个程序**的两种拼法
（`namespace` 多一层壳、`const` 换掉 `static final`，语义一格没动）。所以除了
"两边各跑出 99"之外，还有一条：

> 两份源码翻出来的 Loment **逐行完全相同**
> —— `loment_cstrans_test::test_two_grammars_one_program_translate_the_same`

这是 §0 那句话**本身**，不是对它的推论。**比的是同一个字符串**，不是"差不多"：
差一个空格就说明有一条翻译规则把语义也改了。

### C++ 那一格：**结论与 C 一样，理由完全不同**

这是"同一族里两门看起来一样、解释完全不同"的样本 —— 值得单独写，因为**照 C 的注解
去改 C++ 会当场弄坏一门**：

| | C | C++ |
|---|---|---|
| `a < b` 出什么 | `int`（0/1） | **`bool`**（它有独立的布尔类型） |
| `int x = (a < b);` | 合法（本来就是 int） | **合法**（`bool` 隐式转 `int`） |
| `if (x)`（x 是 int） | 合法（标量即真） | **合法**（`int` 隐式转 `bool`） |

⇒ 两个方向的强制转换**都要补**。C 是因为"**根本没有** bool"，C++ 是因为"**有** bool，
却把两个方向的隐式转换都留着"。而 **Java / C# 是关的**，因为那两门 `int x = (a < b);`
本来就编不过。**三种理由、两种结论**，全靠方言表那两格。

`const` 那一格也一并更正了：C++ 里 `const` 形参是常态，而原先 C 的表把它判成"真的改语义"
—— 在**只有标量、没有指针**的子集里，丢掉 `const` 是**保义**的（源侧本来就保证不改）。
C 与 C++ 一起改成"收下并丢掉"（`docs/186` §6.3 记了那次更正）。

### 写 C++ 的语料时撞出来的三个**共享核**的 bug

都不是 C++ 特有的 —— 是 C++ **逼出来**的：

1. **`return` 写死了整数场合**：`bool f(int x) { return x > 0; }` 会发成
   `return (x > 0) as i32;`，而函数声明的是 `-> bool`。
2. **变量一律被当成整数**：`ty_of(Var)` 恒报 `"int"`，于是 `bool ok = …; if (ok) …`
   里那个 `ok` 被当成整数 —— Java 那条 `coerce_int_to_bool=False` 的路会对一个**布尔**
   变量报"这里要的是条件，给的是整数"，一句**错的**诊断，而那段 Java 完全合法。
   修法是把"变量声明时的类型"记下来（发射器只需要分 `bool` 与"其它"两档）。
3. **`#` 那条检查是死的**：`unit()` 里有一句 `if self.at("#"): raise …不支持预处理指令`，
   可**分词器根本不产出 `#`** —— 于是任何带 `#include` 的文件都在**分词那一步**
   就报"认不出的字符 `#`"，那句更准的话永远轮不到。把 `#` 加进运算符类才通。

第 1、2 条都只有"翻 `bool` 的代码"才撞得到，而 C 那门**没有 bool**、Java/C# 的语料里
也没有返回 `bool`/声明 `bool` 变量的函数 —— 所以三处一直躺着，直到这一门。

### Go 那一门**不共用**那份共享核 —— 三条形状都不一样

`docs/188` §7.1 的架构是"一份解析器 + 方言表"，而那一份是给"**类型在名字前面**、
**条件带括号**、**`;` 结句**"那一族的（C / C++ / Java / C#）。Go 三条都不同：

| | 花括号族 | Go |
|---|---|---|
| 类型写在哪 | 名字前面（`int f(int a)`） | 名字**后面**（`func f(a int) int`，且 `a, b int` 可共享） |
| 条件括号 | 要 | **不要** |
| 循环 | `for` / `while` / `do` | **只有 `for`**，一个词管 `for {}` / `for cond {}` / `for init; cond; post {}` |

硬塞进方言表就得给解析器加三个"哪一门"的开关 —— 那就不是方言表了。加上 Go 还有
**自动分号插入**（行尾那个 `;` 是词法器补的，不是源码里的），所以 `tools/gotrans.py`
自足一份。

### 六门里独一份：**两边的严格程度正好对上**

Go **没有隐式数值转换** —— 所以 `int(b)` 这种转换在 Go 里到处都是，而那**正好**是
Loment 的 `as`：**源码里已经写好了，翻译器直接搬**。对照另外五门：

* **C / C++**：两边都做隐式转换 ⇒ 翻译器要**补**（`as i32` / `!= 0`）；
* **Java / C#**：两边都严，但语料里没撞到 ⇒ 方向开关**关着**；
* **Go**：源语言自己就要求显式 ⇒ **一个都不用补，也不用猜**。

### 同一处相反的结论：`i++` / `x += e`

C / Java / C# 里 `++` 与 `+=` 是**表达式**（有值），`y = i++` 那种写法映射不过去 ⇒ 拒。
**Go 里它们是语句、没有值**（`y = i++` 在 Go 里编不过）⇒ `i++` 就是 `i = i + 1`，照收。
按"能表达的就转"那条判据给出**相反**的结论 —— 而差别**在源语言那边**，不在 Loment 这边。

### 写这一门时撞出来的三处（都在共享层，不是 Go 特有）

1. `potato_from.from_go` **不收 `a, b int` 这种分组形参**（Go 里极常见）—— 于是
   `gcd(a, b int)` 整个函数被跳过；而且它**根本不存函数正文**，`--impl` 那条路是空的。
2. `from_go` 抹注释用的是 `sub(" ", …)`（**不保长度**），而取正文要拿剥离后的下标去切
   原文 —— 长度一变切出来就是别处的字节。`from_c` 那边早就是保长度的写法。
3. **跨层打架**：`gotrans.GO_TYPES` 第一版把 `int` 映成 `i32`（照着 Loment 的默认整数
   顺手写的），而 `potato_from.GO_TYPES` 写的是 `i64`（Go 的 `int` 在 x86-64 上就是
   64 位）。同一份 Go 会产出两个**互相矛盾**的单元 —— 一个 `pub extern fn` 说 `i64`、
   一个 `pub fn` 说 `i32`，而那种错两边都编得过。**两层口径必须是一个。**

### 补写三份**复杂**语料（C / Java / Python）撞出来的（2026-09-18）

三份新语料与它们的判据（各自由**三个独立作业**写出来，再逐条复核）：

| 语料 | 钉住什么 | 判据怎么比 |
|---|---|---|
| `loment/ctrans/numeric.c` | 七函数协作、`while`/`for` 两种循环、**跨函数调用**、位运算与除法取余 | clang 侧 103、翻译侧 103、**独立推的期望值** 103 三方相等 |
| `loment/jtrans/Bits.java` | 六个方法、**递归**（`collatz` 调自己）、`static final` 常量、位运算混排 | javac 侧 168、翻译侧 168、独立期望 168 |
| `loment/pytrans/overflow.py` | **不同意集**：`int` 的拼法是 `i64`，连乘**回绕** | 本语言 **175** / CPython **7** —— 两数**必须不同** |

**撞出来一处真洞（已补）：`~` 能过前端，却死在后面。**

`trans_core.unary()` 原先**收下** `~` 并照发 `(~v)`，而 **Loment 没有按位取反**
（一元只有 `-` 与 `!`）。于是产物死在**编译器**的词法那一步（`非法字符 '~'`），
而且报的是**生成出来那个单元**的行号 —— 用户在源码里找不到那一行。同一个文件里
`>>>` 却是**点名拒 + 给出路**的：一处"能过前端、在后面才炸"的洞，与 `docs/167`
要消灭的那类同形。现在 `~` 进了 `trans_core._REJECT_NAMED`：**四门共享核**都在分词
那一步拒，并给出**按宽度**的两条出路（`v ^ -1` / `v ^ 255`）。它本可以自动转，
但翻译器**不做整数宽度跟踪**（§7.1.1），替不了你选 —— 所以与 `>>>` 同一条纪律：
**先不收，除非有语料逼它**。判据四门各验一次 + 前门另验一次
（`loment_ctrans_test::test_bitwise_not_is_loud_in_every_brace_dialect`）。

**同一处病灶的另一面（已修）：走前门时，报的行号是"按函数体"算的。**

`.java` 文件 → 该交给编译器的 Loment 源这条路，前端报的行号是**函数体内**的行号。
实测：`~` 在文件第 3 行，报出来是"第 2 行"（= 那个函数体的第 2 行）。根因在
`lomt_from.emit_lomt`：它把**各函数体拼起来**再交给翻译器，拼接时**不带行偏移**
—— 而 `trans_core` 里那几十处 `第 {n} 行` 数的是**它拿到的那串文本**的行号。

修法是**位置另记一个字段**：`potato_from` 抓正文时同时记下它在源文件里的起始行
（`functions[i].body_line`，可选、与 `body` 配对，**不动契约版本**），`lomt_from`
拼那份**临时源**时按它垫空行。这样三件事同时成立：

* `body` **一个字节都不动** —— `loment_ctrans_test::test_body_is_byte_faithful`
  钉着"与原文逐字节相同"，所以垫空行只能垫在**拼出来的**那份源里，不能垫进 `body`；
* `trans_core` 那一侧**一行都不用改**（行号在源头就对上了，不用去改写诊断）；
* `--impl` 发出来的 `.lomt` **一个字节都不变**（`Emitter` 从语法树出行）。

六门的正文抓取都记了这一行（C / C++ / Go 是按下标切、Python 取 `node.lineno`、
Java / C# 那族共用引擎）。**顺带补掉一处同源的洞**：类壳那一族剥注释原先是
`sub(" ", …)`（**不保长度**），一段多行注释会把后面的行**整体上移** —— 与
`docs/186` §3.2 在 `from_c` 上修掉的是同一处，这一族一直留着，现在一并换成保长度的写法。

判据 `loment_multisyntax_test::test_subset_error_line_is_the_file_line`：**八份源**
（六门各一份**两段正文**的夹具 + 缺陷报告里那个最小复现 + 它的多行注释变体）
**两个入口各验一次** —— 前门与 `translate()`（`docs/182` §1.9）。
期望行号**从源里推**（那一处标记落在第几行），不写死；并且夹具自证**能分辨两种读法**
（函数体内的行号 ≠ 文件里的行号），否则测的是一个"两种读法都对"的输入。
实测：把拼接退回裸拼，这条当场红。

**三份共有的边界（不是 bug，是子集画的线）**：

* **数组 / 指针**：C 与 Java 都写不出来（`不支持指针/数组声明`；数组字面量撞"不支持裸块"）
  —— 三份因此全用标量。
* **整数宽度**：Java 的窄类型、C 的 `unsigned` 一旦混进 `int`，翻出来的单元会在
  `lomentc.check` **硬失败**（§7.1.1）—— 所以每份只用一个宽度。
* **Python 那一门说不出宽度**（`x: u8` 直接报"注解不在子集里"）—— 于是"溢出"在源码层
  **看不见**，只能靠语料把它钉住。这正是 `overflow.py` 存在的理由。

## 7.2 `choose write grammar`：**编译器这条路走通了**（`loment_grammar_test` 14/14）

用户 2026-09-18 要的那个开关。**命令行上真能编了**：

```
$ lomentc --check  pyunit.lomt        # 里面写的是 `choose write grammar python` + Python
[OK] 生成物与磁盘一致                  (rc=0)
$ lomentc --print llvm pyunit.lomt    # 真的 IR，`; entry -> i64`
```

### 落了地的

| 落点 | 是什么 |
|---|---|
| `potato_from.GRAMMAR_ALIASES` | **出厂锁的取值表**，16 条拼法 → 8 个规范名 |
| `find_decl` / `read_grammar_decl` | **文件头预扫**：必须在 `module` 之前、只许一次、拼法要在锁里 |
| `potato_from.resolve_lang` | 次序改成 **声明 > 后缀 > 内容** |
| `potato_from.strip_grammar_decl` | **等长空白抹掉那一行**（行号不漂） |
| `potato_from.front_door` | **前门**：一份源 → 该交给编译器的**那一份 Loment 源码**；别的写法就在本进程里翻 |
| `lomentc.load` **与** `prescan_switches` | **两处入口都过前门** —— 见下面那条教训 |
| `mod.src` | **翻译出来的单元不记账**（`!DIFile` 说的是"行号属于哪个文件"） |
| `loment_grammar_test` | **14 条**：锁被钉住 / 规范名 == `potato.GRAMMARS` / 别名归一 / 声明压嗅探与后缀 / 四档报错 / **前门两条路** / 翻不出来时拒 / **两处入口各一条** / `.lomt` 不嗅探 / 枚举对拍 469 条 |

### 四处刻意的设计，都写在判据里而不只在注释里

1. **锁是被"钉住"的，不是被"推出来"的**：判据里有一份**字面量**。加一门语言要**同时**
   改它 —— 那一步就是"改锁"，得是显式的一笔（用户说的"将来可以用哈希把它钉死"的前一步）。
2. **规范名只有一处**：别名表右列**必须恰好** == `potato.GRAMMARS`。对不上的症状是
   "源里能写、对象却非法"。
3. **声明是"前端指令"，不是语法** —— **抹掉那一行，parser 一行不动**。
   见 `front_door` 的注解：让它成为真语法要动 lexer/parser，而语言面有两个实现 +
   种子重生成；而 `choose` 在 Loment 里**已经是开关关键字**，`choose write grammar python`
   会被读成"取开关 `write`"—— 要加**特例**才分得开。**"声明"本来就不是那份源的一部分**
   （它说的是"怎么读"），所以它属于前端、不属于语法。
4. **`.lomt` 不嗅探，但 `resolve_lang` 照旧嗅探** —— 不是不一致，是**分工**：
   编译器要求显式，前端工具可以先猜。见 `front_door` 的注解。

### 一条教训：**入口不止一处**（`docs/182` §1.9 那张清单）

只接 `lomentc.load` 是**不够的** —— **开关预扫**（`prescan_switches` 里那个 `scan`）
**自己**读一遍源。症状是**命令行**上报"未定义的开关 `write`"，而**库那一侧的判据全绿**。
⇒ 判据因此写成**两条**（一条钉 `load`、一条钉 `load_unit`（含预扫））——
**一条判据盖不住多个入口**，这条与 `docs/182` §1.9 是同一个形状。

**2026-09-18 又撞到一次（这回是"入口"的另一种）**：前门**拒**的那三档
（别名不在出厂锁里 / 后缀和内容都认不出来 / 这门拼法翻不出来）在**命令行**上是
**Python traceback** —— `front_door` 抛得挺对（`FrontDoorRefused` / `NotRepresentable`），
但 `lomentc` 的**两个调用点都没人接**。于是**库那一侧的判据全绿**（它们直接调函数），
而用户一句话都看不到。修法**拦在唯一入口**上：`lomentc.load_unit` 把这一支翻成编译器
自己的 `LomError`（`lomc.py` 里 `line == 0` = "指不出位置"，那就**不编**一个位置），
八个调用点于是都按既有方式报错。判据钉的是 **CLI 的输出**、不是某一行代码
（`loment_grammar_test::test_a_front_door_refusal_reaches_the_cli_as_an_error_not_a_traceback`，
三档各一次）。

### 自举侧那一半：**`grammar loment` 那一格落了**（`loment_p8_test` M87）

自举侧在 **`lex` 之前、按字节**抹那一行（`driver.lomt` 的 `strip_grammar_decl`）——
于是 lexer / parser / codegen **一行都没动**，语言面不为它添任何规矩。

**只收一种形状**：写在 `module` 之前、只写一次、拼法是 `loment`。别的形状一律**拒**，
理由与 `has_extblock` 同一条纪律（**错要指在错的地方**）—— 放它过去，用户看到的是
"未定义的开关 `write`"，而真正的理由是"这门写法还没接上"（下一格）。

判据是 `loment_p8_test::test_m87_driver_strips_grammar_decl`，钉三件：

| 钉什么 | 怎么钉 |
|---|---|
| **抹掉之后不留痕** | 带声明那份的产物与**不带声明**那份**逐字节相同** —— 对照面是**另一个单元**，不是参考实现（两个实现一起错时"自举 == 参考"照样绿，`docs/182` §1.9） |
| **别的拼法拒，且说得清** | 参考实现**真收**那份 `grammar python` 的（按 Python 读），自举侧拒；拒的话里要有"自举侧收不了"、**不能**是"未定义的开关" |
| **拒的时候不产 IR** | 非零退出 + 空 stdout |

语料在同名目录 `loment/selfhost/grammar_decl/`（三个单元**同一个模块名**，产物才好比）。

### 写这一格时撞出来的**真** bug：不是"函数形状"，是 `.ll` 越过了 2 MiB（`docs/192`）

这一段值得留着 —— 因为**我先把因认错了**。

第一版那个函数是一个 74 行的嵌套级联（5 层 `if`、7 个 `while`、18 个局部）。它让
`loment_seed_test` 的**定点**判据红（stage1 段错误，退出 139）。当时的推理是"**形状**问题"，
证据看起来还挺硬：把函数体换成一坨**等长**的桩，判据就 4/4 过。

**那个证据是错的，错在比的对象**：比的是**源文件**长度（2791 B 对 2791 B），
而决定这件事的量是**产物 `.ll`** 的长度 —— 同一份源，桩 2082032 B、嵌套版 2100891 B，
**差了 18 KB**（`--emit` 的字节数就在手边，我却没去量它）。

真正的线是 genesis（`lomelf`）的输入上限 **2 MiB**（`loment/tools/lomelf.lomt:53`）。
五组实验全部落在这条线上，只有分开量 `.ll` 才看得见：

| 版本 | `.ll` | 2 MiB = 2097152 | 结果 |
|---|---|---|---|
| 桩 | 2082032 | 低 15 KB | 定点 4/4 ✓ |
| 扁平（现在这份） | **2095761** | 低 **1377 B** | 定点 4/4 ✓ |
| 嵌套 | 2100891 | **高 3.7 KB** | stage1 段错误 ✗ |
| 嵌套 A1（去掉长字符串） | 2099742 | 高 2.6 KB | 段错误 ✗ |
| 嵌套 B（连调用点都删掉） | 2099612 | 高 2.5 KB | 段错误 ✗ |

**B 那一行是决定性的**：函数**根本没被调用**，程序照样崩 —— 崩的不是那段代码，
是**汇编出来的那个二进制**。再用同一份 `.ll` 换汇编器，一眼分清责任：

```
genesis 汇编 -> rc=139 (段错误)        clang 汇编 -> rc=0, 产物 3172 B 正常
```

⇒ **是 lomelf 的输入上限 + 静默截断**，与"函数长什么样"无关。扁平化能修好，
只是因为它把那 5 KB 缩回去了 —— **治的是症状**。

**两条纪律**（都是这次踩出来的）：

1. **比"大小"时先问清楚是哪个东西的大小。** 源文件长度 ≠ 产物长度；
   `--emit` 的输出字节数是现成的，别用手边那个更容易量的代理量。
2. **"换一坨等长的东西就好了"不是因果证据**，只要那个替换顺带改了别的量（这里是
   18 KB 的 IR）。真正分清的是**换一个变量**：同一份输入、换**汇编器**（genesis vs clang）。

### 还没落地的

* **别的写法那一半**：自举侧**做不到** —— 它得先**有那些翻译器的 Loment 孪生**
  （`docs/189` §4.1）。所以这一半**正确地阻塞在自举那一格**上，不是阻塞在 `lomentc.py`。
* **直接读源的编辑器入口**（`lomfmt` / `lomdoc` / LSP）：它们仍会看到那一行。
  要不要认是**另一件事**（那些入口在 `docs/182` §1.9 那张清单里）。

**顺序**（定死了，别反）：先在 `lomentc` 定下"前门怎么分派"，再照到自举侧 ——
反过来做，种子会先被一条还没定型的规则位移一次。

## 7.3 `grammar rust` 是**基础语法的另一种拼法**（2026-09-22）

用户 2026-09-22 的裁定，一句话：

> **rust 语法是 Loment 基础语法，不需要翻译**

### 7.3.1 改之前：一个**登记在锁里、却没有任何一份源编得过去**的名字

`rust` 在**两处**都登记着 —— 出厂锁 `GRAMMAR_ALIASES` 的右列（== `potato.GRAMMARS`）
与 `LANGS`。于是**源码里能写、对象也合法**。可 `lomt_from._TOOLS` 里**没有 rust 这一门**
（`from_rust` 是 §7.1 之外的另一条路：`docs/179` 抽接口，**只记声明、不抓正文**）。后果：

而那句跳过理由**还指反了**：它劝人「带正文的加 `--impl` 翻出来」，而前门**已经**用的

### 7.3.2 改了什么

| 落点 | 改了什么 |

### 7.3.3 一处**刻意保留的不对称**：声明 vs 后缀

**后缀 `.rs` 与 `--lang rust` 照旧走 `from_rust`**（抽接口那条路 —— `kernel/src/*.rs`
与 `lompotc --rust` 那条孪生判据都靠它）。两者不冲突，因为**分工不同**（§2 自己那条）：

* **后缀**说"这是**哪个语言的文件**" → `.rs` 是 Rust 的文件 → 抽它的接口；
* **声明**说"这份 **Loment** 用哪种**写法**" → `grammar rust` 是基础语法的拼法 → 原生读。

判据把这一条**也钉住了**（`test_declared_rust_is_the_base_syntax_not_a_foreign_module`
第 3 件）：少了它，下一次"顺手统一"就会把接口那条路悄悄换成原生读法，而那是
`lomt_audit` / `fuai_contract_check` 的对照面。

### 7.3.4 六门**各一个大型项目**（语料 `loment/examples/multisyntax-projects/`）

同一轮里落了六门表层语法各一个**带正文、能真跑**的项目 —— 与 §8 那批"抽接口"的语料
是两件事（那批只测"抽得对不对"，这批测"**算得对不对**"）。判据
`loment_multisyntax_projects_test`，问的是**三方相等**：

```
那份源 ──真实工具链（clang/g++/javac/go/CPython/rustc）──> rc_control ─┐
那份源 ──前门翻成 Loment──> lomelf ──> ELF ──WSL 跑──> rc_loment ──────┼─ 三者相等
项目 README 里独立推出来的期望值（`EXPECTED: <数>`）───────────────────┘
```

**少了哪一方都有一种错穿不过去**，而且**实测过一次三方不一致**：`c/01-algo` 的
`isqrt` 写了 `mid * mid <= n`，n 过 8.6 万时有符号溢出（C 里是 UB）——
`clang -O1` 给 1000、本语言给 458753（**回绕**语义）、独立推的又是 1000。
**三方里有两方相等不能说明什么**；改成语料里不留溢出（`mid <= n / mid`）之后三方一致。
这一条与"每门配一个独立推出来的期望值"是同一件事的两面。

### 7.3.5 `mut` 映射掉：`grammar rust` 里必须写得出一句重赋值（`#77`）

`grammar rust` 是**原生读法**，而 Rust 与本语言在"本地变量怎么声明"上没有交集：

| | 重赋值一个本地变量 | 重赋值一个形参 |
|---|---|---|
| Rust | `let mut v: T = e;` | `fn f(mut a: T)` |
| 本语言 | `let v: T = e;`（本地变量本来就可变） | `fn f(a: T)` |

两种拼法互不相容：写 `let mut` 在 `mut` 上解析不过（`期望 :，得到 'v'`），去掉 `mut`
又被 `rustc` 拒（`cannot assign twice to immutable variable`）。后果不是一条小限制 ——
**每一个有状态循环都写不出来**（累加器只能改成递归辅助函数）。

**决定（`#77` 的两个选项里选 1：前端映射掉）**：前门对 `grammar rust` 做一次
**等长**的表层改写 —— `let mut x: T = e` → `let x: T = e`、`fn f(mut a: T)` →
`fn f(a: T)`。这是**拼法**上的事，不是语义：在本语言里那些本地变量本来就可变，
与另外五门翻译器做的事同类（它们把源语言的声明搬过来，这一门只是把标记抹掉）。

**只动这两种位置**。`mut` 在本语言里还有别的意思 —— `mut [T]`（可变切片类型）与
`&mut`（可变借用）—— 一刀切会把那两处一起抹掉，直接改坏程序。判据用**词法器的
token** 而不是正则（字符串/注释里的 `mut` 不算 token）：
`loment_grammar_test::test_declared_rust_maps_mut_away_but_keeps_mut_slices`。
改写是等长的（换空格、保留换行），所以行号/列号/偏移都不动。
