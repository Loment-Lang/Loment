## 3. 架构：让"外部库"成为库系统的头等公民

今天"一个库 = 一个目录里的 `.lomt`"（`docs/168:8`）。这条垂直要把这句话**推广**成：

> **一个库 = 一份声明面 + 一份实现（源码**或**二进制）+ 一个身份。**

| 件 | Loment 库（今天） | 外部库（要做的） |
|---|---|---|
| **声明面** | 就是 `.lomt` 本身 | **由语法层生成**的接口单元（`docs/179` 那条链的产物） |
| **实现** | 同目录的 `.lomt` | `.a` / `.so` / `libpython` / 一个解释器 |
| **身份** | Merkle 内容哈希（`docs/168:29`） | 推广：源码哈希 ⊕ 二进制哈希 —— **二进制也要进身份**，否则"同一份声明绑到不同的机器码"正是 `docs/168` 要防的那种错合并 |
| **发现** | `deps/` → store → 四根（`lomentc.py:2116-2130`） | 同一条 `use <名字>`，只是在 `deps/<名字>/` 里多认一个**接口单元 + 二进制** |
| **取/锁** | `lompi`（registry = 同布局的 git 仓） | `lompi` 多认一种成员 |

**关键点：`use <名字>` 是唯一需要动的地方。** 只要 `deps/<名字>/` 里能同时存在
`<名字>.lomt`（声明面）与二进制，编译器就**不需要知道**它是外部的 —— 它照旧 `use`，
只是那些 `extern fn` 这次**真有人提供**。

### 3.1 `choose` 开关：把"禁令"从**全局**改成**每程序**

`docs/168:152-159` 把"二进制分发"列进**不做**。用户 2026-09-17 定的解禁方式不是删掉这条，
而是**把它变成一个 `choose` 开关**：

- **默认仍然是禁的**（不写 `choose` 就是今天的行为）—— 那条纯度主张**原封不动**；
- 写 `choose <二进制开关>` 的程序才允许把二进制依赖链进来。

这与 `docs/182` 的设计严丝合缝：**官方开关是核心语法的硬写法**（用户原话："未来官方写入的
choose 也是硬写法"），所以它是**核心语法**的一个新开关名，不是 `set choose` 那种用户自定义开关。

**收益**：可审计（`choose` 在根单元、只许一次、库不许写）、可逐程序关闭、
而且 `no_std` 与它在同一套机制里。

## 4. 分阶段（每步独立可交付 + 可证伪）

判据的形式统一为：**照着 README 的说法做一遍，`loment run` 出正确结果**。
每步都要有**两侧**（参考实现 + 自举）—— `docs/158` §5 那条。

| # | 阶段 | 解开什么 | 证伪判据（端到端） |
|---|---|---|---|
| **V0** | **结构**：外部库在库系统里有位置 | `deps/<名字>/` 能放"接口单元 + 二进制"；`lompi` 能取/锁/校验它 | 一个**手工搭的**外部库目录，`use <名字>` 能解析、能链、能跑。**后端仍是玩具**（自包含 freestanding），所以这一步不动链接器 |
| **V1** | **静态 libc** | 带 libc 依赖的**真实 C 库** | `loment run` 调 **zlib** 的 `compress`/`uncompress`，解压回原文。zlib 是 `.a` + 依赖 `malloc/free/memcpy` |
| **V2** ✅ **2026-10-17**（`#360`） | **动态库**（`docs/173` 阶段 3） | "装好的 `.so`" | `loment run` 调**系统装的** `libz.so`（不静态链）。**产品发的是表，不是 loader**：两个链接器都读 `ET_DYN` 的导出表、发 `PT_INTERP`/`PT_DYNAMIC`/`DT_NEEDED`/PLT-GOT；**映射与重定位绑定由系统的 `ld.so` 完成**。已兑现：产物 20 KB、`compress → uncompress → 原文` rc=0，两侧逐字节相同 |
| **V3** | **运行期嵌入**（阶段 4） | Python / Java **的 API** | `loment run` 调 **`numpy`** 算一个数组的和。要 `libpython` + CPython C-API 胶水 |
| **V4** | **语法层解真实源** | 从**真实库**生成声明面 | 喂 **`zlib.h`**（typedef / 函数式宏 / `unsigned long` / `Bytef*`）→ 接口单元 → V1 那条跑通。今天 C 前端是**轻量正则**，`zlib.h` 会当场碎 |
| **V5** | **`choose` 解禁开关** | 二进制从**全局禁**变成**每程序可开** | `choose <开关>` 的程序能链二进制；**不写就编译不过**（且报错说清为什么） |

**次序的理由**：V0 是"接成一条"（用户那条垂直的本体）；V1 是**最小的真实库**（C 已是
最强的那条腿）；V2/V3 是 `docs/173` 的阶段 3/4；V4 让 V1–V3 的声明面**不必手写**；
V5 是纪律面，放在最后是因为它要等"二进制真的能用"才有意义。

**V2 的 interp 与多库**（`#604` / `#596`，**参考链接器 `tools/lomelf.py`**）：
产品**不携带自己的 loader** —— 它只写出 `ld.so` 会消费的表（`PT_INTERP` 指名那个
loader），真正的映射与符号绑定发生在宿主 loader 里（`docs/219` §164）。
`PT_INTERP` 不再写死 —— 链接时按 `--interp PATH` → `LOMENT_INTERP` → 链接机上的候选
（glibc 两个常见落点、musl）解析，Windows 上交叉链接仍默认
`/lib64/ld-linux-x86-64.so.2`（目标不是本机，用 `--interp` 覆盖）。`--link` 可以给多个
`.so`：每个一个 `DT_NEEDED`，导入按 `--link` 顺序解析（第一个导出它的库胜出）——
`docs/219` 那条"同时要 `libz` 与 `libc`"的组合因此可用。自举镜像
（`loment/tools/lomelf.lomt`）在这一版仍只做单库、且不接受 `--interp`；两边产物在
现有语料上逐字节相同。

## 5. 代价与风险（如实记，不粉饰）

1. **V3 是另一个量级。** CPython C-API 的胶水（引用计数、GIL、`PyObject*` 的生命周期）
   不是"再写个加载器"。`docs/173:53-55` 已经把它单独列为阶段 4。
2. **PE 侧全线缺失。** `--link` 配 `--target pe` **明确拒绝**（`lomelf.py:2472-2474`），
   动态库在 PE 上要**自己解导入表**。这条垂直在 Linux/ELF 上能走通时，Windows 可能还在原地。
3. **两个实现的差距会被真实库放大。** `docs/158` §4 里 #8（括号 `ptr` 表达式 `as` 整数，
   自举发 `zext i32` **截地址**）、#9（自举链接器 **4 MiB** 暂存上限）、#10（PC64 符号扩展）
   —— 玩具对象撞不到，真库会。
4. **与 `docs/176` 直接冲突。** 这条垂直会**持续动冻结面**（语法层、`extern` 签名、`choose`、
   链接器符号约定），而 `docs/176` 测出来的结论是"改冻结面贵在**架构差**不是行数"。
   每一次改动都要走 `docs/158` §5 四条 + 两个实现同一次提交。**这是本计划最大的成本项。**
5. **Rust crate 靶子可能撞死。** `_check_representable` **直接拒** `generics`/`instances`
   （`lomt_from.py:55-61`），而 crates.io 上的公开 API 几乎全是泛型。
   所以要**提前选好**：靶子必须是那些**有 `#[no_mangle] extern "C"` 面**的 crate
   （`*-sys` 那一类，如 `zstd-sys`/`lz4-sys`），否则这条靶子在 V0 就过不去。
6. **"全部同时"不是并行开工。** 三条二进制路线有硬依赖；V3 之前 V2 必须站稳。

  这条垂直要新增的语法只有 **`choose` 的一个官方开关**。

> **本节推翻了 §6 的一条明写在案的边界**（"这条垂直要新增的语法只有 `choose` 的一个官方

### 8.0 用户原话与我的读法

| 用户写的 | 读成什么 |
|---|---|
| `let py {py代码}` / `c {c代码}` | **外部代码块**：块里是别语言的**正文**，Loment 当宿主 |
| `foruse c/py/…`「这个文件由 Loment 调节器拉起目标语言的编译器，若不存在报错」 | **编译期**的调节器：调目标语言的编译器 |
| `command c` / `c { }` / `py { }`「主要运行 c，py 作为 c 的辅助」 | 选**主语言** + 多个语言块共存 |
| `command c without loment`「在运行时脱离 loment 宿主」 | **运行期**脱离宿主 |
| `comefor let <语言> '词语' to { … }` … `byuse <语言> done` | **用户自定义语法** |

**经三问确认**：① 时机 —— **编译期先、运行期后**；② `comefor` —— 要**完整宏系统**；
③ 关系 —— **并入本文件**。

### 8.1 三堵墙（都是实测过的，不是估计）

**墙 ①　Potato 没有 `body` 字段 —— 已经量过。**
`docs/183:22`：v0/v1/v2 三版顶层字段里没有 `body`，`docs/179:70` 明说这是**结构性扩展**，
不是加个字段。而 `let py { … }` 要的是把**外部代码正文**带到 codegen。
方向还是**倒过来**的：今天多语法前端的产出**恰好就是 FFI 声明**（§3），也就是
"给外部实现抄一份接口"；S1 要的是**正文给外部、接口留 Loment**。

**墙 ②　`without loment`（运行期脱离宿主）在 Windows 上今天做不到。**
`docs/182:417-419`：PE 的导入表是**写死的 11 个 kernel32 函数**（`lomelf.py:1203-1205`），
**没有 `CreateProcess`** —— 编出来的程序**自己起不了进程**；`loment/lib/proc.lomt:18-19`
在 PE 上**一律返回 -1**（且不是悄悄失败）。

**墙 ③　`let` 是绑定关键字。**
`docs/182` §1.6 ④ 已经因为 `choose close X` 抢走 `close` 这个词记过一次账（代价是
"用户从此不能给开关起名 `close`"）。`let` 的量级不一样 —— 它是**绑定关键字**，
而 Loment 的定位是 **Rust 严格子集**。
**用户已定：两种写法都要、且等价**（见 §8.4）。

**墙 ④　§3 的"全部自己做"会被 `foruse` 顶到。**
§6 写着"**不把 FFI 构建交回 clang/lld**"。而实测**今天的正常构建一个外部编译器都不需要**：
`tools/loment_build.py` 不 shell out；`tools/loment_boot.py:49-52` 专门把 clang 换成了
`lomelf.compile_ll`；发行版启动器写着 "no Python, no clang"。
**建议的划法**：纯度主张保留在**"没写 `foruse` 的程序"**上 —— 只有显式写了 `foruse` 的程序
才需要外部编译器。那条原则不必删，只是加了条件。

### 8.3 S1 的关键：**必须新开 raw 词法模式，绝不能用字符串字面量装**

依据（实测，`tools/lomc.py:61,86-99`）：

- 转义表只有 **4 条**（`n`/`t`/`"`/`\`）；**未知转义静默退化** —— `\0` → `"0"`、`\x41` → `"x41"`。
  那是**静默改内容**，正是本仓反复要消灭的东西。
- **没有非 UTF-8 通道**（源按 UTF-8 文本读）。

⇒ 新 AST 节点（外部代码正文）；Potato 升 **v5** —— validator **拒未知顶层字段**
（**v4 已被 `comefor` 的 `dialects` 用掉**，见 `docs/184` §7 ②：本仓的规矩是一个必填字段一次升版。写 v5 不写 v4，是因为 v4 已经发出去了。）
（`tools/potato.py:99-101`），所以只能升版。

### 8.4 S4 的落点：**内核外**，而这一点是用户指出的

> **当时的推理**（它把账算清是有用的），但**落点、代价、分步一律以 `docs/184` 为准**。
> 最大的区别：`docs/184` §2 核实出**自举的 parser 没接进编译管线**，所以就算搬到内核内，
> **语义宏那一档也拿不到** —— 那条不是内/外的区别，是"两个实现一致"逼出来的。

> 用户原话：**"当这个伟大的计划结束，你可以用 Loment 在 Loment 内核外部、用 Loment 语法
> 创造新的 Loment 语法。"**

我原来的设计把 `comefor` 当**内核特性** —— 于是要表驱动 parser、要两份实现逐字节一致、
要把三张静态关键字表改成动态查询。**那份代价清单大部分是白算的**：挪到内核外，它大半消失。

**既有先例就是 `lomenterr`**（`docs/182` §6）：

- 放 `bin/`，与 `loment-driver` / `loment-cli` / `lompi` 并列；**复用**既有工具清单
  （`loment_dist.py:52-68`）与解析函数 `tool()`（`:111-116`）—— 不引入新约定
  （`docs/162` §2b："没有注册表，约定就是文件名"）。
- **同一份源码两种用法**：编译期工具链起它；运行时同一份源码被链进程序。
- **找不到时落到内置，但要说出来** —— 不能悄悄换掉用户以为在用的东西。

⇒ **语法扩展是同一个形状**：`bin/` 下一个**用 Loment 写的**程序，吃源码、吐源码。**内核不动。**

**这保住了 `docs/182:262`**（"新关键字不需要改词法/语法分析器"）—— 那条省成本结论的前提是
**内核的关键字固定**；扩展挪到内核外，前提重新成立。**双实现逐字节一致的负担也随之消失**：
扩展是**一个**程序，不是两个。

**换来的新东西（要新设计，但小得多）**：

| 件 | 说明 |
|---|---|
| **源码预扫挂钩** | 声明点**正好是 `loment.conf`** —— 它今天就是"工具链怎么读源码"的载体（`docs/182` §7 已划清）。加一个标签，**读法照抄 `_conf_ext_from_tokens`**（词法器，不是解析器） |
| **找不到那个工具 → 落到"不扩展"并把话说出来** | 与 `lomenterr` 同一条纪律 |
| **可复现** | 预扫是**变换**，纪律与自举种子同构：**能藏的前提是它可复现**（`CLAUDE.md` 种子那条） |

**`comefor` 那套语法本身**仍要定，但**落点从内核变成了一个工具**。两种模式：

- **填了语言名**：体是**那门语言的代码**，与 S1 的外部块同类，只是由用户起的词触发。
- **不填语言名**（`comefor let '…' to { … }`）：体是 **Loment 代码** —— 纯语法扩展（造一个新词）。

原先那条语法问题也还在：终结符是**另一个顶层语句** `byuse <语言> done` 而不是花括号 ⇒
这套块**不能嵌套**、且**跨整个文件有序依赖**。

### 8.5 `let` 的两种写法（用户已定：都要，且等价）

`c { … }` 与 `let c { … }` **两种都收**。消歧规则（必须写下来，`let` 是绑定关键字）：

- `let IDENT {` → **外部块**
- `let IDENT :` 或 `let IDENT =` → **绑定**（今天的行为）

今天 Loment **没有块表达式**，所以 `let x { … }` 现在根本解析不过 —— 这个产生式是**新加的**，
不与既有语法冲突。但要**额外一条判据**钉住：同一个块，两种写法产出的 IR 与 Potato
**逐字节相同**（否则"等价"就只是一句话）。
