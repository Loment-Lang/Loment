## 0. 先解决"能不能互认"

跨实现恢复的第一道墙不是序列化，是**地址布局**：

| 量 | 之前（参考） | 之前（镜像） | 现在（两边） |
|---|---|---|---|
| `MEM_SIZE` | 16 MiB | 4 MiB | **4 MiB** |
| `GLOBAL_BASE` | 64 KiB | 64 KiB | 64 KiB |
| `FRAME_SIZE` | 4096 | 32768 | **32768** |
| 帧内槽区起点 | `base` | `base + 16520` | **`base + 16520`** |
| `MAX_DEPTH` | 128 | 32 | **32** |
| 堆上限 | `MEM_SIZE` | `MEM_SIZE - 32*FRAME_SIZE` | **3 MiB** |

布局不一致时，快照里的 alloca 地址、帧基址、堆游标都是"另一套坐标系"，
恢复只能靠搬指针 —— 而裸地址里分不出哪个 8 字节是指针。所以参考实现**改成镜像的布局**
（`docs/263` 的上限表随之更新），两边对同一份程序算出同一组地址。

剩下的是**帧内表示**：

* 镜像把一帧的 SSA 值放在 guest 内存 `fr+8` 的值表里（`name_off/name_len/vlo/vhi`），
  槽区从 `fr+16520` 起；
* 参考实现的值在 Python 字典里。

共同快照让参考实现**把字典写进同一张表**：快照时按 IR 里的名字跨度写下去，
恢复时按同一张表读回来。名字跨度（`%t1` 在输入文本里的偏移）由 `ir_layout()` 从 IR 重扫，
必须与镜像解析出来的逐字节一致 —— 它不是元数据，是**键**。

## 1. 共同格式

```
头      16 B : "LVMC" / version 1 / 输入 FNV-1a / 基质 flags（0 none / 1 sw_cap / 2 sw_tag）
ctx    256 B : 深度、步数、堆游标、对象计数、特权层数、站点……
全局     4+N : count；每项 = 名字（u32 长度 + 字节）+ 地址
对象     4+N : count；每项 = oid / base / limit / gen / alive / kind / tag（7 × u32）
            next_oid / tag_seq（各 u32）
续延栈 2112 B: 33 帧 × 16 u32（fi/fr/cfr/ro/rl/bi/j/do/dl/priv/hook/a0/prev/steps）
内存  4 MiB  : 整个 guest 地址空间（含帧值表与聚合暂存）
扩展    可选 : "LVEX" / version / npending，然后 pending / caps / shadow / vfd / argv
```

* **对象 kind 码两边同数**：1 global / 2 brk / 3 alloca / 4 heap / 5 argv
  （argv 只出现在参考侧；镜像读到 5 当 global）。
* **PC 用名字，不用下标**：续延栈里的 `fi / bi / prev` 是**两边各自解析出来的块号** ——
  同一份 `.ll` 喂两个解析器，累加出来的块号就会差一格（两边都从同一个块表数，
  差的是一处解析差异，不是偏移）。第一版按全局下标交接，两个方向都停在错的块上
  （`%n` 未定义 / "块没有终结指令"）。现在扩展里带**函数名、块标签、前驱标签**，
  恢复侧按名字查回自己的下标；续延栈里的下标仍写，但只作参考面自己用。
* **`ir_fnv`**：两边都用 FNV-1a 32（镜像没有 SHA-256）。换一份 IR 恢复会被点名拒。

### 1.0 一个已经踩过的坑：`FBASE` 的下标单位

镜像恢复后第一次**函数返回**会把整张对象表当成那一帧的，全部归还（症状：`sw_cap` 下
一恢复就 `F02 dangling`，地址正好是栈顶帧的槽区）。根因是 `frame_obj_rebuild` 用
`store32(a, FBASE_OFF + d*4, …)` 写，而 `bind_call` / `frame_retire` 读的是
`rd(a, FBASE_OFF, d*4)` —— **第 d*4 个字**，不是第 d*4 个字节。恢复时这条路径第一次
被走到（`_start` 的正常路径只写深度 1 那一格），所以只有恢复的判据抓得到。

### 1.1 参考侧扩展

共同格式用镜像的布局；参考实现多的东西放在**扩展**里，镜像读到就跳过：

| 段 | 内容 | 镜像怎么处理 |
|---|---|---|
| `pending` | 停在 `phi` 一半时的待写回值 | **非零就拒**（镜像没有并行 phi 暂存） |
| `caps` | 每个 SSA 值的能力 `(oid, gen, tag)` | 忽略（镜像按地址） |
| `shadow` | 指针存储的影子表 | 忽略 |
| `vfd` | 合成文件的 fd / 游标 / 字节 | 忽略（镜像用自己合成的 cmdline） |
| `argv` | 被解释程序的命令行 | 忽略（镜像用自己进程的 argv） |

镜像写快照时写一个**最小扩展**（全零），参考侧能解析；参考侧读镜像的快照时，
扩展里的空字段按"没有"处理，能力用 `cap_for_addr` 按地址重建。

## 2. 两个方向

### 参考 → 镜像

1. 参考在 K 条指令处快照（共同格式 + 扩展）；
2. 镜像 `resume=PATH`：读头、ctx、全局表、对象表、续延栈、4 MiB 内存；
   跳过 `place_globals`，按名字把全局地址补回 G 表；重建各帧的 alloca 列表
   （按帧地址区间分组）；扩展里的 `pending` 非零就拒；
3. 从续延栈继续。

### 镜像 → 参考

1. 镜像 `ckpt=K ckpt-out=PATH`；
2. 参考读同一格式：扩展里的帧名字换成自己的函数/块，按值表的名字跨度把值读回字典
   （聚合从内存里读 `size` 字节），能力按地址重建；
3. 从 `stack` 继续。

### 保真度（写死的边界）

* **能力精度**：镜像没有 SSA 能力表。参考 → 镜像会丢掉 GEP 派生的精确能力（退化为按地址）；
  镜像 → 参考会按地址重建能力。合法程序两种基质下答案相同；故障面的精确度不同。
* **`sw_tag`**：镜像不支持，读到头里的 flags=2 直接拒。
* **`phi` 中途**：参考的并行 phi 暂存只在参考侧有；跨实现恢复要求没有 pending。
* **外部输入**：合成 cmdline 用各自进程的 argv；跨实现恢复要在同一命令行下。
  真实文件 / 时间 / pid 不在快照里（`docs/360` W5 的同一条边界）。

## 4. 我不主张

1. **不主张任意程序。** 夹具是 `_start`、标量/少量聚合、无 `phi` 中途、无 `sw_tag`、
   无真实文件 I/O。镜像的固定表（1024 值/帧等）仍是硬上限。
2. **不主张能力精度跨实现。** 见 §2 的保真度。
3. **不主张快照跨版本。** 格式 version 1；改了字段就要升版并拒旧。
4. **不主张性能。** 4 MiB 裸写、每次恢复重扫 IR，未测。
