# 298 · LomentFaster：三档加速，一个开关

> 状态: **设计**（2026-11-04）
> 上游: `docs/212`（逃生舱：`extern fn` + `--link`）· `docs/226`（性能账）·
> `docs/259`（LVM T2 6.1×）· `docs/262` §10.1（关闭关键系统要带 `_admin`）·
> `docs/231`（`choose` 渠道闸的先例）
> 实测: 2026-11-03/04，WSL2 / Ryzen 9 7945HX / glibc 2.43 / Python 3.14.4 /
> rustc 1.93；源与脚本在临时 worktree 的 `bench/`，未提交。
> 一句话: **加速是一条 `choose` 维度的六个取值 —— 三档各带开/关；关档产出的字节必须与今天完全相同。**

---

## 0. 一句话展开

LomentFaster 不是三个可以叠着写的开关，而是**一个维度 `lomentfaster` 的六个取值**：

六个取值，一个程序写其中一个：

```rust
choose lomentfaster_C_close   // 默认：C 档关（基线）
choose lomentfaster_C_open    // C 档：把优化交给 C 工具链
choose lomentfaster_f1_close  // f1 关（基线）
choose lomentfaster_f1_open   // f1：Loment 自己做的标量优化
choose lomentfaster_f2_close  // f2 关（基线）
choose lomentfaster_f2_open   // f2：在 f1 之上加循环优化与向量化
```

`_open` = 这一档开；`_close` = 这一档关（走基线）。

`choose` 的既有规矩照旧：**每维全程序恰好一个取值，且只有根单元能写**（`tools/lomentc.py`
的 `CORE_DIMS` / `CORE_DIM_OF`）。所以"同时开 C 和 f1"这件事在语法上就不存在 ——
写两个值就是 E22「同一维写了两次」，报错会点名 `lomentfaster`。

**默认值 = `lomentfaster_C_close`**：默认档不改任何既有程序的字节。三个 `_close` 取值
语义相同（都是基线），保留三份写法是为了让"我明确关的是哪一档"在源里可读、在 Potato
形态对象里可查。它们**不带 `_admin`**：`docs/262` §10.1 要求的是"关闭关键安全系统"，
而这里关的是性能档，不是判决。

## 1. 三档各是什么

| 档 | 取值 | 优化由谁做 | 需要外部工具链 | 产物 |
|---|---|---|---|---|
| **C** | `lomentfaster_C_open` | clang（LLVM `-O3`） | 要（clang，ELF） | clang 直接编 IR 并链接 |
| **f1** | `lomentfaster_f1_open` | Loment 自己的后端 | **不要** | 仍是 lomelf 发的字节 |
| **f2** | `lomentfaster_f2_open` | Loment 自己的后端（f1 + 循环/向量） | **不要** | 仍是 lomelf 发的字节 |

### 1.1 C 档：现在就能兑现的那一档

做的事只有一句：**把 Loment 的 IR 交给 clang `-O3`，不再经过 lomelf 的未优化后端。**
机制已经存在（`--opt` / hosted 两条 clang 调用点）；缺的是"按 `choose` 走"，
以及 hosted 侧要把 `-O3` 显式补上（本机原型已验，见下表）。

实测（同一轮交替、7 次中位数、全部从 `/tmp` 执行、输出逐字节一致）：

| 任务 | lomelf 今天 | **C 档 `-O3`** | Python | rustc `-O3` | C 档 / Rust |
|---|---|---|---|---|---|
| 启动打印 hello | 1.05 ms | **1.00 ms** | 21.8 ms | 1.55 ms | 1.55× 快 |
| 100 MB 数行 | 127.4 ms | **111.3 ms** | 152.3 ms | 147.1 ms | 1.32× 快 |
| 10⁸ 素数筛 | 2927.6 ms | **782.5 ms** | 1094.9 ms | 742.4 ms | 0.95×（慢 5%） |
| 200 万数求和 | 238.4 ms | **39.3 ms** | 320.4 ms | 81.8 ms | 2.08× 快 |

**边界（照抄 `--opt` 的既有边界，不新发明）**：

- **ELF 侧有效；PE 侧明确拒绝**，不静默降级（`tools/lomelf.py` 对 `--target pe` + `--opt`
  的既有处理）。
- 找不到 clang 时**响亮降级**到 lomelf 并说明，不失败（与 `--opt` 同一条纪律）。
- C 档产物不是"Loment 自己的后端出的"，所以 `loment filetype` / 审计面要能区分；
  不能把它当 f 档的产物做字节比对。

### 1.2 f1 档：不依赖 clang 也能打平 Rust 的那一半

f1 是**标量优化**，只做四件事（顺序有依赖）：

| # | pass | 解决什么 |
|---|---|---|
| 1 | **mem2reg / SSA 构造** | 把局部变量从 `alloca` 提升成值。今天 lomelf 不做，筛法程序里有 **21 个 `alloca`**，每轮迭代的每次读写都是一条 `load`/`store` |
| 2 | **寄存器分配**（线性扫描即可） | 让值留在寄存器里，而不是每条指令都落栈 |
| 3 | **常量折叠 + DCE + 窥孔** | 去掉死代码与显然的常数运算 |
| 4 | **小函数内联** | Loment 的辅助函数多（`write_u64` / `load_u64` 一类），不内联就永远跨调用 |

**目标与依据**：实测 clang 各档（同一份 IR）：

| | `-O0` | `-O1` | `-O2` | `-O3` |
|---|---|---|---|---|
| 10⁸ 素数筛 | 1.24 s | **0.83 s** | 0.79 s | 0.77 s |
| 200 万数求和 | 70 ms | 40 ms | **30 ms** | 40 ms |

`-O1` 已经拿到 `-O3` 的 **94%**；`-O1` 里没有向量化，只有上表这四件事。所以
**f1 的目标是"≈ clang `-O1/-O2`"，也就是这批负载上打平 Rust** —— 并且产物仍然由
lomelf 自己发出，不需要任何外部工具链。lomelf 今天比 clang `-O0` 还慢一倍多，
差距主要在 1 和 2，不在高级变换。

### 1.3 f2 档：向量化与循环优化

f2 = **f1 的全部 pass** + 下面这些：

| pass | 目标 |
|---|---|
| 循环不变量外提（LICM）、强度削减 | 消掉循环里的重复地址计算 |
| 循环展开 / 旋转 | 给后续向量化创造形状 |
| **向量化**（`<N x i32>` 一类的向量 IR 或直接发向量指令） | 数值内核再拿 2–4× |
| 边界检查消除（复用 LMS 的 L0/L1 证明面，`docs/210`） | 带检查的代码不再为证明付运行时钱 |

**边界要说清**：在这批内存受限的负载上，`-O1 → -O3` 只值约 **7%**（上表）；
向量化的收益在**数值内核**（矩阵、图像、统计）上才明显。f2 不是"f1 的优化版"，
它是"另一类负载的优化"。

## 2. 组合、冲突与默认

| 写法 | 结果 |
|---|---|
| 什么都不写 | `lomentfaster_C_close`（基线，字节与今天相同） |
| 写两个 `lomentfaster_*` | **E22**：同一维写了两次，报错点名 `lomentfaster` |
| 在库文件里写 | **E22**：核心模式只能出现在根单元（既有规矩） |
| `f2_open` | 蕴含 f1：f2 的流水线里包含 f1 的全部 pass，不是"跳过 f1" |
| `C_open` | 走 clang，不经过 lomelf 的优化器；与 f 档不可能同时出现（同一维） |
| `C_open` + `no_std` | **允许**：`--opt` 那条路本来就是 freestanding（`-nostdlib`，三个 libcall 由链接步补） |
| `C_open` + `hosted` | 允许：hosted 本来就要 clang 读 IR，直接 `-O3` |
| `C_open` + PE 目标 | **明确拒绝**，不静默降级 |
| `f1/f2` + `no_std` | 允许：f 档不需要外部工具链，也不需要 libc |

## 3. 产物保证矩阵

| | `C_close`（三个） | `C_open` | `f1_open` | `f2_open` |
|---|---|---|---|---|
| 产物字节 == 今天 | ✅ 必须 | ❌ | ❌（预期变短） | ❌ |
| 需要 clang | 否 | **是** | 否 | 否 |
| 需要 libc | 否 | 看模式：sealed 不要（`-nostdlib` + libcall），hosted 要 | 否 | 否 |
| 双链接器逐字节一致 | ✅ | 不适用（不走 lomelf） | ✅ 必须 | ✅ 必须 |
| 自举种子需重算 | 否 | 否 | **是** | **是** |
| LSPE / LMS 判决 | 不变 | 不变 | 不变 | 不变 |
| 产物可复现（同源同字节） | ✅ | ✅（绑 clang 版本） | ✅ | ✅ |

两条硬约束：

1. **`_close` 是棘轮**：三个 `_close` 取值下，编译产物必须与今天**逐字节相同**。
   这条不是形容词 —— 它就是现有 `loment_elf_test` 的自举镜像那格在比的字节。
2. **f 档在两侧同时实现**：`tools/lomelf.py` 与 `loment/tools/lomelf.lomt` 的产物
   逐字节一致；改一条指令要两边一起改、重算种子（本机 12–14 分钟）。

## 4. 判据（不用墙钟比值）

仓库的既有规矩：**门禁不用墙钟比值**（同一个量在不同机器上能差 3–5×）。所以三档的
判据全部落在**确定性量**上：

| 档 | 判据 | 量 |
|---|---|---|
| 全部 `_close` | 同一程序、同一输入，产物与今天**逐字节相同** | 字节 |
| 语义 | 三档产物对同一输入**输出逐字节相同**（用现有端到端套件：行数 / 素数个数 / 求和） | 字节 |
| `f1_open` | IR 里 `alloca` 数 → 0（取地址的除外）；`load`+`store` 指令数相对基线下降（阈值先量基线再定） | IR 指令数 |
| `f2_open` | 向量 IR 指令数 > 0；且同一函数在 f2 下的 IR 指令数不高于 f1 | IR 指令数 |
| `C_open` | 产物要带**来源标记**（今天还没有，需要新增）；`loment build --check` 拒绝把 C 档产物当 f 档比 | 元数据 |
| 降级 | 没有 clang 时 `C_open` **必须报出降级**（stderr 一行），不静默 | 退出码 + 文本 |

端到端的实测数字（§1.1 那张表）**只作为证据与目标**，不进门槛。

## 5. 实装落点（"加一维只动这一处"的清单）

1. **取值表**：`tools/lomentc.py` 的 `CORE_DIMS` / `CORE_DEFAULTS` / `CORE_DIM_ZH`
   （同一张表还喂 `CORE_WORDS` / `CORE_DIM_OF`，所以只加一次）。
2. **自举侧**：`loment/selfhost/checker.lomt` 的同一张表；两侧对拍。
3. **形态对象**：Potato 的 form 记录这一维（"不看源码也能回答产物是什么"）。
4. **C 档**：`tools/loment_dist.py` 启动器的 hosted / `--opt` 两条 clang 调用点；
   `tools/lomelf.py` 与自举镜像的 PE 拒绝路径。
5. **f1 / f2**：`tools/lomelf.py` 与 `loment/tools/lomelf.lomt` 的优化流水线；
   两处逐字节一致；种子按既有纪律重算。
6. **文档与编辑器**：`.claude/skills/loment/SKILL.md` 的 `choose` 表、
   `editors/vscode/` 的着色词表（它按 `choose` 行上色，**不读** SKILL）。
7. **判据**：`loment_cli_test` / `loment_elf_test` / 一个新的 `loment_faster_test`。

## 6. 非目标与不可能性（先写死）

1. **C 档不是"远超 Rust"**。它只是把优化交给同一个 LLVM；实测对 rustc `-O3`
   几何平均约 **1.42×**（3 胜 1 负），不是数量级。任何"默认 clang"的承诺都不能
   说成"远超"。
2. **f1 的目标是打平，不是超过**。按 §1.2 的表，标量优化做到位就是 `-O1/-O2`
   的水平；在这批负载上这已经足够打平 Rust。
3. **f2 只在向量化负载上超过**。内存受限的循环（筛法）两边生成同一水平的代码，
   向量化帮不上忙。
4. **"远超"要靠运行期特化，不在本文三档里**。那是 `docs/259`（LVM T2 6.1×）
   那一线的事：按运行期才知道的形状/值重编译热函数，Rust 的 AOT 结构上拿不到。
   LomentFaster 的三档只解决"AOT 产物本身有多快"。
5. **默认值不改字节**。发行渠道若要默认 `f1_open`，走 `docs/231` 那条渠道闸的
   同一套机制（dev 通道默认开、正式通道默认关），不是在 `CORE_DEFAULTS` 里
   直接改数字 —— 那会让今天所有逐字节判据一起红。
