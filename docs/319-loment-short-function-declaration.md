# 319 · Tur 2026.3：函数声明去掉 `fn` / `def`（短声明）

> 状态：**设计（未实现）**（2026-11-09）· 版次：`tur2026.3`（未封顶）
> 上游：`docs/296` §5（Tur 3 的计划清单）、`docs/305`（2026.2 封版 / 2026.3 开版）、
> `docs/312`（默认 = 最新版次）· 判据落点（未来）：`loment_grammar_test`、
> `loment_p8_test`、`loment_fmt_test` / `loment_doc_test` / `lsp` 各自一条
>
> 一句话：**在 item 位置，函数名本身就是声明** —— `main() { … }`。
> `fn` / `def` 仍然能写（版次只加不改），但 2026.3 的规范写法不再带这两个词。

---

## 1. 问题

一份 Loment 源里，函数是**唯一**大量重复的条目。每写一个函数就要先付三四个字符：

```rust
fn add(a: u32, b: u32) -> u32 { return a + b; }

// 2026.2 起还可以写：
def add(a: u32, b: u32) -> u32 { return a + b; }
```

`def` 是 2026.2 加的糖（`docs/296` §2.1），它的存在让同一件事有了两种拼法。
默认版次切到最新（`docs/312`）之后，两种拼法会同时出现在一份代码里 —— 读者要
分辨"这两个词有没有区别"（没有），而答案只是**视觉噪声**。

**声明形状本身已经携带了全部信息**：在 item 位置，`名字(…) -> T { … }` 只能是函数。
`fn` / `def` 没有区分任何东西。

## 2. 提案：item 位置的短声明

在 **item 位置**，函数可以省略 `fn` / `def`：

```rust
module demo

pub add(a: u32, b: u32) -> u32 {
    return a + b;
}

main() {
    print_num(add(1, 2));
}
```

允许省略的位置（都是 item 容器）：

1. **顶层**：`pub` / 无修饰的普通函数、泛型函数 `f<T>(…)`；
2. **`impl` 块**里的方法；
3. **`trait` 块**里的方法签名（`m(self) -> R;`）；
4. **`register <名字> { … }`** 块里的条目（与顶层同一批条目）；
5. **`extern`** 声明：`extern puts(s: ptr) -> i32;`（`extern` 已经标了它是外部函数）；
6. **`interrupt`** 处理函数：`interrupt tick() { … }`。

**不允许省略的位置**：函数体内（那里是语句，`foo();` 是调用）、`struct` / `enum`
的字段、`capability` / `const` / `use` / `choose` / `module` 的取值位。

## 3. 为什么没有歧义

短声明只改**一个位置**的读法：item 的起点。

* item 位置**没有表达式语句** —— 那里的标识符本来只能是声明的名字。今天在顶层写
  `foo();` 会得到「未知顶层关键字 `foo`」；短声明把同一串 token 读成函数，不改变
  任何**本来合法**的源的含义。
* 函数体内部**不启用**这条规则。`while c { foo(); }` 里的 `foo()` 仍然是一次调用。
* `impl` / `trait` / `register` 块里没有别的"裸标识符条目"：别的条目都以关键字
  开头（`fn` / `const` / `struct` / `use` …）。
* 泛型函数写成 `f<T>(…)`：item 位置的 `标识符 <` 也只有这一种解释。

因此这条改动**不需要进 `EDITION_COLLISIONS`**（`docs/312` 的那张表针对的是"新语法
复用旧标识符"）。这里没有新词，只有一个**原本是语法错误**的位置被赋予含义。

## 4. 与版次的关系：只加不改

* 短声明**只在 `tur2026.3` 及以后**被接受。`tur2026.1` / `tur2026.2` 仍然要求
  `fn` 或 `def` —— 两个封版版次的读法一个字节都不动。
* `fn` / `def` 在 2026.3 里**继续接受**，语义与短声明完全相同。不允许删除它们：
  那会让所有旧源在新默认下失效，正是 `docs/312` 花力气避免的那种断裂。
* 默认版次已经是最新（`docs/312`），所以新文件不写声明就自动得到短声明。

## 5. 与 `def` 糖的关系

`def` 是前门的**等长改写**（`potato_from._tur2_sugar` / 自举 `tur2_sugar`）：
`def f(` → `fn f(`。这条改写**不改**：

* 短声明与 `def` 是两条独立的路，最终都得到同一个 `Func` 节点；
* 2026.3 的新代码不写 `def`；`def` 留作"旧写法仍能编"的兼容面，不在这一版弃用。

**可选**（待裁，见 §10）：2026.3 的 `def` 给一条**提示级**诊断（"可以用短声明"），
但绝不能是错误。

## 6. 两个实现怎么落

### 6.1 参考实现（`tools/lomentc.py`）

`Parser.parse_items` 已经按 item 逐个分派。短声明只需要在**最后那个 `else` 之前**
加一支：

* 当前 token 是标识符，且下一个 token 是 `(` 或 `<`；
* 版次是 2026.3+；
* 调 `parse_fn(implicit=True)` —— 它不消费 `fn`，直接把当前标识符当函数名。

同样的 `implicit` 开关接到：

* `parse_impl`（方法）；
* `parse_trait`（方法签名）；
* `parse_items` 的 `extern` / `interrupt` 分支。

`parse_fn` 目前以 `kw = self.expect("ident", "fn")` 取行号；`implicit` 时用**名字
那一行**（诊断仍指得准）。

### 6.2 自举实现（`loment/selfhost/*`）

自举侧的 checker / codegen **没有 AST**：它们靠 token 流里的 `fn` 定位函数，并且
约定 `fn` 在 `i`、名字在 `i+1`、`(` 在 `i+2`（`parser.lomt` / `codegen.lomt`
里十几处）。两种落法：

* **（推荐）装载期注入一个合成 `fn` token。** `driver.load_file` 把每个文件的
  token 拼进单元流；在**拼接时**对 item 起点的短声明先写一个合成 `fn`、再写名字。
  下游所有扫描一行不改，`i+1` / `i+2` 的约定继续成立。合成 token 只携带
  `kind=ident, len=0` 与名字的 `start/line/col`，不占用源文本。
* 逐个改那十几处扫描点。不推荐：它们分散在 parser / checker / codegen 三处，
  每处都要重新判断"这是不是 item 起点"，漂移风险远大于注入。

**判定 item 起点**用一个小状态机（顶层 / `impl` / `trait` / `register` 是 item
容器，函数体是语句容器），与参考实现 `parse_items` 同一张表。它是这份设计里唯一
新增的"扫描"，必须两边对拍。

### 6.3 生成物

自举侧一改，种子必须重算（`loment_seed.py --emit`），并按 `CLAUDE.md` 的纪律
**单独一条 `[生成物]` 提交**；genesis 与 `docs/270` 的地板数跟着重算。

## 7. 消费者（`docs/182` §1.9 那张清单）

读 L1 源的入口不止编译器。短声明落地时，每个入口各要一条判据：

| 入口 | 要做什么 |
|---|---|
| `loment fmt`（`lomfmt.lomt`） | 识别 item 起点的短声明；缩进/格式不能把它当表达式 |
| `loment doc`（`lomdoc.lomt`） | `///` 注释要能挂到短声明的函数上 |
| LSP（`lsp.lomt`） | 补全/跳转/大纲要列出短声明的函数；**它今天不读版次**（#262），要么补版次读法，要么用"item 起点"判定 |
| 报错器（`lomenterr.lomt`） | 只看声明行的定位逻辑不受影响；短声明"没有那一行"要如实处理 |
| VS Code 语法 | 函数名上色/大纲；TextMate 规则可不改，但要有判据说明"不改也不会错色" |
| `lomgrammar.lomt` | 只扫 `choose write grammar`，不受影响 |

**建议**：编译器与两个实现先落，消费者按"每条入口一条判据"分批跟；没跟上的入口
在清单里**显式记一笔**，不要让它静默半懂。

## 8. 判据（实现时）

1. **版次门**：`tur2026.3` 收 `main() {}` / `pub f()` / `f<T>()`；`tur2026.2` 与
   `tur2026.1` 在同一位置**拒**（封版不动）。
2. **同义**：同一份程序的短声明、`fn` 版、`def` 版在 2026.3 下 IR **逐字节相同**
   （版次元数据相同，因为版次没变）。
3. **位置**：函数体里的 `foo();` 仍是调用；`struct S {` / `use foo;` /
   顶层 `foo;` 的读法不变（最后一条仍是错误）。
4. **孪生**：参考实现与自举驱动对上述正负例的收/拒与产物一致（M 系列新增一条）。
5. **门禁**：`loment_grammar_test` / `loment_p8_test` 的判据数与地板同步抬（双向棘轮）。

## 9. 明确不做

* **不删除 `fn` / `def`**：封版版次仍要用它们；2026.3 里它们也照常接受。
* **不在函数体内启用**：那会把调用读成声明。
* **不引入新关键字或符号**（`def` 已证明"两个词"只会增加噪声）。
* **不改默认版次与碰撞表**：这两件事在 `docs/312` 已经定了。
* **不顺手改仓库全部示例**：先把语言面落地，示例批量迁移是另一笔（见 §10）。

## 10. 待裁

1. `trait` 的方法签名、`extern`、`interrupt` 是否一起放开？
   **建议：是** —— 它们都是 item 位置，规则一致比"只放开一半"更好解释。
2. `def` 在 2026.3 是否给提示级诊断？
   **建议：先不给**。先把短声明落地；提示会制造一批"每次编译都有"的噪声。
3. 仓库自己的示例（`loment/examples/`、skill 里的样例）什么时候迁移到短声明？
   **建议：语言面落地后的单独一笔**，按"示例即规范"逐目录改，并保留 `fn` 版对照。
4. LSP / fmt / doc 是在同一笔里跟，还是各自开 issue？
   **建议：fmt 与 doc 同一笔**（它们只换扫描规则）；LSP 单独一笔（它没有版次读法，
   要先补 #262 那一格）。
