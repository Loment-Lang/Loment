## 1. 语言面：新增四样

### 1.1 `set choose <名字> { <代码> }` —— **一个名字，没有 `at`**

用户原话：**"彻底修复 choose 问题与 set choose 问题，而且可以出现至少 500 次"**。

**第一版（`set choose <取值> at <名称> [lock] {…}`）有两个名字，是错的**，实测撞出来三条：

1. **两个名字没有任何消歧规则**：同一个名称被两个取值定义算谁的？同一个取值配两个名字算不算
   同一个开关？用户自己说名称"没有特殊意义" —— 那编译器**为什么需要第二个名字**？
2. **`choose <开关名>` 被两条既有 E022 规则直接禁止**（下面 §1.6 有实测）。
3. **`close` 抢走了一个词** —— 用户从此不能给开关起名 `close`。自定义机制里不该有这种限制。

**定稿**：

```
set choose <名字> { <开关打开时才编进去的代码> }
```

- **`<名字>`** 必须是名字（用户原话："只管'不能是数字或符号'"），与既有标识符规则一致，
  **不新增词法约束**。
- **`{ <代码> }`** —— 开关**打开时**才存在的东西。**空体合法**（有些开关只驱动编译器行为，
  见 §1.5）。

### 1.2 `choose <名字>` / `choose close <名字>`

打开 / 关闭。`close` 是**上下文词**，只在 `choose` 后面有意义，**不算关键字**。

**一个文件里 `choose`（含 `set choose`）的条数上限 ≥ 500**（用户 2026-09-17 定）。
这与 `use` 的 300 条上限（`MAX_USE`）是同一种保护：**超限报错，绝不静默丢**。

### 1.3 `std` / `no_std` 是**核心硬写法**，不是用户开关

用户原话："**`no_std` `std` 是硬写法，是 Loment 核心语法不可动，未来官方写入的 choose 也是硬写法**"。

⇒ 它们**不走** `choose <名字>` 那条路，**保留自己的语法与规则**。所以 §1.6 里那条
"模式只能是 `std`/`no_std`" 的规则**原样保留** —— 它管的是**核心模式**，不是开关。

### 1.4 `addin <名字>` + `chooseset.lomt`

用户原话："**`addin` 是全新语法，未来 Loment 基础语法系统一部分，与 `choose` 一样**"。

- `addin <名字>` 是**新的顶层语法**，与 `choose` 同级。
- `chooseset.lomt` 内**只能写 `choose` 相关代码**，且**开头要写 `addin chooseset`**。

**它与 `use` 的差别（`addin` 存在的理由）**：`use` 拉进来的是**库**，而库**不许 `choose`**
（E022 第三条，落在装载器 `driver.lomt:708-719`，按 `depth>0` 拒）。`addin` 拉进来的是
**一份开关设定**，它的 `choose` **就是要在整个程序生效的**。两者方向相反。

**⚠️ 这一步依赖"装载器预扫"（§1.6 问题②）**，所以排在核心之后 —— 见 §1.7 的分步。

### 1.5 它**驱动什么**（"插槽要插上插头"）

另一位 2026-09-17 的判词，**核实过是对的**：

> `choose` 到今天为止什么也不驱动 —— `mode` 一直被校验、进 Potato v2、被回放。**有形状没有
> 用处的构造是承诺，不是发明。** 它现在的位置，很像一个设计得很好的插槽，但**插头是空的**。

统计口径（实测）：`loment_build.py` 里 `mode`/`choose`/`no_std` **零命中**；
`lomelf.py` 命中的 `mode` 全是 POSIX `openat(..., mode)`；没有任何一行按它分支。

**要插上的三个插头**（前两个**今天就能插**，不需要跨线契约）：

| # | 插头 | 今天 | 谁消费 |
|---|---|---|---|
| 1 | **代码裁减** —— 开关状态决定 §2 那段体编不编进去 | 无 | 两个实现的**解析/检查/codegen** |
| 2 | **依赖门槛** —— 关着时体内引用的外部符号**不需要存在** | 无 | 装载器 + 检查器 |
| 3 | **二进制开关** —— 能不能链外部二进制（`docs/183` V5） | 无 | 链接器 |

**为什么前两个是"今天就能插"**：`no_std` 要驱动"哪些 L0 原语可用"，而那要 `lom/*.lom` 带
freestanding/hosted 标记 —— 那是 `docs/176` 的 **B0**，卡在跨线冻结契约上（`docs/180` §86-97
"不替对方猜"）。**但开关的代码裁减不需要它** —— 它完全是语言内部的事。

⇒ **这就是把"承诺"变成"发明"的那一步**：先让 `choose` 有一个**不依赖任何外部前提**的真消费方，
而且**有判据**。

### 1.7 分步（每步独立可交付 + 判据）

### 1.8 C1 的判据（每条都要能证伪）

- **裁减真生效**：开关**关着**时 —— 语义错**不报**、**语法错照报**（§2 那两行各一条判据）；
  关着时体内引用的符号**不需要存在**。
- **开着时照常**：同样的源，`choose <名字>` 打开后那段**编进去且错误照报**。
- **两个实现一致**：同一份源，参考与自举的码集相同（进 `loment_rule_parity._CASES`，
  预算上调）。
- **≥500 条**：写 500 条 `choose` 能过；写到上限之外**报错**（不静默丢）。
- **`std`/`no_std` 不受影响**：既有三条 E022 在核心模式上的行为**一字不变**
  （`choose-twice`、`choose-bad-mode` 两条既有用例必须继续过）。

### 1.9 C1 落地时撞到的两条真缺陷：**同一个语义，消费者清单是空的**

两条的形状不同（一条"被上游盖住"、一条"根本不在视野里"），但根因是同一个：
**"读 L1 源"这件事没有唯一入口，于是每加一个语法构造，就有一处会漏。**

#### 1.9.1 `switches.lomt` 的依赖声明被上游盖住

`switches.lomt`（C1 新加的模块）初版**没有 `use bytes`**，而它通篇调 `load32`/`store32`。
模块头注释里我还写着"**零依赖**（只用语言内建的 `load8`/`load32`/`store32`/`str_ptr`/`str_len`）"。

**那句话是假的**：`load32`/`store32` 不在 `lomentc.BUILTINS` 里，它们是
`loment/examples/bytes.lomt` 里的 `pub fn`。

**为什么一路是绿的**：`checker.lomt` 与 `lomdoc.lomt` 都写了 `use bytes`，而符号解析在
**单元**层面（依赖 + 本模块）做 —— 于是 `switches` 里那些调用被**上游**的 `use bytes`
盖住了。整条自举链、`lomentc_test`、`loment_rule_parity` 全部放行。

**谁抓住的**：`test_m85_checker_accepts_corpus_units`。它把每个 `.lomt` 当**拼接单元**看。
第一次红是另一个形状（`未知顶层关键字 'set'`，夹具绕过了 `lomentc.load` 的开关摊开），
修完立刻露出这一条：`switches.lomt: 单元上有假报 [2] 2@58:load32 …`。

**两边一致，所以不是检查器缺口**：`python tools/lomentc.py --check loment/selfhost/switches.lomt`
在参考实现下**报同样的 43 条**"调用未定义的函数 `load32`"。是文件错了，不是尺子错了。

**修法**：加 `use bytes`，并删掉那句没被任何判据验证过的"零依赖"承诺。实测这条依赖
**一个新环节都没加** —— `checker`/`driver`/`lomdoc` 的依赖集合加不加这一行完全一样
（`bytes` 本就在每条用 `lexer` 的链上）。

**顺带补上判据的覆盖面**：本判据原先只 glob `loment/{examples,selfhost}`，
**`loment/tools/` 没有被任何判据按单元看过**。已加入。加之前先量过：12 份
`loment/tools/*.lomt` 在参考实现下当单元看**都是零诊断**，所以这不是把尺子放宽。

**这一条与 `docs/176` 的"承诺不是发明"是同一件事的第二个实例**：注释里写的性质
（"零依赖"、"只用内建"）如果不被一条判据钉住，它就只是一句话。不同的是这次的
"承诺"是我自己写的，而且**写反了**。

#### 1.9.2 语言服务：**根本没在任何一条尺子的视野里**

`lsp.lomt` 是"读 L1 源的东西"之一，但它
拿 `lex` 的原始 token **直接**喂 `run_check` / `scan_syms`，四处调用点**都没有**落定开关。
后果不是报错而是**报假错**：在编辑器里打开一个带 `set choose` 的文件，关着的那段照样被
检查；体里定义的 `fn` 还会进补全与跳转。

它被漏掉的原因和上面是同构的：编译链的判据（`lomentc_test` / `loment_rule_parity` /
`loment_seed_test` / `loment_p8_test`）**全部不经过语言服务** —— 那是独立进程、独立入口。
所以这一处不是"被上游盖住"，是**根本没在任何一条尺子的视野里**。

修法：`lsp.lomt` 四处 `lex` 之后各接一次 `switchify`（`apply_switches` 的薄封装，
表放在 `mem` 块末尾并显式撑大 `MEM_CAP` —— 塞进 `SCR_OFF` 那段会和行缓冲抢地方，
越界是静默改坏）。判据：`loment_lsp_test::test_lsp_check_honours_switches`
（关着 -> `--check` 一声不吭；`choose` 打开 -> E002 照报）。

**而且语言服务是两份实现**。`tools/loment_lsp.py`（VS Code 扩展的默认后端、`loment lsp`
的实现）同样绕过了 `lomentc.load`，同样漏了开关 —— 它是**第二个**独立入口。已一并修
（`_parse` 里补落定），判据 `loment_lsp_test::test_python_lsp_also_honours_switches`，
不依赖 clang/WSL 所以永远会跑。**修了自举那份不等于修了这份**。

**这一轮撞出、但按纪律不顺手修的（如实记着）**：

1. **两份语言服务的诊断字段不一致**：自举版吐 `code`（`E0NN`），Python 版
   `_diagnostics` 只给 `range`/`severity`/`source`/`message`，**没有 `code`**。
   从没被判据碰过 —— 既有判据只对自举版断言 `d["code"]`。新判据因此按**消息内容**
   断言，不假装 Python 版有 `code`（也不顺手把它掩盖过去）。
2. **两份语言服务都不做预置枚举注入**：`lomentc.load` 会补 `Option`/`Result`，
   而两个 LSP 的解析入口都不走 `load` —— 于是语言服务至今不认识这两个枚举。
   与开关同源（绕过 `load`），但**后果不同**（不会报假错，只是漏补全），
   所以不在这一轮的范围里。真修法是让 `lomentc` 出一个公开的
   `parse_source(text)`，两个 LSP 与 p8 夹具都走它 —— 那是一次独立的重构。

**这正是 `docs/158` §5 那条"别只看一条判据"的第二个面**：那一条讲的是"同一个实现的两侧"，
这一条讲的是"同一个语义的**不同消费者**" —— 消费者的清单和判据的清单必须一起长。

**边界（不是遗漏，是划出来的）**：`loment/tools/lomc.lomt` 也 `lex` + 解析，但它编的是
**L0 `.lom`** —— 而 `set choose` 是 **L1 构造**。依据：参考实现 `tools/lomc.py` 里
`choose`/`switch` **一个字都没有**（L0 面根本不认识这个语法）。所以它**不在**消费者清单里。
`lomfmt` 相反：它格式化的是 `.lomt`，所以它得认识这两个关键字（且**故意不做裁减** ——
格式化器把关着的那段删掉是错的；它只用关键字表把结构认对）。

### 1.10 C2 落地：`addin` + 预扫（`docs/182` §1.4/§1.6 ②/§1.7 的实现记录）

**§1.6 ② 那个鸡生蛋真的存在，而两个实现踩的是**不同**的坑。**

| | 参考实现（`tools/lomentc.py`） | 自举（`loment/selfhost/`） |
|---|---|---|
| 装载模型 | **逐模块**：每个文件各自 `load()`，再 `mods = deps + [mod]` | **先拼成一整块**：`load_file` 把 use 依赖递归写进同一个 `unit` 缓冲 |
| 所以鸡生蛋 | **存在** —— 根的 `choose` 要按名字找的 `set choose` 定义在还没读到的单元里 | **不存在** —— 拼完之后所有 `set choose` 都在同一块 token 流上 |
| 所以预扫 | **必须显式做一趟**（`prescan_switches`） | **隐含在"先拼后落定"里**，不需要单独一趟 |

⇒ **`docs/182` §1.7 把 C2 叫"跨单元"是字面意思**：`addin` 拉进来的单元**本身参与编译**
（`set choose X { … }` 的体是**代码**，X 开着时那段就是程序的一部分）。所以体里给根用的
函数要 `pub` —— 它仍然是一个模块。

**§1.9 那根"消费者"轴又一次咬人。** 预扫要把 `load` + `resolve_deps` **一起**用，而仓库里
**八处生产代码各自手拼过这两个调用**（`loment.py` / `lomdoc.py` / `loment_build.py` /
`loment_diag.py` / `loment_ir_diff.py` / `loment_boot.py` / `loment_bootstrap.py` /
`lom_audit.py`）。手拼的版本**少了预扫那一趟**，于是 `addin` 白写 —— 症状是
"未定义的开关"加上 `addin` 目标**根本没进单元**，而编译链的判据**全绿**。

⇒ 新增**唯一入口** `lomentc.load_unit(path, root)`（预扫 → 装载 → 解析依赖），八处全部改走它。

**两个新的硬错误，都不许静默：**

- **嵌套开关声明**（`set choose A { set choose B { … } }`）：`B` 算不算数取决于 `A` 开没开，
  而 `A` 的状态正是这一步要算的东西 —— 放开它就把状态变成**求不动点**。
  **必须在摊开之前判**（摊开之后"体里的"与"顶层的"在 token 流上分不开）。
  判据是**声明形状**而不是词本身（`set`/`choose`/`addin` 都不是保留字，`fn set()` 合法）。

## 2. 开关**关着**时，那段代码走到哪一步

用户原话："**关掉也会被检查语法，你都写了一定要为写了付出代价，但无需被解析因为入口是关闭的，
解析跳过这段代码**"。翻成本仓的三段管线：

| 阶段 | 关着时 | 说明 |
|---|---|---|
| **词法** | **照做** | 非法字符、未闭合字符串照报 —— 这是"为写了付出代价" |
| **花括号配对** | **照做** | 不配对会让整份源结构塌掉，挡不住 |
| **解析（建 AST）** | **跳过** | 用户原话 |
| **语义检查** | **跳过** | 关着时它引用的东西**不需要存在** —— 这才是"关掉 = 不依赖"成立的条件 |
| **codegen** | **不产出** | 编译期裁掉 |

**关键后果**：解析要跳过一段代码，就得**在那之前知道开关状态**；而 `choose` / `set choose`
可能写在后面 ⇒ 这个状态只能在**装载器**里定（根单元的开关决定，装载每个单元时套用）。
这正是 `docs/176` §7.3 预言的那一层："找不到落点的那条规则，多半会落到装载器层"。
既有先例就是它：**"库不许 `choose`" 落在 `driver.lomt` 的 `load_file`**，不在 checker。

**代价（如实记）**：关着时那段里的**语义错**看不见。这是 `#[cfg]` 类语义的固有代价。

## 3. `lock` 与解锁

- **`lock`**：把这个开关定义**装进本机**，之后任何项目都能 `choose` 它而不必重写 `set choose`。
- **状态放哪**：**用户目录**（用户原话："2，卸载需要同时卸载掉这个文件"）。
  ⇒ 与之配套的规矩：**卸载脚本要把这个文件一起删掉**。
- **解锁**：写一份 **`chooseunlock.lomlock`**，里面是 `unlock choose <取值> <名称>`。
  用户原话："去用 chooseunlock.lom 文件写入 … unlock choose <取值> <名称>"，
  随后改用新后缀：**"我们直接写个新后缀，现在新建 `.lomlock`"**。
  **后缀一分开，L0 契约面一个字节都不用碰** —— `lom/fuai.lom` / `fuc.lom` / `fujr.lom`
  照旧（`CLAUDE.md` 第 1 条，跨线协作唯一的支点）。

### 3.1 ⚠️ 锁定与"逐字节一致"那套文化冲突，必须给一条出路

锁是**本机**的，而本仓的整个身份是"同一份源 → 同一串字节"（seed / `_CASES` / 自举镜像）。
**锁住之后，同一份源在两台机器上会编出不同的东西。** 不处理这件事，CI 与开发机会给不同结果，
而且**红得没有道理**（判据不知道有锁存在）。

**必须定一条**（我倾向第一种，但这条要你点头）：

1. **判据与 CI 显式忽略本机锁**（一个开关，比如环境变量 `LOMENT_NOLOCK=1`，或判据跑在干净用户目录下）
   —— 锁是"本机偏好"，不是"语言语义"。
2. 锁**只影响开关的默认值**，源码里显式写的 `choose` **永远能覆盖它**。
   （这条与"锁定"的字面意思冲突，但它让锁退化成"默认值"，就不再破坏可复现性。）
3. 接受不可复现 —— 如实记在文档里，不再管。

## 5. 结构化诊断

用户定了：**"编译器/驱动先吐结构化诊断"**。这是 `lomenterr` 的输入前提，也是本设计里
**唯一落在既有输出面上**的改动。

现状（实测）：`check()` 吐 `list[str]`，形如 `"<行>: <文本>"`（**只有行，没有列**）；
词法/解析/装载期是 `LomError`，形如 `"<行>:<列>: <文本>"`。**两者都是裸文本，无码、无字段。**

**优先复用既有形状，不新造**：
- `loment_diag.py:189-191` 的 `--json`：`{"diagnostics":[{code,title,message,hint}], "foreign_note":…}`
- 自举 `lsp.lomt:364-402` 的 LSP Diagnostic：多一个 `"code": "E<nnn>"`

**吐到哪（我的决定，你不同意就说）**：**另给一条路径**（`--diag-out PATH`），每行一条
JSON（JSONL），由调用方传路径进来。理由：stderr 上混两种格式，解析方要"嗅"，而本仓一贯
反对"嗅"（`docs/179` §6 那条 `clang` 按后缀认语言、rc=0 却什么都不产出，就是这个坑）。
另开 fd 在 PE/POSIX 上语义不一致，路径最稳。

**字段**（`lomentc.DIAG_FIELDS`）：`file / line / col / code / title / message / hint`。

### 5.1 顺带撞出：分类表的**覆盖缺口**（已修）

做这一步时立刻撞见一件事：**`loment_diag.RULES` 只覆盖了 `check()` 的消息**，

**为什么一直没人看见**：判据 `test_m64_all_reference_messages_are_classified` 用 ast 抽模板时

### 5.3 `title`/`hint` **不由编译器出** —— 归报错器（这一条把上面简化了）

写 §5.2 时先想的是"让自举驱动也吐 `title`/`hint`"，那要求驱动手里有那张表。**但那个靶子本身是错的**：

**两个实现的消息文本本来就不同**。参考实现的 `check()` 吐的是整句中文
（`使用未声明的变量 x`），自举手里只有 **码 + token 索引**（片段是源码里那几个字节）。
`docs/158` §4 早就把这类分叉记在案上；`loment_rule_parity` 测的是**码相等**，不是文本相等。
⇒ **"两侧 JSONL 逐字节一致"不是一个诚实的靶子**，硬凑它只会造出一堆假一致。

诚实的靶子是**码一致 + 形状一致**。于是渲染这件事该归谁就清楚了：

| 谁 | 出什么 |
|---|---|
| **编译器**（两个实现） | `file / line / col / code / message` —— **码 + 位置 + 原文片段**，不解释 |
| **报错器 `lomenterr`** | 拿 `code` 去 `surface_data` 查 **标题 + 建议**，渲染给人看 |

**好处**：自举驱动**根本不需要那张表**（它只吐码），第三份手抄从设计上就不存在；
而"渲染"归报错器，本来就是它该干的事。`surface_data` 只服务两个消费者：`lomenterr`
（中文标题/建议）与 `lomcli`（ASCII 一行式，它那 24 条手抄删掉）。

**因此 §5 里 `DIAG_FIELDS` 的 `title`/`hint` 已挪走**：现在是
`("file", "line", "col", "code", "message")`，编译器不填标题/建议，由 `lomenterr` 补。
**两个实现共用这一份形状** —— 自举驱动那边因此**根本不需要那张表**（它只吐码 + 位置 +
源码片段），第三份手抄从设计上就不存在。

### 5.4 自举驱动那一侧（已做完）

`loment/selfhost/driver.lomt` 加了 `--diag-out PATH`：

- **必须在取 `argv[0]`/`argv[1]` 之前解析** —— `argv_at` 每次都重写同一块 `argv_buf`，
  而 `ap`（入口路径）是指进那块缓冲的指针，顺序反了内容会被抹掉；
- **写打开要走 `syscall6`** —— Linux 的 `openat` 是 4 参系统调用（`dirfd, path, flags, mode`），
  既有的 `open_ro` 用 `syscall4` 只递得到 rdx（flags）。带 `O_CREAT` 时 r10 里的 mode
  递不过去，文件会被建成权限 0。这是本仓第一次用 `syscall6`；
- **JSON 转义是必须的**：片段是**源码原文的字节**，里面有 `"`/反斜杠/控制字节就会写出非法
  JSON，下游整行解析失败。控制字节走 `\u00XX` 而**不是**替换成空格 —— 替换是悄悄改内容；
- 判据 `loment_p8_test::test_m85_driver_emits_structured_diagnostics`：字段集与参考一致、
  **码集与参考相等**、有错退非零、无错时**存在且为空**。

**途中撞到一条真实分叉，已记进 `docs/158` §4 第 12 条**：参考实现**接受关键字做标识符**
（`fn` / `if` / `let` 都能当形参名），而**自举 checker 撞上会错位** —— 参数位置的 `fn`
被当成"又一个函数声明"的起点，于是几十行之后报一条毫不相干的假阳性。我给形参起名 `fn`
时踩到（`test_m85_checker_accepts_corpus_units` 报 `2@65173:",\"line\":"`，而那个 token
与 `fn` 毫无关系）。**现在的绕法是改名**；根因的正确修法是**参考实现拒**（关键字不许做
绑定名），那是一次语言面改动。

- **找不到时**：落到内置报错器，**但要说出来** —— 本仓那条"**静默才是敌人**"（`docs/179`:113-115）。
  不能悄悄换掉用户以为在用的东西。

## 7. 边界（C2 落地时划清了）

**`addin` / `chooseset.lomt` 与 `loment.conf` 的边界 —— 已划，不合并。**

（这一节原先写的是"**现在没划**，会在有人两处都写的时候出事。我在实施时**先按'划清'写**"。
C2 落地时按那句写下来了，这里把结果记明白。）

| | `loment.conf` | `chooseset.lomt` / `addin` |
|---|---|---|
| 回答的问题 | **工具链怎么读源码** | **程序怎么编** |
| 今天认什么 | `source_ext`（唯一的标签） | `module` / `addin` / `set choose` / `choose` |
| 谁读它 | 词法器（`_conf_ext_from_tokens`，**不是**解析器） | 装载器预扫（同一种读法） |
| 换了会怎样 | 名字形式 `use` 找另一个后缀 | 开关的开/关状态变了 |
| 作用域 | 一个项目一棵目录树 | **一个程序**（`addin` 只在根单元） |

**为什么不能合并**：前者是**工具链**的输入（换掉它，同一份源码照样编，只是文件名不同）；
后者是**程序**的一部分（换掉它，编出来的程序就不是同一个了）。混在一个文件里，就再也分不清
"改了它会不会改变产物"。

**这条边界在 `docs/183` 的 S4 会更有用**：那里的"语法预扫"也属于"**工具链怎么读源码**"，
所以它落在 `loment.conf`（加一个标签），**不是**落在 `chooseset.lomt`。现在的划法正好接得住。

**唯一还没定的**：`loment.conf` 今天只认 **一个**标签（`_conf_ext_from_tokens` 是"找第一个
字符串就返回"）。加第二个标签（语法预扫）时那个读法要改成"认标签名"，而**两个实现必须一起改**
—— 那条钉在 `lomentc.py:2204-2207` 的注释里。

### 10.2 三条实测出来的细节（都不是猜的）

1. **未知码的判据是"查出来的标题空不空"，不是"码号解没解出来"**。第一版按 `cnum == 0` 判，
   而一份码 `E042` 能解出数字 42、表里却没有 ⇒ 标题空着、**建议被静默丢掉**。实测的输入
   （`{"code":"E042"}`）把这条逼出来了。现在标题/建议两边都按**返回值长度**判，
   未知码明说"这个码不在表面数据表里"。
2. **`n_codes()` 是条数，不是最大码**。两个消费者拿它当上界用，那只有"码从 1 起连续编号"
   时才对。第一版 `codes` 循环写 `< n_codes()`，**E23 当场消失**（判据抓到）。
   这条不变式现在有判据钉着（`loment_tools_test::test_code_tables_cover_the_same_codes`）。
3. **启动器必须吞掉驱动的 stderr**：实测语义错时自举驱动**既**打裸行到 stderr **又**写 JSONL
   （`fujoc-s: 静态检查未通过 / E2 @11 line 4: z`）—— 不吞就会把同一件事说两遍。而**装载失败**
   （文件不存在）只打 stderr、JSONL 是空的 ⇒ 吞掉之后必须原样回吐，否则那条消息就没了。
   四种组合都有判据（桩驱动，`loment_err_test::test_launcher_renders_with_it_and_says_so_without_it`）。

**如实记的代价**：标题/建议是中文，Windows 控制台按 936 解 UTF-8 ⇒ 乱码（PE 垫片没有
`WriteConsoleW`，程序侧无从补救，`docs/169` §3a）。诊断这条路上本来就是中文的
（`loment diag` 与编译器的 `[ERR]` 都是），所以不做特殊处理，也**不**因此把标题换成英文
—— 那是另一个受众的事，由 `loment codes` 走 `code_ascii` 提供。

### 10.3 两侧一致（`docs/158` §5 的口径）

`cmp` 实测：同一份源，参考实现与自举编出的 `lomenterr` IR **逐字节相同**（205453 字节）；
自举产物链出来的 exe 跑出的渲染与参考侧一致。`lomcli` 加了 `use surface_data` 之后同样
逐字节相同（编它的是 stage1，所以这条是**包**能不能编出来的直接证据）。

判据：新增 `tools/loment_err_test.py`（7 条，已进门禁）；`loment_cli_test` 的两条改成
**从真源推导**（`codes` 扫全部码并核对说明文字、`explain` 的边界从 `max(ASCII_ONE_LINER)`
算）—— 硬编码 23 那种写法在下一个码加进来时只会静默过期。

### 10.4 运行时那一半：**推迟**，卡在两处未定（不是技术上做不到）

§6 的第二半（同一份源码链进程序、给 trap 渲染、`choose close lomenterr` 决定编不编）**没做**。
可行性核过是通的 —— PE 垫片有 `GetStdHandle` / `WriteFile`（`lomelf.py:1203-1205` 的
`PE_IMPORTS`），fd 2 有映射，inline-asm syscall 是既有 IR 构造（`lomelf.py:579-580`）。
卡住的是两条**设计**，得先定：

1. **官方开关的默认值与现语义冲突**。`choose close lomenterr` 字面上隐含"默认开"，而
   `SwitchTable.state` 是"没写就是关"（`lomentc.py:772-775`；自举 `switches.lomt:132-152`
   的 `sw_find` 返 2）。今天**没有**官方开关机制 —— 只有 `std`/`no_std` 被按**字面名**特判
   （`lomentc.py:758-760`、`:826`、`:993`、`:1175` 等约六处 + 自举三处），没有表可加。
   另一条路是随包发 `chooseset.lomt`，但**极性反了**（用户得写 `choose lomenterr` 才开），
   而且同名两个取值本身就是 E022（`switches.lomt:287-307`）。
2. **同一个 `__loment_abort` blob 就是内核运行时**。`docs/155:70-73` 承诺内核不需要 libc，
   那三个 `__loment_*` 是 inline 的 ⇒ 在里面**无条件** `write(2, …)` 在内核里是错的。
   所以带写的那一版必须**受开关控制**才编出来。
   连锁面：这个 blob 两个实现各一份（`lomentc.py` 的 `_IR_RUNTIME` 与 `codegen.lomt:4254`
   的 `emit_runtime`）且要逐字节一致；`__loment_abort` 有 **8 个调用点**（Python 4 + 自举 4）；
   而**开关状态今天到不了 codegen**（`emit_llvm`/`emit_module` 从不读 `mod.switches`，
   代码裁减只发生在装载器里）—— 那是一类**新的消费者**。

⇒ 这一半要单开一轮，并且开头就得把上面两条定下来。

## 11. 报错器再进一步：说明卡 + 外源语言的衔接（2026-09-18）

用户 2026-09-18 定：**每一条都要非常明确地指出「错了什么 / 为什么错 / 如何解决（至少 3 种方案）/
什么不支持什么支持」，并且与六语言方言翻译那条线做到内容衔接。**

### 11.1 每个码一张说明卡

`tools/loment_diag.py` 里新增 `CARDS: dict[int, Card]`（`docs/176` B 那条"数据与逻辑分开"的
老路数）：`what` / `why` / `fixes`（**≥3 条**）/ `yes` / `no`。

| 字段 | 说清什么 |
|---|---|
| `what` | 是什么错了（**不复述消息原文**，原文已经渲染在上面） |
| `why` | 语言上的规则 —— 用户看完要能自己判断**下一个**同类错 |
| `fixes` | ≥3 条**能照做的一步**（不是"检查一下"） |
| `yes` / `no` | 相关构造的支持面：分得清"我写错了"与"这门语言没有这个" |

三条门槛与四段的完整**都有判据钉着**（`loment_tools_test::
test_every_code_has_a_card_with_at_least_three_fixes`）：23 个码共 85 条修法，
四段里有空就红。上界也钉了 —— `code_fix` 用平键 `c*8+i`（`FIX_STRIDE=8`），
**第 9 条会被静默挤掉**，所以超过 8 也要红。

### 11.2 与六语言翻译线衔接的那一半

同一张表里的 `LANG_CARDS`：每门语言给「显示名 / 后缀 / 内容特征词 / 边界 / 调用约定」。
报错器在"这个文件不是 Loment"时渲染的三条路（接口单元 / `--impl` / 运行期桥）就是从它出的。

**三条自律，都是被本仓已有的判断逼出来的**：

1. **语言清单不另抄一份**。键集由判据钉死 == `potato_from.LANGS`
   （`loment_tools_test::test_language_cards_cover_every_language_the_frontends_know`）——
   翻译线加一门语言而这里没跟上，症状是**新语言的文件报错时只字不提怎么翻**，静默缺口。
   这条正是 `docs/158` §5"消费者清单要和判据一起长"的又一次落点。
2. **不下"这条路通不通"的结论**。`foreign_note` 里有一条既有自律：**问出来、不是按语言写死**
   （拿 `lomt_from.emit_lomt` 数它到底发了几条 `pub extern fn`），因为"签名过不过得了 FFI
   那道闸门"是**逐文件**的。所以 `LangCard` 上那格叫 `abi`（陈述语言那一档的**事实**），
   而**不是** `iface`（替用户下"走不走得通"的判决）—— 后者的第一版写出来了，读完那条自律
   当场改掉。报错器那一侧没有 Python 可问，所以它只说事实 + 让用户跑一下看 stderr 有没有
   `[skip]`。
3. **语言是提示不是结论**。真正的判定权在翻译器的 `--lang auto`（它跑
   `potato_from.detect_lang`），所以渲染出来的命令**一律带 `--lang auto`**，末行也写明
   "别拿它当结论"。说死一句错的语言，用户会拿着错的命令去试 —— 比不说还坏。

**特征词专门挑"Loment 里不会出现"的形状**：`fn` / `impl` / `class ` 这些 Loment 自己也有，
拿它们当特征会让一份正经 Loment 文件（注释里写一句 `import` 就够）被误判成外源。
现在的词是 `#include` / `def ` / `use std::` / `System.out` / `func ` 这类。

**内容兜底只在语法错时用**：那才是"它可能根本不是 Loment"的信号；一份语法正确的 Loment 文件
报语义错时按内容闻，会被注释带跑。后缀那条路**优先**（一份 `.java` 无论里面写了什么都按
Java 说 —— 与 `potato_from.resolve_lang` 同一口径）。

**一个文件只给一次**：那段建议有几百字，重复 N 遍会把真正的诊断挤没。靠记住"上次给过哪个
文件"实现，判据用"两条同一文件的诊断 → 外源段只出现一次"钉着（可证伪）。

## 13. 语法声明压过内容嗅探（2026-09-18）

对端落了 `choose write grammar <别名>` 的**源侧**那一半（`docs/188` §2），
`potato_from.resolve_lang` 的次序因此变成 **声明 > 后缀 > 内容**。
他们当时说"`foreign_note` 那条链不受影响" —— **对 `foreign_note` 成立，对报错器不成立**：
`foreign_note` 问的是 `potato_from`（答案自然跟着变），而**报错器自己嗅探**，看不见那一行。

**实测出来的缺口**：一份 `choose write grammar python` 的 `.lomt`，工具链知道是 Python，
而报错器因为内容里没有 Python 特征词（`def ` / `__name__` / `self.`）**一个字都不说** ——
工具链知道、渲染器沉默，是最坏的一种。

**修法**：`sniff_lang` 改成**与工具链同一条次序**，并把**依据**说给用户听：

```
| 这个文件看起来**不是 Loment** —— 看内容像 Python（据文件头 `choose write grammar` 声明）。
| 这个文件看起来**不是 Loment** —— 看内容像 Java（据后缀）。
| 这个文件看起来**不是 Loment** —— 看内容像 C（据内容特征词）。
```

用户要能判断这句话有多硬 —— 声明是作者写的，内容特征词只是"看像"。

**别名表也走同一条管线**：`--dump-surface` 从 `potato_from.GRAMMAR_ALIASES` 导出
`alias_count` / `alias_word` / `alias_lang`（16 条），所以"作者能写哪些词"仍是一处真源，
渲染器不另抄一份。**导不出来时 `--dump-surface` 直接抛**，不给空表 —— 空表会让报错器在
"文件头声明了语法"时沉默，正是这一步要治的病。

**词序也走同一条管线**（`b494944` 之后补的）：`--dump-surface` 从
`potato_from.GRAMMAR_DECL_WORDS` 导出 `decl_word_count` / `decl_word(i)`，渲染器**逐词吃**
而不是写死那三个字面量。对端的判断是"判据红了比共享常量更直接"，我不同意这一条：
**判据只能事后抓，共享常量是防**。而且别名表已经走了这条管线，词序不走就是**不一致**
—— 这一节反复要治的正是那个。收益不止于防漂：`decl_at` 因此变成一个循环，
比三次 `eat_word(..., "choose")` 更短也更好读。

**次序那条线埋的同一个坑又出现一次**：`decl_lang` 只找那一行，**不管**"必须在 `module`
之前""只许写一次"—— 那是**工具链该报的错**。渲染器找不到就退回嗅探，
而"语法真变了"由判据钉着（`test_a_grammar_declaration_beats_content_sniffing` 会红），
不会静默漂。

判据：`loment_err_test` 15/15 —— 声明压过内容嗅探（**内容里一个 Python 特征词都没有**
也能认出来）、别名 `cs` / `c#` / `C#` 都落到 C#、依据说得出是哪一条路。
`loment_tools_test` 26/26；两侧 IR 逐字节相同（`lomenterr` 与 `surface_data`）。

## 14. 语言：默认英文，`errconfig` 切中文（2026-09-18）

### 14.1 为什么默认换成英文

报错器的骨架字串与说明卡原先只有中文。理由是"诊断这条路本来就是中文的"（`loment diag`
与编译器的 `[ERR]` 都是）—— **但这条理由只解释了"没人做"，没解释"这是对的"**：它同时意味着
**默认输出在中文 Windows 上就是乱码**（936 代码页解 UTF-8，PE 垫片没有 `WriteConsoleW`，
程序侧无从补救，`docs/169` §3a）。

换成英文之后，**报错器自己那部分**在任何代码页下都解码一致。**这句话的边界要写清楚**：
编译器给的消息原文仍是它自己的语言（现在还是中文），所以"默认输出不再是乱码"这个说法
如果整句吞下去就是错的 —— 修好的是渲染层，消息那一行没有。判据也是分开判的：
`test_english_is_the_default_and_the_renderers_own_text_is_ascii` **自己造一条 ASCII 消息**，
这样"输出里没有 >=0x80 的字节"才是对渲染器那一半的断言，而不是把编译器的中文也赖上。

### 14.2 语言槽进了 `surface_data`，不是渲染器里的一张表

`--dump-surface` 现在把每段文字**按语言槽出两份**：`lang = 0` 是英文（默认）、`lang = 1` 是中文。
平键因此变成 `code_title(c, lang)` 的 `c * 2 + lang`、`code_fix(c, i, lang)` 的
`(c * 8 + i) * 2 + lang`；`lang_edge` / `lang_abi` 同理。`code_ascii` **没有语言槽** ——
它是第三个受众（`loment codes` / `explain` 的一行 ASCII），本来就只能是 ASCII。

**为什么加一维而不是另开一张表**：另开一张表意味着渲染器要在两个调用点之间选，
而"哪个调用点忘了选"是判据抓不到的（渲染器是 Loment 程序，没有类型能表达"必须选"）。
把语言放进**键**里，调用点只剩一个形状：`code_what(cnum, lg(ctx))`，忘了传就编不过。

**中文那份不是被删掉，是换到后面**：`CARDS_EN` / `TITLE_EN` / `LANG_EDGE_EN` / `LANG_ABI_EN`
与中文那几张**相邻**放在 `tools/loment_diag.py` 里。挨着放是有意的 —— 改一处语义要同时改
两处，而**判据抓不到"两处说的不是一件事"**（键集相等、条数相等、非空、纯 ASCII 都能判，
"意思对不对"判不了）。所以唯一能做的就是把它们放在一眼能同时看到的位置。

### 14.3 `errconfig`：形状照抄 `loment.conf`，读者只有这一个

```rust
// errconfig — 报错器说哪种语言
module errconfig

pub fn error_lang() -> str {
    return "zh";     // "en"（默认） / "zh"
}
```

**为什么是独立文件而不是 `loment.conf` 里多一个键**：`loment.conf` 管「**工具链怎么读源码**」
（`source_ext` 那类，词法器要读，`docs/182` §7）。"报错器说哪种语言"是**渲染层**的口味，
与怎么读源码无关 —— 混进去会让一个"语言怎么认"的文件里出现一条与源码识别毫无关系的设置。

**形状**照抄 `loment.conf`（一个标签 + 一个字符串），因为仓库里已经有一个人人认得的配置
文件长这样。但**读者只有这一个**（Python 那边不读它），所以这里没有"同一份契约抄两遍"，
只有"长得像"。

四条规则，都是"读不出来就当没配"那一侧：

| 输入 | 结果 |
|---|---|
| `"zh"` / `"ZH"` / `"cn"` / `"Chinese"` | 中文（**一律大小写不敏感**） |
| `"en"` / `"English"` | 英文（显式写回默认，也合法） |
| `"klingon"` / 引号没闭合 / 没有这个文件 | **当没配** —— 不报错、不猜，继续找下一份 |
| 注释里提到 `error_lang` | **不算**（标签后面必须紧跟 `(`） |

最后一条是设计的一部分，不是巧合：少了"标签后面必须紧跟 `(`"这条判据，**一句注释就能把
语言悄悄改掉** —— 而"悄悄生效"正是这套东西要挡的。

**"认不出来 = 没配"这一格是实测补上的**：第一版只让长写法（`English` / `Chinese`）不敏感，
`en` / `zh` 是**逐字节**比的 —— 于是 `"ZH"` 静默退回默认，而文档上写着"大小写不敏感"。
文档说 A、代码做 B，只有判据抓得到，所以现在五个拼法各有一条断言。

**两份文件，项目那份优先**：`./errconfig` 然后 `<工具目录>/../share/loment/errconfig`。
与 `loment.conf` 同一条（"项目那份优先"），而**项目根 = 当前工作目录**（启动器就是这样进来的）。
"认不出来 = 没配"在有两份文件时才有分量：项目那份写错一个字母，不该把用户**系统级**的那份
一起作废（不然两份都没生效，而输出里没有任何提示）。

判据走的是**用户走的那条路**：在一个临时目录里真的摆一份 `errconfig` 并把 cwd 切过去，
而不是给渲染器塞一个内部开关；工具链那份由一条**假包布局**的判据覆盖
（`<tmp>/bin/lomenterr` + `<tmp>/share/loment/errconfig` —— 那个路径是从 `argv[0]` 推的）。

### 14.4 判据

`loment_tools_test::test_the_english_tables_are_complete_and_pure_ascii` —— 四样一起钉：
键集与中文相等、段不空、**修法条数与中文相等**（`code_nfix` 只报一个数，语言不进它的键，
少一条会被静默挤掉）、**全 ASCII**（默认语言换过去的前提）。`LANG_EDGE_EN` / `LANG_ABI_EN`
用同一把尺子。

`loment_tools_test::test_ui_strings_have_both_languages` —— 渲染器自己的骨架字串在
`lomenterr.lomt` 里，直接读源码判 `ui_en` / `ui_zh` 键集相等且从 1 起连续。

`loment_err_test::test_errconfig_switches_the_language_and_a_bad_one_falls_back` —— 六种输入
各跑一遍真渲染，判决只有两个（`zh` / `ZH` / `Chinese` 切中文；`en` / `klingon` / 注释里的
伪标签都退回默认）。

`loment_err_test::test_the_toolchain_beside_errconfig_is_the_second_place_read` —— 两份文件
的次序与"认不出来 = 没配"这一格。它摆一个**假包布局**（`<tmp>/bin/lomenterr` +
`<tmp>/share/loment/errconfig`），因为工具链那份的路径是从 `argv[0]` 推的 ——
`./errconfig` 用 cwd 就够，那一份不行。

## 15. 三个出口与两条码专属补充（2026-09-18）

### 15.1 同一份渲染，三个出口

`--short` 与 `--json` 是**同一份渲染的另外两个出口**，不是另做一套判断：读的还是 `C_CODE` /
`C_MSG` / `C_PATH` 那几格，查的还是同一张 `surface_data`。所以"总结给谁看"变了，"说什么"没变。

| 模式 | 形状 | 给谁 |
|---|---|---|
| 默认 | 位置 + 源行 + 插入符 + 四段说明卡 | 人（在终端里读） |
| `--short` | 一行一条：`文件:行:列: error[码]: 消息` | 人（CI 日志里 grep）/ 编辑器 |
| `--json` | 一行一个对象（JSONL，与 `--diag-out` 同族 + 卡片字段） | **程序**（quickfix / 按码统计） |

两个都是**顺带关色**：它们存在的意义就是给管道与编辑器读，一条带 ANSI 转义的"机器可读行"
没人能 grep。`--short` 还多做一件事：消息里的换行**折成一个空格** —— 不折的话一条诊断变成
两三行，"一行一条"这个承诺就破了。

`--short` 在 `col == 0` 时**不印列**（`check()` 的语义诊断只给行号），与 `h_loc` 同一条纪律：
`x.lomt:9:0:` 会让编辑器按第 0 列跳，那是编出来的位置。

`--json` 的转义是**必须的**：卡片正文里有反引号包裹的 `"`（E005 的 `excluded "<space>: ..."`）
与反斜杠，不转义就是一个坏 JSON —— 而在编辑器那边那表现为"报错器坏了"，不是"这条消息有点怪"。
边界上的东西还多写了一条控制字符分支（`\u00XX`）：消息是编译器给的，`--json` 的消费者是程序，
一个坏 JSON 的代价比四行代码大。

**`--json` 里没有汇总**：那是一行给人看的文本，混进 JSONL 会让下游解析器当场坏掉 ——
把"给程序读"这个承诺自己破掉。判据专门数行数（`2 个诊断 == 2 行`）。

**两种"不完整"要在每个出口都说出来**（`#478`、`#485`）：

* **诊断文件里有一行读不懂**：`--json` 出口吐 `{"broken":true,"text":"<原文>","note":"…"}` ——
  仍然是一个对象，流照样可解析；形状与诊断对象**故意不同**（没有 `code`/`line`/`col`），
  因为这条记录唯一的事实就是"读不懂"，硬造一个码会让它看起来像一条真诊断。
  末尾那句 `lomenterr: N lines are not valid JSON` 在 `--json` 下**不打**（它就是汇总）。
* **消息本身被截断**：三个出口各说各的 —— 完整模式印 `被截断` / `truncated`，`--short`
  在行尾补 `[truncated]`，`--json` 多一个 `"truncated": true`。判据是"消息装满 `MSG_CAP`"：
  正常消息几十到几百字节，正好 16 KiB 的真消息不存在；而为了更精确再数一遍解码，换来的是
  本仓反复踩的那类"同一件事的第二份实现"。

### 15.2 汇总：按码分组，条数多的先出

```
4 errors: E019 x3, E002 x1
```

它比"4 条错误"多出来的那点信息是**分布**：4 条里有 3 条是同一个原因时，改一处就消掉三条，
而按出现顺序一条条修会白改两次。所以**顺序是被判的**（判据故意让少见的码在文件里靠前 ——
按出现顺序排的话它会先出，那条判据就抓得到）。

中文那侧写 `4 条错误：E019 ×3, E002 ×1`。码号统一写成 `E019` 那种三位补零的样子；
解不出数字的码写 `E?` —— **不许写成 `E000`**，那是一个看着像真码的假码。

### 15.3 E002："你是不是想写 X"

```
  | did you mean `leftover_count` (declared at line 7)
```

E002 最常见的成因就是**拼错一个名字**，而通用建议（"补类型标注 / 改拼写"）帮不到具体这一个。
所以扫一遍本文件里已声明的名字（`fn` / `let` / `const` / `struct` / `enum` / `trait` /
`capability` 后面那个），按编辑距离给一个候选。

四条门槛**全在"宁可不猜"这一侧**，其中第二条是重点：

1. 距离 ≤ 2；
2. **候选必须唯一** —— 有两个一样近的就不说。**说错比不说坏得多**：用户会照着它改，
   而那是把一份本来能编的代码改坏。判据专门造了并列（`alpha_count` / `beta_count` 对
   `gama_count` 都是差一个字符）来证伪这一条；
3. 线索短于 3 个字符不猜；
4. 候选名本身也要 ≥3 个字符。

**不收 `pub` / `use` / `impl`** —— 它们后面跟的不是新名字（`impl M for S` 引入的是既有类型），
收进来就是把噪声当候选。**只看本文件**：`use` 进来的名字在另一个单元里，距离比较无从谈起。

已知的粗糙处（如实记）：扫的是**词法形状**，不认注释与字符串。影响是双向的，而两个方向都是
保守的：噪声候选要成为建议，得**恰好唯一**地落在距离 ≤2 上；更多时候它只是制造一个并列，
于是我们不说。为这点噪声写一个词法器不值。

### 15.4 E018：把手上真实有的列出来

光说"补文件"没有用 —— 用户不知道补到哪，也不知道自己手上已经有什么。所以：

* `./deps` 打不开（单文件项目最常见的那种）→ 明说"这里没有 `deps/`"，并把第 1 层找的是什么
  路径写清楚。**这条不需要 `getdents64`**：`openat` 失败本身就是答案（好消息是这条路
  在 PE 上也稳）；
* `./deps` 打得开 → 列里面**名字接近**的那几个（距离 ≤2，最多 5 个）。

**为什么不列"诊断文件所在的那个目录"**（这是我最初的想法，实现时被自己否掉的）：
`use <名字>` 从来不在文件旁边找东西 —— 按层搜的第 1 层是**项目根**下的
`deps/<名字>/<名字>.lomt`。列文件旁边的目录会给出一个看着相关、其实无关的清单，
**那比不说更坏**。项目根 = 当前工作目录，与 `errconfig`、`loment.conf` 是同一个约定。

### 15.5 判据

`loment_err_test` **24/24**（§14 加 §15 一共新增 8 条）—— 默认英文且渲染器那部分纯 ASCII；
errconfig 六种输入 + 两份文件的次序；汇总的顺序；`--short` 的行数与折行与关色；
`--json` 每行可解析 + 卡片字段齐全 + 转义正确 + 不掺汇总行；拼写建议的"唯一才说"
（并列与差得远都要**不说**）；E018 两种地方各一条；启动器把三个开关都转交到位。

`loment_tools_test` **28/28**（新增 2 条）—— 英文表完整且全 ASCII；界面字串两门语言齐全。
`loment_cli_test` **34/34**（新增 1 条）—— 两个启动器都转交那两个输出模式。
两侧 IR 逐字节相同（`lomenterr` / `surface_data` / `lomcli`）。

**发布清单（`loment_release`）故意没重生成**：`GLOBS` 覆盖 `tools/*.py` 与
`loment/tools/*.lomt`，而树上还有**别人的在制品**（`lomentc.py`、`editors/vscode/*`、
`potato_from.py`）—— 这时 `--emit` 会把它们的工作树哈希烤进清单，那份清单一提交，
HEAD 上 `loment_release --check` 对所有人红。**谁最后提交谁重生成**（这条纪律已经有过一次
代价，见 `project_concurrent_sessions` 那条记忆）。

## 16. 抄 16 门语言的报错消息（2026-09-18）

用户要「收集 Java/C/Python/Rust 等 15 个语言的报错消息，超级进化 lomenterr」。
**收集**那一半（16 门对照、每门抄什么、哪些**不抄**以及为什么）单独一篇：
`docs/191-error-reporter-survey.md`。这一节只记**落进代码的那六条**与它们逼出来的两件事。

### 16.1 落地的六条

| 抄自 | 形态 | 为什么它值得抄 |
|---|---|---|
| rustc 的 `help:` | 唯一候选时印**改好的那一行**（新名字下带插入符） | 一句"你是不是想写 X"要人在脑子里做替换，**而替换正是最容易再错一次的地方** |
| Ruby 的 `Did you mean?` | 并列时**列候选**（≤3 条），每条带**种类**与**行号** | 闭嘴与抛硬币之间还有第三档 |
| rustc `--error-format=json` / Swift fix-it | `--json` 的 `suggestions[]`：`replacement` + `byte_start`/`byte_end` + `applicability` | 编辑器要的不是"看到一句话"，是**一键改对** |
| rustc 的 `try 'rustc --explain E0308'` | 结尾一行 `more: loment explain E002` | 把"还有详解"变成一条**能敲的命令**，而那命令真的存在（`lomcli` 的 `explain`） |
| clang `-ferror-limit=20` / Go 的 10 条 / javac `-Xmaxerrs` | `--max N`（默认 20，`0` = 全部），超了**明说还剩几条** | 生成的代码一错几百条；三家都默认设上限 |
| clang 的 `^`/`~` 两种标记 | 只抄**精神**：插入符要指到 token | 定位到 token 是实测 8 门里做得到的那几家都做了的事 |

### 16.2 两条契约**当轮改掉**的（都写进判据的 docstring 了）

1. **并列不再闭嘴**（原先：两个一样近就什么都不说）。那是**我在没有更好的办法时**的保守。
   有了候选表之后，"列出来 + 说清每个是什么、在哪一行"既不猜、也不把"有两个可能"
   这个事实瞒掉。差的仍是不说。
   → `test_did_you_mean_only_when_it_is_the_only_candidate` 拆成两条：
   `test_the_help_block_prints_the_fixed_line` 与 `test_ties_list_candidates_with_kind_and_line`。

2. **`--short` 的"一行一条"从"总共 N 行"改成"前 N 行"**：尾巴上多了汇总与 `more:`，
   而**断言一改，往尾巴上加东西就会红**——尾巴本来就该能加东西。判据按"前 N 行"判。

### 16.3 一个**真 bug**：线索取自源文件，不是"消息里最后一个词"

换成**真编译器产出的**诊断之后，拼写建议一条都不出、插入符也跑到错的地方。真消息是：

```
10: 调用未定义的函数 leftove_count（跨模块调用需要 pub）
```

"最后一个长度 ≥2 的词"取到的是 **`pub`**（括号里那句提示的末尾），于是插入符划到了 `pub`。

**根因不只在那条规则，还在夹具**：此前判据用的是**手写**的 JSONL，消息比真东西干净，
于是它测的是一个**不会发生的输入**。修法不是维护一张"噪声词"表（同一份清单抄第二遍，
编译器改一次措辞就过期），而是**拿源文件当裁判**：从消息末尾往前找第一个
"**在本文件里整词恰好出现一次**"的词 —— "唯一"正是"它指着源里一处"该有的性质，
而 `pub` 要么不出现要么出现多次，自动被跳过。

副作用（也是收益）：那条规则同时管住了插入符、拼写建议与机器可应用的偏移，
三者**找的是同一个词**，不会再各指一处。

### 16.4 顺带修掉的：源里的 CR 不再被就地剥掉

`--json` 要给出**能直接切片的字节偏移**，而 `src_ensure` 原先会把源里的 CR 就地剥掉 ——
那样每个 CRLF 文件**从第二行起每行偏一个字节**（Windows 上 CRLF 是常态），
交给编辑器的偏移会切错地方。现在不剥（`line_span` / `is_blank` 本来就认 CR），
判据在一份 CRLF 源上真的切一刀验它（`test_json_suggestions_are_machine_applicable`）。

### 16.5 上限**不管 `--json`**（这一条是抄的时候自己加的）

`--max` 是"别把人的屏幕顶爆"的装置，而**机器出口没有屏幕**：那里少一条记录就是
**静默丢数据**（下游按条数算的东西全错，而它在 stderr 上也看不到任何提示 ——
JSON 模式压根不打汇总与说明）。所以 `--json` **从不截**。

clang 的 `-ferror-limit` 对 SARIF 也生效，但那是**编译器停手**、并且会打一条 fatal；
我们这里没有那条路可走（诊断已经全在文件里了），所以宁可让 JSON 全给。
判据：`test_max_caps_and_says_how_many_were_hidden` 里那一条 25 行的 `--json --max 3`。

### 16.6 `suggestions` 为空时**字段缺席**（`#51`）

`suggestions` 原先**每个对象都写**，没有候选时给 `[]`。消费者分不出两件事：
"这个码没有可应用的修改" 与 "建议功能还没做"。字段缺席 = 后者（今天只有 E002 产建议），
字段在且非空 = 前者有东西可一键套用 —— 与 `byte_start`/`byte_end` 只在指得准时出现
是同一条纪律。判据在 `loment_err_test` 里：E002 的 `suggestions` 非空且能切片，
E015（结构体没有这个字段）的对象里**没有这个键**。

### 16.7 判据

`loment_err_test` **29/29**（这一轮 5 条新的：help 块 / 并列列候选 / 线索取源 /
机器可应用建议（含 CRLF）/ explain 指针 / `--max`）。
`loment_cli_test` 加一条**两个启动器都要转交** `--max`（含它的值 —— cmd 那路是 `for`
扫全命令行，得记住"下一个词是它的值"，否则 `--max 0` 会把 `0` 当成源文件）。
两侧 IR 逐字节相同。

## 17. 报错器有自己的版本号：0.1.2（2026-10-13）

### 17.1 为什么要一个独立的号

`lomenterr` 到这一节为止，对外只有**语言**那一个版本号。那一格是错的，而且错得有点隐蔽：
它让"报错器改了什么"没法记。2026-09-18 到 10-13 这三周里，报错器改了七八轮 ——
四段说明卡 → 六语言方言卡 → 上色 → 语法声明优先 → 双语（默认英文）→ 三个出口
（`--short`/`--json`）→ 逐条建议（help 块 / 并列候选 / 机器可应用）—— 而**语言版本在这段
时间里只动过一次**。把两件事捆在一个号上，就只能记成"语言又升了一版"，那既不真，
也让人没法回答"我用的是哪个报错器"。

所以：**两条线，各自独立**（用户 2026-10-13 定）。报错器是**一件独立交付的程序** ——
它有自己的命令行面（`--short` / `--json` / `--max` / `errconfig` / `version`）、
自己的判据（`loment_err_test`）、自己的孪生（`loment/tools/lomerrcheck.lomt`），
而且它的改动**与语言面无关**。

### 17.2 一处真源，不许有第二份字面量

| 环节 | 在哪 |
|---|---|
| **真源** | `tools/loment_release.LOMENTERR = "0.1.2"` |
| 生成物 | `loment_diag.py --dump-surface` 把它导成 `surface_data.lomenterr_version()` |
| 消费者 | `lomenterr version` 打的就是它 |
| 文档 | README / QUICKSTART 里那两句（**不是**第二份真源，是叙述） |

**为什么这么走**：`loment_release.py` 本来就是"版本这件事"住的地方（`RELEASE` /
`RELEASE_NAME` 在那儿），报错器的号属于同一个家族；而 `surface_data` 是**生成物**，
已经被 `test_surface_data_is_up_to_date` 钉着逐字节可复现 —— 于是"真源改了、生成物忘了
重跑"会被判据抓，不需要再写一条。

**取不到就炸，不给默认值**（`_lomenterr_version()`）：给了默认值，生成物会带着一个
**编出来**的号出门，而它看着完全正常（`0.1.0` 这种真像回事的号），没人会发现。

**为什么不塞进 `share/loment/version`**：那是**语言**的版本文件，`lomcli` 读它打
`loment version`。两个号共用一个文件，就是"同一份清单抄第二遍"的另一副面孔 ——
而且这次两份都是 `0.1.x`，不同步时看不出谁对。

### 17.3 这一条线对应哪三次交付

`0.1.2` 是**现在**这个号；前两个号是这次补记的（按实际发生的三次交付划分，逐条见本文件）：

| 版本 | 是什么 |
|---|---|
| `0.1.0` | 编译期落地 —— 渲染器本身，接进工具链与两个启动器（§10） |
| `0.1.1` | 说明卡 + 六语言方言卡 + 上色 + 语法声明优先（§11–§13） |
| `0.1.2` | 双语（默认英文）+ 三个出口（`--short`/`--json`）+ 逐条建议（§14–§16） |

### 17.4 输出走 **stdout**（这是一个有意的例外）

`lomenterr` 别处一律写 **fd 2** —— 它渲染的是错误，而错误该与诊断同路。`version` 不一样：
**它不是诊断，是"你是谁"**，而且脚本要 `v=$(lomenterr version)` 拿它，fd 2 抓不到。
所以这一行**故意**走 fd 1，并在代码里写明是例外，免得下一次有人"顺手统一成 fd 2"。

三个写法都认（`version` / `--version` / `-V`）：裸词与 `loment version` 一致，
两个带横杠的与别处一致（`lomcli` 也是 `version` 与 `--version` 都收）。

### 17.5 判据

`loment_err_test::test_version_prints_the_reporter_own_number` —— **三个写法**都打出
`lomenterr 0.1.2` 且退 0；打的那一行**在 stdout**（stderr 是空的）；
它与 `loment_release.LOMENTERR` **逐字相同**（这条同时是"没有第二份字面量"的判据：
改真源而忘了重跑 `--dump-surface`，`test_surface_data_is_up_to_date` 与它一起红）。

## 18. 适配 0.1.4.5：E022 的卡追上了**五维**（2026-10-14）

### 18.1 哪里没跟上

分类**早就**跟上了 —— `RULES` 里 E022 那一行的正则已经认得 0.1.4.5 的新消息
（`核心模式这一维只能声明一次`、`不能同时选`、`发行版不含 VM`、`发行版不含对外端口`）。
没跟上的是**卡片**：它的 `what` 还写着"核心模式（`std`/`no_std`）"，
第一条修法还是"`choose std` 或 `choose no_std`" —— 而 0.1.4.5 的核心模式是**五维**。

**症状有多隐蔽**：用户写 `choose gc_auto` 撞上 E022 时，分类对、标题对、位置对，
而卡片教的是**上一个大版本的语言**。这类"卡是旧的、码是对的"不会让任何判据变红 ——
它只会让用户照着一张过期的图去改。

### 18.2 五维（`lomentc.CORE_DIMS`，卡里逐维写全）

| 维 | 取值 | 是什么 |
|---|---|---|
| `mode` | `std` / `no_std` | 能用哪一层 |
| `gc` | `gc_manual` / `gc_auto` / `gc_auto_alpha` | 回收由谁做 |
| `runtime` | `runtime` / `no_runtime` | 产物里有没有运行期 |
| `port` | `sealed` / `hosted` | 通不通着世界 |
| `vm` | `vm` / `no_vm` | 要哪种执行模型 |

卡里同时说清三件 0.1.4.5 才成立的事：**每一维各自只能声明一次**（不是"整个核心模式只能
写一次"）、**两维取值互相矛盾也在这里报**（`gc_auto` 与 `no_runtime`）、
**渠道闸**（发行版里 `choose vm` / 带对外端口的 `hosted` 进不来）。

### 18.3 顺手把"卡会不会再落后"这件事也钉住

卡片落后之所以没被发现，是因为**没有任何东西在比"卡"与"语言"**。这一轮能钉的是**分类**
那一半（下一节），卡片内容那一半仍然只能靠人 —— **这是这一节的诚实边界**：
`test_every_message_the_compiler_can_print_has_a_code` 保证"每条消息都有一张卡"，
**不保证"那张卡说的是当前的语言"**。后者要另一条判据（比如把卡里的取值表从
`lomentc.CORE_DIMS` 生成出来），列在 `docs/244` §3。

### 18.4 减少静默：把"0 条未分类"从一次测量变成不变式

`loment_err_test::test_every_message_the_compiler_can_print_has_a_code` ——
AST 扫 `tools/lomentc.py` 里 `errs.append(...)` / `LomError(...)` 的调用点，枚举出
**诊断模板**，逐条过 `loment_diag.classify()`，断言没有一条落到 **E999**。

**为什么扫模板而不是跑语料**：模板是"编译器可能说什么"的**上界**，运行时消息是它的实例化。
上界覆盖了实例化一定覆盖；反过来不成立 —— 跑一遍语料只碰得到其中一部分，
而**碰不到的那些恰恰最容易漏**（罕见路径）。实测 102 种模板，0 条未分类。

**判据自己也要能证伪**：它先断言"扫到了东西"（`assert seen`）—— 提取方式哪天跟编译器
脱节，这条判据会**说自己在空转**，而不是拿一个空集合报绿。

### 18.5 判据

`loment_err_test` **35/35**（本轮 +1：上面的分类枚举）;
`docs/244` 是"更多错误 / 更少静默 / 更详细"的**计划**，其中 §3#1 与 §1.4 是下一轮的两件。
