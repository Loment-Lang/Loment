# 158 · Loment L1 冻结面（M96）

> 版本：`L1 0.1.4`（显示名 `Loment 0.1.4`；`loment/build/release-manifest.json`
> 的 `release` 字段由 `tools/loment_release.py:RELEASE` 单一真源给出）；对外 tag `v0.1.4`
> 判据（docs/145 M96）：**冻结意味着"改动要付代价"** —— 任何触及冻结面的改动都必须
> 同时改规范、改一致性套件、两个实现同一次提交改完，并走 §5 的流程。
> 本文只写"冻结了什么"和"怎么改"，不重复语法细节（那在 `docs/manual/` 与
> `docs/15*-loment-*.md`）。

## 1. 为什么现在能冻结

冻结的前提不是"功能齐全"，而是**规范有唯一的执行者且可测量**：

- 自举 checker 与参考实现在 **63/63 条规则**上判定等价（`tools/loment_rule_parity.py`，
  棘轮门禁 `eq ≥ BUDGET`、假阳性/漂移必须为 0，已进 `tools/ci.py` 静态门禁）；
- 63 条规则负例**直接喂自举驱动**全部非零退出且无一因信号而死
  （`test_m85_driver_gate_on_probe_cases`）；
- 40/40 语料单元零诊断、40/40 可发射目标**两个后端逐字节一致**、三阶段自举定点成立
  （`tools/loment_p8_test.py`）；
- 错误码口径是**单一真源** `tools/loment_diag.RULES`（E001–E019），
  且 **checker 诊断**能发出的全部 81 条消息模板都被它分类
  （`test_m64_all_reference_messages_are_classified`）。
  **这句话原先说宽了**（2026-09-15 更正）：那 81 条是 ast 从 `errs.append` 抽出来的，
  覆盖的是 **checker 的语义诊断**；解析期的消息是 `raise LomError`，不在抽取范围里，
  于是它们原先在 `loment diag` 里一律显示成 **E999「未分类」**。现在解析期归 **E019**
  （语法错的修法只有一种，按「码按修法分」共用一码），并由
  `test_m64_diagnostics_have_codes_and_hints` 之外的两条最小负例钉住。

换句话说：从这一刻起，"语言是什么"由**规范 + 一致性套件**定义，参考实现不再是唯一权威
（它是套件里的一员）。

## 2. 冻结面（改动要付代价）

| 面 | 内容 | 为什么冻结 |
|---|---|---|
| **语法与类型规则** | 词法（含"多字符运算符拆成单字符 token"这一条）、解析形状、类型系统、移动/借用规则、**`extern fn` 声明**（`docs/143` §3.1） | 它们是用户程序与一致性套件的接口 |
| **诊断口径** | 错误码 E001–E022 及其"码按修法分"的分组原则 | 用户脚本/CI 会按码匹配；码是最稳的 ABI |
| **单元装载规则** | `use` **两种写法**（路径 `use "…lomt"` / 名字 `use 名字`）递归装载、依赖**先序**拼进单元、去重、预置枚举注入点（单元末尾）；名字形式的搜索根、唯一性与单文件条数上限见 `docs/143`。**后缀不属于这一层**：只有 `.lom` 是特殊的（L0），别的后缀都是 L1 源，名字形式用哪个后缀由 `loment.conf` 定（默认 `.lomt`） | 决定同名/顺序/枚举可见性，跨文件程序的语义靠它 |
| **发射符号约定** | **顶层名字在单元内唯一**（平名字空间，不做 mangling）；入口名（`_start`/`timer_isr` 等）由内核线按名查找；内核/驱动按名解析的符号不得私有化。**调用约定有两套并存**：Loment 之间走自家约定（实参走栈），**`extern fn` 的调用点走平台 C ABI**（`docs/143` §3.1） | 这是**跨线 ABI**（docs/155 §3）：内核与 C 夹具按名字找入口，改名就是破坏契约 |
| **两个后端的等价性** | 对同一输入，自举 codegen 与参考实现的 IR 必须**逐字节相同**；三阶段定点必须成立 | 这是"两个实现"能互相验证的前提；它也是回归检测的主要手段 |
| **内建函数表** | 18 个内建的名字、元数、参数/返回类型（`lomentc.BUILTINS` ∪ `{slice_len}`） | 名字与签名被内核线直接调用 |
| **能力域语义** | `capability`/`guard`/`excluded` 的判定，字面量越界在编译期拒 | 它是信任自适应能力域（B25/docs/125）的输入 |

## 3. 明确**不**冻结（可以自由改）

- 实现内部：两张编译器的内部表布局、缓冲尺寸、遍历顺序、临时名；
  自举侧的 arena 分段、类型表述、性能（只要不动 §2 的等价性与容量闸门）。
- 工具链内部：`tools/*.py` 的函数/结构，只要对外命令行的**行为**与 §2 的判据不变。
- 文档结构：`docs/manual/` 的生成物内容随源变化（它由 `loment_manual --emit` 生成）。
- 性能：M86 目前只有护栏（自编译 ≤ 30s，实测基线 12.8s）。优化不受冻结限制 —— 索引化
  符号查找这类改动只要不改变产物字节，随便做。

## 4. 已知的开放项与刻意偏离（冻结时必须写明）

冻结**不等于**"完备"。这些是已知的口子，写在这里是为了让后续使用者与审计者不必自己撞：

| # | 项 | 现状 | 影响 |
|---|---|---|---|
| 1 | 三处**刻意偏离** | 下标/`&` 在"类型未知"时不报；`match` 主体未知时不报；`?` 只在能确定不是 `Result` 时报（详见 docs/150 缺口③） | 自举 checker 在这三种情形下**可能少报**；参考实现会报。方向是保守（不假阳性） |
| 2 | 同名 `let` 双 `alloca` | 参考实现复用槽位（一条 `%x.addr`），自举 codegen 发两条且第二条遮蔽第一条（docs/150 bug ⑬） | 同一函数里重复声明同名变量时两个实现语义不同 |
| 3 | 驱动器**没有 parser** | 驱动是 lex → check → emit；解析期错误（如 `const C: bool = true;`）它看不见，只能靠参考实现兜 | 自举链单独使用时，解析期错误不会被报出来 |
| 4 | `aarch64` 目标 | 后端支持 `elf64-littleaarch64`，但**未在真机/模拟器上执行过**（docs/145 M92） | 只保证发射，不保证运行 |
| 5 | 自举性能 | 自编译 12.8s（参考实现 1.2s），符号查找是线性扫 | 大单元编译偏慢；不影响正确性 |
| 6 | DWARF 变量信息 | 只有语句级行表，没有变量位置信息（docs/145 M59） | 调试器能按行断点，看不到变量值 |
| 7 | 外部审计 | **已由独立 agent 复核**（`docs/203`，2026-09-22：24 条里 22 接受 / 1 驳回 / 1 未验证）；**仍无外部人类/组织**复核 | 冻结面内的判据**仍然是自证**的 —— "两个同一作者的实现两边一致"**不等于**"对"。这一条**没有被那次复核改变**（复核者自己也把这一点写在 §7.3 的"不授权"里） |
| 8 | **括号里的 `ptr` 表达式再 `as` 整数** | 参考实现发 `ptrtoint ptr`（正确）；**自举 codegen 发 `zext i32`** —— 把指针截成 32 位 | 自举侧编出的机器码在运行期**会用错地址**。2026-09-16 写 `loment/lib/proc.lomt` 时撞到：`(ptr_add(out, total)) as u64`。**语料里以前没有这种写法**，所以逐字节判据一直没覆盖它 —— 现在那条源码绕开了（先 `let dst: ptr = ...` 再 `dst as u64`），但**自举侧这个转换仍是错的**。根因：自举按**源类型的 token** 判 ptr→整数，括号表达式没有那个 token |
| 9 | FFI 外部目标文件的**大小上限** | 参考实现 (`tools/lomelf.py`) 读任意大小的 `.o`；**自举链接器**把它读进一个 **4 MiB 固定暂存缓冲**，超了**报错退出**（不截断）。2026-09-16 补 FFI 自举镜像时引入（`docs/173` §5b） | `.o` 超过 4 MiB 时两个实现行为不同：参考能链，自举拒绝。自举侧没有动态增长缓冲的来源（只有 brk 一块固定 arena），要去掉得先给它一个堆。**同一版内**其它 FFI 差异见 `docs/173` §5b |
| 10 | **`R_X86_64_PC64` 的符号扩展** | 参考实现按**有符号**写（`S + A - P` 的 64 位有符号值）；**自举链接器按零扩展**写 | 只在 `S + A - P` 为负且落在 `.text` 里时不同。**实测到不了这条路**：`PC64` 只出现在数据节的 64 位 PC 相对引用上，而落在非代码节的重定位两个实现都**一开始就拒**。留记号是因为"逐字节一致"这句话不该有一个未记的例外（`docs/173` 阶段 2） |
| 11 | **B1 · 混宽整数比较不给两边统一宽度**（2026-09-17，**新发现，未修**） | 参考实现只把**左边**提升到较宽类型，右边留原宽 —— 于是 `u32 == u8` 产出**非法 IR**，clang 当场拒（`'%t9' defined with type 'i8' but expected 'i32'`）。自举那边则把左边**截到窄的**再比（对 `load8` 恰好等价，对一般 `u32 == u8` 是**错码**），且在 `load8(…) == x: u8` 这个形状上与参考**不一致** | **最小复现**（两边都"过"，参考产出非法 IR）：<br>`fn eq(a: u32, b: u8) -> bool { return a == b; }`<br>参考发 `%t2 = load i8` 后 `icmp eq i32 %t1, %t2`。语料里从来没有混宽比较，所以逐字节判据一直没覆盖它 —— **两边一致地错**，而"一致"让人以为它是对的。<br>**写 std 核时撞到**：`loment/lib/mem.lomt` 的 `mem_find` 原来写 `load8(hay,i) == needle`（`load8` 是 `u32`、`needle` 是 `u8`），于是 `loment_pkg_test` 三个用例全红（clang 拒 IR）、`loment_cli_test` 的自举/参考对照红 2 字节。<br>**现在的绕法**：`mem.lomt` 显式 `let want: u32 = needle as u32;` 把两边都变宽（合法 IR）。**编译器本身没修** —— 修它要走 §5 四条（两个实现同一次提交 + `_CASES` 加混宽比较的负例 + 上调 `BUDGET`），是一次独立的语言面改动 |

| 12 | **关键字可以当标识符，两个实现处理不同**（2026-09-17，**新发现，未修**） | 参考实现**一律接受**关键字做绑定名 —— `fn` / `if` / `let` 都能当形参名或变量名（Rust 的规则是关键字不能做标识符，这里是个洞）。**自举 checker 撞上它会错位**：它按 token 文本判关键字，参数位置的 `fn` 被当成"又一个函数声明"的起点，于是**后面整段 token 流对不上**，报出一条毫不相干的假阳性 | **最小复现**：给任一函数加一个名叫 `fn` 的形参，自举 checker 就会在**几十行之后**报一条 E002（符号未声明），指着一个字符串字面量，而参考实现干干净净。<br>**写驱动的 `--diag-out` 时撞到**（`docs/182` §5）：`wdiag(..., fn: u32, ...)` 让 `test_m85_checker_accepts_corpus_units` 红 —— 报 `2@65173:",\"line\":"`，而那个 token 与 `fn` 毫无关系（我先按字面量/转义/花括号三个方向查过，都不对）。<br>**现在的绕法**：形参改名 `fnam`。**根因没修** —— 正确方向是**参考实现拒**（关键字不许做绑定名，两个实现才谈得上一致），那是一次语言面改动，要走 §5 四条 |

| 13 | **紧凑形 / T2 没有自举镜像**（2026-10-18，**推迟到 0.1.5**） | `tools/lvm_compact.py`（`docs/250`）与 `tools/lvm_t2.py`（`docs/259`）只有 Python 一侧；`loment/tools/lvm.lomt` 里没有紧凑形（`grep -i compact` 无匹配）。于是 `docs/250` §3 E 那条"两个实现逐字节相同"的孪生判据**对它不适用** | 判据 `lvm_compact_test.py::test_the_mirror_is_still_deferred` 钉住"仍然没有"：镜像一开工它就红，逼着按 §5 四条一起走、并把这条删掉。排期在 #586（0.1.5）。**"紧凑形的判据全绿"不等于"孪生过了"** —— 它只说明 Python 那一侧自洽 |

## 5. 改冻结面的流程（四条，缺一不可）

1. **改规范**：先改 `docs/manual/`（或对应的语言章节），把新规则写成可判定的句子；
   若涉及诊断，先在 `tools/loment_diag.RULES` 里给码（**码只增不改**；新规则加 E018+）。
2. **改一致性套件**：在 `tools/loment_rule_parity.py` 的 `_CASES` 里加**最小负例**，
   并**上调** `BUDGET`。**只调低 BUDGET 是放松门禁，等于隐瞒缺口** —— 门禁会因此变红。
3. **两个实现同一次提交**：`tools/lomentc.py`（参考）与 `loment/selfhost/checker.lomt`
   （自举）必须一起改；`loment_rule_parity`、`loment_p8_test`（含 40/40 逐字节一致与
   三阶段定点）全绿才算完成。
4. **过静态门禁**：`python tools/ci.py --static-only` 里的 L0/L1 门禁全绿；
   若触及内核线按名解析的符号（§2 那一条），必须先走 docs/155 的交接约定。

**2026-09-15 加的一条（名字形式 `use <名字>`，E018）** —— 记在这里是因为它**没走第 2 条**：
它是**装载器规则**，不是检查器规则，而 `loment_rule_parity` 喂的是**自包含单文件源码**，
结构上装不下"解析一个导入名"这件事。所以：

- 第 1 条照走：规范改了 `docs/143`（两种写法 + 搜索根 + 唯一性），码是 `loment_diag` 的
  **E018**（新规则加 E018+，码只增不改）—— 找不到与有歧义**共用一个码**，因为用户要做的是
  同一类事（改这个 use，或改文件布局），是哪种由消息本身写明；
- 第 2 条的**意图**（"这条规则要有棘轮盯着"）改由两处承担：参考实现的
  `lomentc_test`（解析/找不到/歧义/两种写法等价）与自举侧的**驱动闸门**
  （`loment_p8_test` 里"名字导入失败必须报错"）。`BUDGET` **不动** —— 它数的是检查器规则，
  把一个装载器规则算进去才是虚报。

**顺带修掉一处两边不一致（同一次改动）**：自举驱动原先遇到打不开的 `use` 是
"**报一行 stderr 然后接着编**"，于是缺依赖的编译**退出码是 0** —— 产出还是照发的。
参考实现遇到同一种输入是抛错退非零的。这正是这套工具链反复要消灭的"静默错编"
（`tools/lomelf.py` 头注与 §5 上面都记过"把静默错编改成报错退出"），所以两边都改成
**硬失败**：打不开路径、名字解析不出来，一律报出原因后 `die(1)`。判据在
`loment_p8_test` 的驱动闸门里（名字导入失败必须非零退出且消息里点出原因）。

**2026-09-17 的一条（项目模式 `choose`，E022）** —— 已**四条全走完**（§5 开头那四条）。
记在这里是因为它跨了两种规则，且和 E018 那次撞上同一个结构。

- **第 1 条**：`docs/143` §3.2 把要判的那几条写成可判定的句子 —— 至多一次、模式名只能是
  `std`/`no_std`、只有根单元能写。码是 `loment_diag` 的**新码 E022**（码只增不改），
  三条消息**共用一个码**：用户要做的是同一类事（改这一行的 `choose`，或把它挪到根单元），
  是哪种由消息写明 —— 与 E018「找不到 / 有歧义」共用一码是同一条理由。
- **第 2 条**：`_CASES` 加了两条检查器负例（`choose-twice` / `choose-bad-mode`），
  `BUDGET` **63 → 65**。
- **第 3 条**：两个实现同一次提交 —— `tools/lomentc.py`（解析 + 三条规则）与
  `loment/selfhost/checker.lomt`（至多一次 + 模式名，第一遍 token 扫描里的一个分支）。
  **`parser.lomt` / `lexer.lomt` 没动**：自举那两个实现的是同一套 token 流，`choose` 在
  自举侧就是个顶层标识符，规则全在 checker 那一遍里判。
- **第 4 条**：`ci.py --static-only` 全绿（含 `loment_rule_parity` 65/65 与 `loment_p8_test`
  的 54/54 逐字节 + 驱动闸门）。

**第三条规则（"库不许 `choose`"）走的是 E018 那条路，不是第 2 条**：它必须由**装载器**判 ——
单元拼完之后检查器拿到的是一整块 token，模块边界已经没了，它分不清这句 `choose` 是入口写的
还是被 `use` 进来的。只有 `load_file` 知道自己在第几层（`depth`）。所以：

- 实现在 `loment/selfhost/driver.lomt` 的 `load_file` 里（`depth > 0 && tok == choose` → 报出
  **是哪个文件**然后 `die(1)`），参考实现在 `lomentc.check` 里按依赖逐个报；
- `loment_rule_parity._CASES` 装不下它（套件喂的是**自包含单文件**源码），`BUDGET` 因此
  **只涨 2 不涨 3**；
- 棘轮改由**驱动闸门**承担：`loment_p8_test::test_m85_driver_checks_before_emitting` 跑
  `loment/selfhost/neg_dep_choose/entry.lomt`，要求非零退出、消息里点出
  `neg_dep_choose/lib.lomt`、且不产出 IR。

**两边的诊断文本不同**（参考是 `13: 库不许 choose（在 lib 里）`，自举是
`fujoc-s: 库不许写 choose …: <路径>`）—— 这与 E018 那一处同类：装载器错在自举侧没有
"行号 + 码"的形状。**判据只比"是否拒 + 是否点出来源"**，不比文本。

**另有前置未做**：`docs/176` §6 主张先做 B0/B1（把"数据"从"逻辑"里拆出来，走仓里已有的
`--dump-*` → `X_data.lomt` 生成管线）再动 `choose` —— 理由是这一次改动的代价结构正是
176 在量的东西。**B0 卡在一处跨线决定**：L0 原语要区分 freestanding / hosted，而那是
`lom/*.lom`（跨线冻结契约，`CLAUDE.md` 第 1 条）的改动，要单独提交并知会 compat 线，
且**标记语法尚未定** —— 不替对方猜。**`choose` 本身不依赖 B0**：模式名只进 checker 与

**2026-09-16 加的一条（名字形式的搜索层 + use 条数上限，E020）** —— 触发原因是用户报的
"装在机器上 `use std` 指向一个不存在的路径"。第 1 条照走：规范改了 `docs/143`（两种写法 +
三层搜索 + 只第③层要唯一 + 300 条上限），码是 `loment_diag` 的 **E018**（三层里任一层的
名字解析失败都归它，用户要做的是同一类事）与**新码 E020**（条数超限；码只增不改）。

两个实现一起改了：`tools/lomentc.py` 的 `resolve_name` / `resolve_deps` 与
`loment/selfhost/driver.lomt` 的 `resolve_use_name` / `load_file`。**顺带修掉两处两边
本就不一致的地方**（都是"静默错编"那一类，与上面 E018 那次同源）：

1. **路径形式的基准**：参考实现是「仓根 → 导入文件所在目录」，自举镜**只按 CWD**。仓库内
   自测看不出（CWD == 仓根），但换成 `deps/<包>/` 这种布局就分叉 —— `deps/std/std.lomt`

2. **单文件 `use` 条数**：自举镜的暂存区按 8 条布局，**第 9 条起静默丢掉**，而参考实现无
   上限 —— 同一份源码两个实现给出**不同的单元**。现在两边都是 300 且超限硬报错。

第 2 条的**意图**（棘轮盯着）由现有两处承担，与上次同一口径：`lomentc_test`（层与上限的
最小用例）与 `loment_p8_test` 的驱动闸门。`BUDGET` 不动 —— 它数的是检查器规则，装载器规则
算进去才是虚报。

**没改的**：`lompi/store/std/0.1.0/` 里 9 个顶层名在两个以上模块重复定义（`hv`/`hx` 三个
文件都有），合并成单元时必然撞平名字空间（E 级错误，不是这里能修的）—— 那是 lompi 线的
包内容，`use std` 要真编出来得先把它们改掉。

**引擎的容量墙（2026-09-16 已修）**。用真包布局跑 `use std` 时先撞上的是三处"按小单元
定死"的容量，现在都按**单元规模**放开了：

| 撞在哪 | 原来 | 现在 |
|---|---|---|
| 单元的词法缓冲 | `(len+64)*20`（= 每源码字节 20 字节，即"1 字节 1 token"的理论上界）；1.86 MB 的单元要 **37 MB**，加上原有 ~30 MB 越过了 PE 垫片的堆上限（`WS_HEAP` 64 MB）→ `fujoc-s: 单元太大` | 按**实测密度**取 10 字节/源码字节（仓库 184 个文件合计 4.81、最密 3.02），并在 `lex_cap` 里**写满就报错**（不再可能静默少 token） |
| codegen 的按函数表 | 320 格，写穿会**静默改名**（`fkind` 被盖成 2） | `CG_MAXFN` 4600 格（`CG_*` 常量 + 与守卫同源），超了 `emit_module` 返回 0 → 驱动器报错退出；整块也从语言自带的 64 KiB bump 堆改由驱动器从 `brk` 开（`cg_arena_bytes()`） |
| checker 的符号表 | 512 格（10240 B） | 92000 B（4600 格）；驱动器在检查前**保守预检**（数 `fn`/`const`/`struct`/`enum` 关键字，上界），超了先报错 |

改完的结果：`use std` 现在**一路走到底** —— 装载、lex、检查全过，报出来的是**真正剩下的
那件事**：E13「函数/常量与模块重名」，正是上面那 9 个包侧的冲突。**引擎不再是瓶颈。**

两条新判据把它钉住：`test_m85_codegen_table_capacity`（容量 >= 最大单元的函数数，
且**守卫与容量常量同源** —— 表放大了守卫还卡旧数同样是写穿）与
`test_m85_heap_budget`（语言堆里不再有固定分配；驱动的固定 brk 块合计 < `WS_HEAP`，
余量留给单元的词法缓冲）。

**2026-09-16 加的又两条（后缀不再属于语言 + 自定义 `loment` 命令，0.1.4-pre1）** —— 这一版
把语言的两个面**交给使用者**，所以冻结面两处要重新划线：

1. **后缀**（`docs/143` §2.3）。原先"L1 必须是 `.lomt`"是**装载器写死的**，现在：
   - **只有 `.lom` 是特殊的**（L0 接口契约，按后缀分流）；**别的任何后缀都是 L1 源**。
     这条是**语法面的放宽**，走第 1 条改规范；它同时让 `use "x.foo"` 这种路径形式成立 ——
     原先它会被当成 L0 去找 `x.lom`，报一句莫名其妙的"不存在"。
   - 名字形式找哪个后缀由**项目**定：项目根（或工具链旁边）的 `loment.conf` 里
     `pub fn source_ext() -> str { return ".foo"; }`。没配就是 `.lomt`。配置**只管名字形式**，
     路径形式自带后缀；默认后缀始终兜底（配了 `.foo` 也还找得到 `.lomt` 的自带模块）。
   - 配置读不出来一律**当没配**（没文件 / 没这个标签 / 值不以 `.` 开头 / 值里带转义）。
     这一条两个实现必须**判断一致** —— 见下面第 2 点为什么。
2. **两个实现的读法必须逐字节同源**。参考实现最初用**完整 parser** 读 `loment.conf`（于是
   要求 `module` 头），自举镜用**词法器**扫标签（`lompi` 读 `lompi.conf` 的做法，不要求
   `module`）。同一个文件于是可能一边认、一边不认 —— 正是这套工具链反复要消灭的
   "两个实现给出不同结果"。改成**两边都走词法器扫标签**（`lomentc._conf_ext_from_tokens`
   ↔ `driver.lomt:cfg_source_ext`），并把转义值在两边一起拒掉：自举镜拷的是**原始字节**、
   参考实现的词法器给的是**解码后的值**，这是唯一还会分叉的口子，而文件名后缀里本不该有
   转义。
3. **自定义命令**（`docs/169`）。`loment foo ...` 先看 `PATH` 上有没有 `loment-foo`，有就
   原样转发（参数不解析、退出码原样带出），没有才交回官方 CLI。这是**启动器**的行为，
   不在冻结面里（§3 的"工具链内部"），但它**改了 CLI 的对外行为**，所以记在这里：
   官方命令**优先**（`loment version` 不受 PATH 影响），且没有注册表 —— 约定就是文件名。

**2026-09-16 又一条（外部函数 `extern fn`）** —— 题目是"兼容 7 个主流语言的库"，
落法是**直接调用外部库（FFI）**，且用户选择**全部自己做**（不把 FFI 构建交回 clang/lld，
保住"不依赖任何外部工具链"）。这**动了冻结面两栏**，是本次要付的代价：

1. **语法与类型规则**：多一个顶层形式 `extern fn name(...) -> T;`（`docs/143` §3.1）。
2. **发射符号约定**：调用约定从"只有自家一套"变成**两套并存** —— Loment 之间仍走自家约定
   （实参走栈），`extern fn` 的调用点走平台 C ABI（ELF: System V / PE: Microsoft x64）。
   这一栏原先的措辞（`tools/lomelf.py:17`）是"**不保证 System V / C ABI** —— 原生产物 v0
   只保证自身自洽，**不给 C 调**"，现在收窄成"**纯 Loment 调用**不给 C 调"。

这次**没有**按 §5 第 2 条加检查器负例进 `loment_rule_parity`：`extern` 的判定是**装载/类型
层**的，不是检查器规则，而那份套件喂的是自包含单文件源码。棘轮改由两处承担：
`lomentc_test` 的正负例（签名形态、重名、无体）与**新增的门面判据**（一个 `.c` 编成 `.o`，
Loment 用 `extern fn` 调它，**由 `lomelf` 单独链接**成可执行文件并跑对）。

**同一次改动要重划线的另外两条（不在 `docs/158`，在各自主处）**：

- `docs/168` §1/§4.3 原写"动态链接**没有**""**不做二进制分发**"，理由是泛型是类型定向
  单态化的、使用方必须看得到源码。这条**收窄成**："纯 Loment 不外发二进制"；
  **FFI 是另一个明确模式**，它消费看不看得到源码都行的外部码。
- `docs/155` §3.7 把"无未定义符号"当成不变量。收窄成"**纯 Loment 单元**无未定义符号" ——
  带 `extern` 的单元**必然**有未定义符号，那正是链接器要去解开的东西。
