# 349 · 语义 oracle：把"应该是什么"从两个实现里拿出来

> 状态: **S1 原型已落地（2026-11-17）** · 上游: `docs/158` §5（双实现逐字节）·
> `docs/228`（表层语义审计）· `standard/LLS.md`（条款来源）· `#513` §12（共错盲区）
> 落点: `semantics/loment_sem.lls`（Loment 写的源级解释器）· `semantics/corpus/*.lomt`
> （10 份语料）· `tools/loment_oracle_test.py`（7 条判据）· `tools/loment_oracle.py`
> （第二读，只作交叉）
>
> 一句话: **仓里所有灯都是"两个实现一致"，没有一盏是"对"。这一页把那盏灯装上 ——
> 用 Loment 写一个只读规范的源解释器，拿手推的期望值当尺子。**

## 1. 问题：一致性证明不了一致之外的东西

现有判据的形状是**对照**：参考编译器与自举编译器发同一份 IR（`loment_p8_test`）、
两只链接器发同一份 ELF（`loment_elf_test`）、三个引擎跑同一份字节（`lvm_test`）、
Potato 对象两份校验器逐条判决相同（`potato_test`）。它们回答的问题是
"**两份实现是否相同**"，而我们要的答案是"**是否对**"。

两者在缺陷为**单边**时重合，在缺陷为**共边**时分开。共边不是假想：

* `#432`：`i1` 宽度 —— 两只链接器一起按 i8 处理；
* `#431`：结构体字段偏移 —— 两边一起错；
* `#513` §12 原话：「A criterion that compares the two twins is green on a shared defect;
  only an independently derived expectation catches it.」

2026-11-17 之前，仓里唯一能抓共边的东西是**手写的期望值**，而它们散在各条判据里，
一两条一次，没有系统。`docs/228` 的审计探针是同一思路的一次性版本。

## 2. 为什么不是"直接形式化证明"

把"应该是什么"钉死最硬的办法是：给核心语言写操作语义、在证明助手里机械化、
再证编译器或翻译验证正确。这条路**现在不做**，理由不是懒：

1. **语言每周在动**。`lom/*.lom` 之外的一切都在变（编译器近两天的 churn 见 `CLAUDE.md`），
   一份机械化语义的维护成本 ≈ 再养一个实现，而它不产生任何用户可用的产物。
2. **证的边界与用户的边界不一致**。用户碰的是七个表层语法 + 能力域 + GC/LMS/LSPE
   四套运行期；可机械化证明的核心子集，恰好是不出问题的那一层。
3. **投入产出的时间尺度对不上**。0.1.5.x 的里程碑按周算，形式化按年算。

**可拿掉的假设**（这就是本页的提案）：

> ~~期望值必须由人一条条手写~~ → **期望值可以由一份"只读规范的独立实现"算出来**。

它便宜、能长、可维护；它**不证明**编译器正确（见 §8 的诚实条款），但它让"共边缺陷"
从**不可见**变成**可测** —— 这是从 0 到 1 的那一步。

## 3. 方案：三层，越往下越贵

### 3.1 正本 oracle：用 Loment 写的源解释器（S1，已落地）

`semantics/loment_sem.lls` 是 Loment 源（`.lls` 扩展名 DEV 工具链直接吃），
`lomentc` + `lomelf` 编成原生可执行文件，读一份 `.lomt`，**直接解释**它，
输出"按规范应当写到的 stdout 与退出码"。

纪律（判据 `test_oracle_is_independent` 钉住）：

* 只照 `standard/LLS.md` 的条款写，**不 import** 编译器/链接器/格式器的任何代码；
* 每一格覆盖都写清条款号（§10.2 回绕、§12.5 短路、§14.1 入口 …），判据核对引用表；
* 用 Loment 写（而不是 Python），顺带让"语义"和"语言"互相验证：
  写 oracle 时踩到的每个语言坑本身就是一条读数（见 §6.3）。

### 3.2 第二读：Python 重写一遍（S1，只作交叉）

`tools/loment_oracle.py` 是同一张规范的另一份读法。它不是判据的期望值来源，
作用是**分工不同的三方差**：Loment oracle、Python 第二读、被验实现，两两独立。
两份读法一致，才能把"oracle 自己也错了"的概率压下去。

### 3.3 手推期望表：地基（S1）

`tools/loment_oracle_test.py` 的 `CASES` 是**人手照条款推出来的**字节串，
不是任何实现算的。10 份语料各带一句推导注释。oracle 与实现都必须对这张表说话。

三层的关系是：**表 > 两份读法 > 实现**。任何一层红，先查它上面那层。

## 4. 第一版的实现

`semantics/loment_sem.lls`（约 2000 行，Loment）：

## 6. 首轮实测

### 6.1 三方一致

10 份语料、三个执行者（Loment oracle / 原生 / LVM 有入口的那一份）+ 第二读：
**全部与手推表逐字节一致**。这是第一份"不是靠两个实现互相看"的证据。

### 6.2 抓到两条真分歧

| 编号 | 规范说 | 实现做 |
|---|---|---|
| `main-with-return-type` | LLS §14.1: "A `main` with a return type is refused" | 接受 `fn main() -> u32`，入口桩**静默丢掉返回值**，退出码恒 0 |

这不是 oracle 的误读，两条独立读法都拒。它属于"规范与实现对不上"，不是编译器崩了——
但正是这类**静默**分歧最难被现有判据看见（没有任何两条实现会为它吵架）。
处理方式：进 `KNOWN_DIVERGENCES` 与判据 `test_known_divergences_are_still_there`，
**先记录、不擅自改语义**（改哪边是产品决定，见 §9）。

**第二类（S2 期间发现，`#1642`）**：两个版次各丢一件规范要求的事 ——
2026.2 的读法拒 `p.x = 99`（§11.4 说字段是左值），默认读法拒 `let mut x`（§11.2 说收下并抹掉）。
判据 `test_edition_divergences_are_still_there` 钉住"不对称仍存在"；修好后它会红。

### 6.3 写 oracle 时踩到的两件事（顺带读数）

1. **`const` 只吃字面量**（仓内参考编译器）：`const M_NODE: u32 = 65536 + 65536;` 被拒；
   装包的 0.1.4.5 却接受并**编出了错的产物**（节点写到 token 表上）。
   原型因此固定用仓内链路编译，并在常量里写死字面量。
2. **`as T <<` 的经典坑**（issue #316）：`1 as u32 << (i * 8)` 被读成泛型实参；
   必须写 `(1 as u32) << (i * 8)`。oracle 里留了注释。

## 7. 往后（S2 / S3）

**S2：把语料变成覆盖面（进行中：第一增量覆盖 §11.6 / §11.7 / §18.1 的四个内建）。**

* 覆盖字典：模板 / 泛型 / 能力域 / 闭包（`docs/348`）/ 标签联合——按"用户最常写的形状"
  排序，一次一类；
* 每加一类，先加**语料与手推表**，再让 oracle 支持它；oracle 拒的每一格都得点名条款；
* 运行方式不变：三条判据（表 / oracle / 实现）永远同一张表。

**S3：信任根与"独立血缘"。**

* 现在的自举起点是一个提交进来的 genesis ELF，能被验证到的程度是"旁边的校验和说它没变"
  （`#513` §6）。oracle 给了一条新路：**不验字节，验行为** —— 用 oracle 的期望值
  跑 genesis 产出的编译器，语义一致才算数；
* 真正的 diverse double-compiling（第二条独立编译器血缘）仍是研究项目，本页只把
  "语义层面的独立证据"摆到桌上。

## 8. 诚实条款（oracle ≠ 真理）

1. **oracle 是一份读法，不是标准本身。** 它可能与实现**共享对规范的误读** ——
   第二读与手推表就是为了压低这个概率，但压不到 0。
2. **oracle 自己的算术跑在它正在检查的那一层上。** 这是自举语义的固有循环：
   回绕、截断、比较都是 Loment 算的。缓解：回绕显式按宽度实现（不用宿主算术），
   再加 Python 第二读。
3. **oracle 覆盖的是子集。** 子集之外它**点名拒**，不猜。拒的那一格没有证据，
   不等于"没问题"。
4. **界外行为不测。** 越界下标、除零在规范里不是值（§10.2 / §12.10）；
   oracle 把它们当 trap，语料不拿它们当差分信号。
5. **"一致"仍然只是必要条件。** oracle 与实现都同意、手推表也同意，仍然可能是三份
   共同的误读。这张网比"两份实现互相看"密，但它不是证明。

## 9. 不做什么

* **不把 oracle 接进编译器链路。** 它是判据的尺子，不是产物的一部分；
* **不因为分歧就改语义。** `main-with-return-type` 这类先登记，改哪边要单独裁定
  （改实现 = 可能破坏既有用户；改规范 = 一次明确的契约变更）；
* **不用它替换孪生判据。** 两者问的问题不同：孪生问"是否一致"（回放、逐字节、发布），
  oracle 问"是否对"（语义）。两盏灯都要；
* **不在 S1 扩到全语言。** 一份小、可读、条款对得上的解释器，比一份大而含糊的有用。

## 10. 发行版锁：`.lls` 永远不随发行版编译（用户 2026-11-17 定）

**规则**：发行版工具链**永不编译 `.lls`**。写了 `.lls` 规则文件，发行版编译器直接拒绝
（E0228），开发版照常编译。

**为什么锁死**：`.lls` 是**规范/语义源**，它回答的是"应该是什么"。一旦它成为发行版的
输入，判据的尺子就落进了被测系统里 —— 尺子必须留在外面。前几道渠道闸
（`choose vm`、端口、`use libl`、`lspe`）打开的条件都是"承诺兑现了"；这一道的答案相反：
**它不该兑现**，所以它不随版本解锁。

**锁从哪来**：同一个渠道常量（`docs/231` §2）。读取点从 `checker.lomt` 的 `check()`
搬到 `driver.lomt` 的入口 —— 检查器只有 token 流，看不见文件名。判据 F
（dev/release 两个种子只差一处）照旧成立。

**判据**：`loment_channel_test` 两端都测 —— dev 必须**收** `.lls`（否则"发行版拒"可能
只是因为它什么都拒），发行版必须**拒**；Python 与自举驱动器各一份。
